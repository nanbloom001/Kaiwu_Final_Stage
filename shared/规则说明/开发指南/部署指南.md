# 部署指南

> Source: https://tencentarena.com/docs/p-competition-legged_robot_competition_26/27.0.21/guidebook/dev-guide/deployment/

> 部署前必读：实机部署涉及机械、电气、网络与软件多环节交叉，模型失控可能对人员、四足机器人本体和周围环境造成损害。请先完整阅读 安全规范 并在仿真环境下完成充分测试，再进入真机部署阶段。

本文档介绍如何将开悟平台上训练完成的模型（`.pkl`）部署到 Unitree Go2 真机的 `Jetson Nano` 主板，并完成速度命令模式验证。

文档内容分为三部分：

- 主线流程（第 1-4 章）：按用户真机部署流程组织，覆盖环境连接、部署包准备和上机测试。
- 问题排查（第 5 章）：汇总部署过程中常见报错与异常现象。
- 附录 A：提供 ONNX 契约、状态机、深度输入处理等原理参考，用于理解部署链路及排查问题。

文中通过方括号标注执行机器：

- 【用户电脑】：用户用于准备部署代码包、导出模型和上传文件的工作机
- 【Jetson】：Go2 机载 `Jetson Nano` 主板，通过 SSH 登录后操作
- 【任意】：任意可运行 Python 或编辑文本的机器
- 【现场】：需要操作人员在四足机器人旁配合完成的步骤

---

## 1. 部署流程总览

真机部署主线流程如下：

1. 连接四足机器人与基础环境：完成物理连接、网络配置、SSH 登录、联网及时间同步，并完成相机标定。
2. 准备部署代码包：将部署代码包下载到用户电脑，导出 `policy.onnx`，准备 `deploy.yaml`，再将整个部署包上传至 Jetson 并完成编译。
3. 进行 Fixed Loco 测试：配置 `config.yaml`，执行预检，启动控制器并通过手柄完成状态切换与停止。

如在部署过程中遇到异常，可直接查阅第 5 章 常见问题排查；如需了解相关实现原理，可参考附录 A。

## 2. 连接四足机器人与基础环境

注意：四足机器人配件连接和安装过程中，请勿热插拔机身配件。

### 2.1 前置物料清单

| 物料 | 说明 |
| --- | --- |
| 网线 | 用于连接 Go2 与用户电脑 |
| 训练产出的 .pkl 模型文件 | 用于导出部署模型 |
| deploy_loco 部署代码包 | 下载链接见第 3 章目录结构部分 |
| D435i 深度相机 | 后续需按第 2.7 节完成标定 |
| UWB 标签和控制器 | 仅在使用 UWB 相关能力时需要 |
| 无线网卡 | 用于四足机器人安装外部依赖包 |
| 泡沫积木 | 多个 |

### 2.2 物理连接、网卡配置与开机 【用户电脑】

控制命令通过局域网从用户电脑发送至 Go2 机载电脑。操作步骤如下：

1. 使用网线连接 Go2 与用户电脑。
2. 短按后长按 Go2 电源键，启动 Go2。
3. 打开用户电脑 IPv4 配置，将网卡 IP 设置到 `192.168.123.*` 网段，建议设置为 `192.168.123.10`。其中 `.18` 为 Jetson 地址，不可占用；子网掩码设置为 `255.255.255.0`。
4. 通过 `ifconfig` 检查 IP 配置是否正确。

### 2.3 SSH 登录 Jetson 【用户电脑】

```
ssh unitree@192.168.123.18
# 默认密码 123
```

后续标注 【Jetson】 的步骤，均在该 SSH 会话中执行。

### 2.4 安装无线网卡 【Jetson】

由于 `Jetson Nano` 主板自带网卡通常不直接连接外网，建议额外接入无线网卡（如 `Tenda W311MI V6.0`）。

- 驱动下载：[690938082103365.zip](https://drive.weixin.qq.com/s?k=AJEAIQdfAAoZ3N67jVAEcAkgb7ACc)
- 安装参考：[腾达指南](https://tenda.com.cn/material/show/200)

### 2.5 连接互联网 【Jetson】

```
sudo nmcli device wifi rescan
sudo nmcli device wifi connect <SSID> password <password>
ping www.baidu.com
```

### 2.6 同步系统时间 【Jetson】

若系统时间未同步，`pip` 下载依赖时可能因证书校验失败而中断。请执行以下命令：

```
sudo apt update
sudo apt install -y chrony
sudo systemctl enable --now chrony
sudo chronyc makestep
```

### 2.7 相机标定 【Jetson】

至少需要完成一次相机标定，仿真训练阶段使用的相机内参与真机 `RealSense` 设备存在差异，部署前需依据真机内参进行深度图重投影对齐。若标定不准确，模型在真机侧接收到的视觉输入将偏离训练分布，从而影响 `loco` 步态表现。

以下情况需要重新标定：

- 首次部署
- 新增外置相机
- 更换或调整外置相机安装位置

请参考 [相机标定代码包](https://git.code.tencent.com/aiarena/open-competition-2026/unitree_isaaclab_deploy/blob/master/camera_calibration) 及 [README.md](https://git.code.tencent.com/aiarena/open-competition-2026/unitree_isaaclab_deploy/blob/master/camera_calibration/README.md) 完成标定，并将标定结果写入相应配置文件。后续用于部署的模型，必须基于标定后的相机参数完成训练；否则真机视觉输入与训练阶段不一致，具体原理见附录 A.6。

整体部署顺序如下：

| 步骤 | 执行机器 | 说明 |
| --- | --- | --- |
| 3.1 | 【用户电脑】 | 将部署代码包拷贝到用户电脑 |
| 3.2 | 【用户电脑】 | 根据模型文件导出 policy.onnx 并完成数值对拍 |
| 3.3 | 【用户电脑】 | 准备 deploy.yaml |
| 3.4 | 【用户电脑 → Jetson】 | 将部署代码包（包括policy.onnx 和 deploy.yaml）上传至 Jetson |
| 3.5 | 【Jetson】 | 编译 go2_loco_ctrl |

### 3.1 将部署代码包拷贝到用户电脑 【用户电脑】

将部署代码包（仓库）下载到用户电脑本地，作为后续 `policy.onnx` 导出、`deploy.yaml` 准备与 Jetson 上传的源头。可使用 `git clone` 或下载压缩包后解压任一方式：

```
git clone https://git.code.tencent.com/aiarena/open-competition-2026/unitree_isaaclab_deploy.git
cd unitree_isaaclab_deploy
```

完成后，确认本地已具备 `unitree_isaaclab_deploy/deploy_loco/` 目录结构，便于后续小节直接进入 `deploy_loco/` 内操作。

### 3.2 导出 `policy.onnx` 【用户电脑】

#### 3.2.1 安装依赖

```
pip install torch onnxruntime onnx pyyaml
```

#### 3.2.2 执行导出脚本

在用户电脑上进入 `deploy_loco/` 目录后执行导出脚本，导出文件会落在部署代码包内的对应位置：

```
cd unitree_isaaclab_deploy/deploy_loco
python3 export_loco_onnx.py \
  --ckpt models/model.ckpt-lbc-loco-637427.pkl \
  --out runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx \
  --opset 17 \
  --frames 8
```

其中：

- `--ckpt`：实际训练产出的模型文件及路径（`.pkl`）。
- `--out`：输出到 `deploy_loco/runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx`，与第 3.4 节 `rsync` 上传后在 Jetson 上的目标路径保持一致。
- `--opset 17`：与 Jetson 侧 `ONNX Runtime 1.19.2` 兼容。
- `--frames 8`：执行多帧数值对拍，包含 `loco LSTM` 状态回喂，相关说明见附录 A.4。

脚本执行时会先校验 `ckpt['format'] == 'lbc_loco'`；若格式不匹配，将直接报错退出。

#### 3.2.3 导出成功标志

```
[OK] 权重加载完成（loco CNN+LSTM+head、teacher_actor）。
[OK] 已导出 ONNX → runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx
[VERIFY] 通过 ✅
```

只有在出现 `[VERIFY] 通过` 后，才可继续后续部署。

需要注意：`[VERIFY] 通过` 仅表示当前导出 `wrapper` 与 ONNX 图在对拍时一致，并不自动保证导出脚本仍与训练侧最新网络结构完全对应。若训练阶段修改了网络结构（如 CNN、LSTM 层数、`proprio` 维度、观测 scale 等），则必须同步调整导出脚本；否则即使对拍通过，导出的 ONNX 仍可能与实际训练网络不一致。相关修改项见附录 A.2。

### 3.3 准备 `deploy.yaml` 【用户电脑】

`deploy.yaml` 必须从与当前模型对应的训练配置中获取，并与 `ckpt` 保持同源。若关节映射、默认姿态、`KP/KD` 或观测 scale 配置错误，四足机器人可能在真机侧出现异常姿态。具体原理见附录 A.5。

#### 3.3.1 从训练配置中提取

训练配置路径如下：

```
agent_ppo/conf/train_env_conf_xxx.yaml
```

在线 IDE 运行 `train_test` 后，会根据当前配置生成：

```
agent_{algo}/conf/deploy.yaml
```

对于 `loco` 阶段，速度由 `config.yaml` 中的 `fixed_cmd` 或 UWB 输入提供，因此 `deploy.yaml` 主要关注关节映射、动作 scale 和 PD 参数。

#### 3.3.2 必填字段自检

精简部署契约至少应包含以下字段：

```
joint_ids_map: [...]
step_dt: 0.02
stiffness: [...]
damping: [...]
default_joint_pos: [...]
actions:
  JointPositionAction:
    scale: 0.25
    offset: [...]
    clip: [-100.0, 100.0]
proprio_scales:
  ang_vel: 0.25
  projected_gravity: 1.0
  vel_cmd: 1.0
  joint_pos_rel: 1.0
  joint_vel_rel: 0.05
  last_action: 1.0
proprio_clip: [-100.0, 100.0]
cmd_ranges:
  ranges:
    lin_vel_x: [...]
    lin_vel_y: [...]
    ang_vel_yaw: [...]
  limit:
    lin_vel_x: [...]
    lin_vel_y: [...]
    ang_vel_z: [...]
  resampling_time_s: [10.0, 10.0]
```

#### 3.3.3 放置到部署代码包内

将准备好的 `deploy.yaml` 拷贝到部署代码包内的对应位置，使其在第 3.4 节 `rsync` 上传后能够落在 Jetson 的目标路径上：

```
cp <你的deploy.yaml来源路径> runtime/unitree_rl_lab_test/logs/loco/params/deploy.yaml
```

放置后，`deploy.yaml` 在部署包内、Jetson 上的对应路径为：

| 文件 | 部署包内路径 | Jetson 上路径 |
| --- | --- | --- |
| deploy.yaml | deploy_loco/runtime/unitree_rl_lab_test/logs/loco/params/deploy.yaml | ~/Kaiwu-test/sim2real_test_loco/runtime/unitree_rl_lab_test/logs/loco/params/deploy.yaml |
| policy.onnx | deploy_loco/runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx | ~/Kaiwu-test/sim2real_test_loco/runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx |

### 3.4 将部署代码包（含 `policy.onnx` 和 `deploy.yaml`）上传至 Jetson 【用户电脑 → Jetson】

完成 `policy.onnx` 导出与 `deploy.yaml` 准备后，将整个 `deploy_loco/` 目录上传到 Jetson。`policy.onnx` 与 `deploy.yaml` 已位于 `deploy_loco/` 内的对应路径下，会随目录一并同步到 Jetson 的目标位置。

在用户电脑上进入 `unitree_isaaclab_deploy/` 目录（即 `deploy_loco/` 的父目录）后执行：

```
cd unitree_isaaclab_deploy
rsync -av deploy_loco/ unitree@192.168.123.18:/home/unitree/Kaiwu-test/sim2real_test_loco/
```

若 Jetson 上目标目录不存在，请先在 Jetson 侧创建：

```
mkdir -p ~/Kaiwu-test/sim2real_test_loco/runtime/unitree_rl_lab_test/logs/loco/{exported,params,logs}
```

### 3.5 编译 `go2_loco_ctrl` 【Jetson】

#### 3.5.1 确认 `RealSense` 设备

```
rs-enumerate-devices -s
```

输出中必须出现 `Intel RealSense`。若未检测到相机，请先处理相关问题，再继续后续步骤，详见第 5.5 节。

#### 3.5.2 编译

```
cd ~/Kaiwu-test/sim2real_test_loco/runtime/unitree_rl_lab_test/deploy/robots/go2_loco
mkdir -p build && cd build

cmake .. \
  -DUSE_REALSENSE=ON \
  -DONNXRUNTIME_ROOT=../../../thirdparty/onnxruntime-linux-aarch64-1.19.2

cmake --build . -j"$(nproc)"
```

#### 3.5.3 确认编译结果

```
test -x go2_loco_ctrl && echo "go2_loco_ctrl build OK"
ldd go2_loco_ctrl | grep -E 'onnxruntime|realsense|unitree|ddsc'
```

若 `cmake` 提示找不到 `RealSense`，则当前二进制不可用于正式 `D425i/D435i` 测试，应先完成环境修复后再继续。

如出现 `libddsc.so.0` 或 `libddscxx.so.0` 缺失提示，可继续执行后续步骤；`run_loco_stage_test.sh` 会通过动态设置 `LD_LIBRARY_PATH` 解决该问题。

## 4. Fixed Loco 测试

`FSM` 三态、手柄按键及急停优先级说明见附录 A.7。

执行前请检查 `run_loco_stage_mode.sh` 和 `run_loco_stage_test.sh` 中的路径配置（`LOCO_TEST_ROOT`）是否正确。

### 4.1 修改 `config.yaml` 【Jetson】

目标文件：

```
runtime/unitree_rl_lab_test/deploy/robots/go2_loco/config/config.yaml
```

配置示例如下：

```
FSM:
  VisionLoco:
    type: VisionLoco
    policy_dir: ../../../logs/loco
    depth:
      source: realsense
      constant_value: 0.6
    goal: [0.0, 0.0, 10.0, 0.0]
    command_source: fixed
    fixed_cmd: [0.30, 0.0, 0.0]
    uwb:
      topic: rt/uwbstate
      max_vx: 0.30
      max_wz: 0.40
      yaw_kp: 0.80
      stop_distance: 0.35
      slow_distance: 1.00
      turn_in_place_angle: 1.0472
      stale_timeout: 0.50
      cmd_slew_rate: [0.30, 0.30, 1.00]
    logging:
      enabled: true
      flush_every: 50
      max_consecutive_errors: 5
      max_raw_action_abs: 20.0
```

若仅需临时调整固定速度，请修改 `fixed_cmd`。在 fixed 模式下，`goal` 不参与速度生成，仅写入诊断日志。

### 4.2 上机前预检 【Jetson】

```
cd ~/Kaiwu-test/sim2real_test_loco
pgrep -af go2_loco_ctrl
./scripts/run_loco_stage_fixed_test.sh --check
```

执行 `--check` 时不会启动 `go2_loco_ctrl`，而是执行以下预检查：

1. 解析 `config.yaml` 中的 `FSM.VisionLoco` 配置，校验 `command_source ∈ {fixed}`、`fixed_cmd` 长度为 3、`uwb.max_vx ∈ [0, 0.3]`。
2. 自动查找拥有 `192.168.123.18/24` 地址的网卡，无需手动指定 `--network`。
3. 校验网卡 `operstate == up` 且 `carrier == 1`。
4. 通过 `pgrep -x go2_loco_ctrl` 避免重复启动控制器。
5. 校验 `logs/loco/exported/policy.onnx` 和 `go2_loco_ctrl` 二进制是否存在。
6. 当 `depth.source = realsense` 时，通过 `rs-enumerate-devices -s` 检查 `Intel RealSense` 是否存在。
7. 启动时会自动备份 `config.yaml`、`deploy.yaml` 和二进制 `SHA256` 到 `logs/<timestamp>_<mode>/`。

预检通过时，输出示例如下：

```
Preflight: network=eth0, source=fixed, depth=realsense
Fixed command: [0.30, 0.0, 0.0]
Preflight passed. No controller was started.
```

若脚本无执行权限，可执行：

```
chmod +x scripts/*.sh
```

### 4.3 启动控制器 【Jetson + 现场】

在 SSH 终端执行：

```
cd ~/Kaiwu-test/sim2real_test_loco
./scripts/run_loco_stage_fixed_test.sh
```

正常情况下，控制台将输出类似内容：

```
Preflight: network=eth0, source=fixed, depth=realsense
Fixed command: vx=0.15 m/s, vy=0 m/s, wz=0 rad/s
Controller: L2+A -> FixStand, L2+X -> VisionLoco, L2+B -> Passive.
```

启动成功后，二进制会打印 `Go2 Loco Controller`。

### 4.4 手柄状态切换 【现场】

操作顺序如下：

1. 按 `L2 + A`，进入 `FixStand`。
2. 检查站姿、关节方向及是否存在明显抖动；如有异常，请立即停止并检查第 5.7 节。
3. 部分手柄固件版本在进入 `FixStand` 后，还需按 `Start` 完成使能。
4. 按 `L2 + X`，进入 `VisionLoco`。
5. 建议先悬空观察 `3-5` 秒，确认四腿动作正常后，再进行落地测试。
6. 按 `L2 + B`，可随时退出到 `Passive`。

### 4.5 停止 【现场】

```
L2 + B    （首选：立即进入 Passive）
Ctrl + C  （次选：终止脚本）
```

不建议通过强制断电停止系统，以免日志丢失并造成 Jetson 与手柄状态不一致。

## 5. 常见问题排查

请根据实际报错信息或现象，直接查阅对应小节。以下标题均来自实际终端输出或常见异常表现。

### 5.1 `eth0: does not match an available interface`

该问题通常与接口名或静态 IP 配置不匹配有关。

```
ip -4 -o address show
```

请确认拥有 `192.168.123.18/24` 的接口名称，并注意：`--network` 参数需要传入接口名，而不是 IP 地址。若未显式传入 `--network`，脚本会自动查找对应接口。

### 5.2 `Failed to create domain explicitly`

该问题通常表示 `CycloneDDS` 未找到指定网卡，或网卡未处于 `UP` 状态、未建立物理链路。建议先修复网卡状态，再重新启动控制器。

```
ip -o link show
cat /sys/class/net/<iface>/carrier
```

其中 `carrier` 应输出 `1`。

若同时出现 `libddsc.so.0 not found` 报错，通常是因为 `Unitree SDK` 的 `CycloneDDS` 共享库位于 `/usr/local/lib`，但未写入 `ldconfig` 缓存。`run_loco_stage_test.sh` 已在启动前通过 `export LD_LIBRARY_PATH=/usr/local/lib` 对当前子进程进行修复，无需修改全局配置或重新编译。

### 5.3 `go2_loco_ctrl is already running`

```
pgrep -af go2_loco_ctrl
```

请先确认已有进程是否为上一轮测试残留。建议按以下顺序停止已有进程：`L2 + B` → `Ctrl + C` → 必要时执行 `kill <pid>`。在未确认进程来源前，不要启动第二个控制器实例。

### 5.4 `The other process is using the lowcmd channel`

当前版本在检查 `lowcmd` 前会自动释放 Go2 默认 `sport_mode`。若仍然报错，说明仍有其他低层发布者正在占用该通道。

```
pgrep -af go2_loco_ctrl
ps -eo pid,ppid,user,lstart,cmd | grep -Ei 'go2_loco_ctrl|lowcmd|unitree|loco|controller' | grep -v grep
```

在连续测试过程中，当前程序退出后可直接运行下一模式脚本；通常不需要重启系统。

### 5.5 `no Intel RealSense depth camera was detected`

```
rs-enumerate-devices -s
```

输出中必须出现 `Intel RealSense`。若未检测到相机，请勿继续进行正式落地测试。

当 `source: constant` 时，仅适用于悬空链路排障；`loco latent` 仍然依赖深度输入，常量深度会使视觉信息退化为零输入。

请检查相机连接状态及数据线是否正常。

### 5.6 找不到 `policy.onnx` 或 `deploy.yaml`

正确路径如下：

```
runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx
runtime/unitree_rl_lab_test/logs/loco/params/deploy.yaml
```

两个文件必须同时存在：

- `policy.onnx`：来自第 3.2 节导出与第 3.4 节上传
- `deploy.yaml`：来自第 3.3 节准备与第 3.4 节上传

### 5.7 四足机器人站姿或腿方向异常

请立即按 `L2 + B` 使四足机器人进入 `Passive`，然后重点检查以下配置：

- `joint_ids_map`（应为 `0..11` 的完整排列）
- `default_joint_pos`
- `action.offset` / `action.scale`
- `KP` / `KD`
- `checkpoint` 与 `deploy.yaml` 是否同源

`deploy.yaml` 与 `ckpt` 不同源是该类问题最常见的原因，详见附录 A.5。

## 附录 A：原理参考

### A.1 `ckpt` 格式：本包部署 `lbc_loco`

当前部署包 `deploy_loco` 仅支持部署 `lbc_loco` 类型的 `ckpt`。该模型包含 `vision_encoder_state_dict` 与 `teacher_actor_state_dict`，其顶层字段满足 `format == 'lbc_loco'`，对应单管线 `loco` 阶段产物。

其中：

- `vision_encoder_state_dict` 的子模块前缀为 `cnn.`、`rnn.`、`rnn_output_layer.`
- `teacher_actor_state_dict` 对应 `loco` 阶段的 12 关节 actor

`export_loco_onnx.py` 会强制校验 `format == 'lbc_loco'`，并检查上述前缀是否存在；若校验失败，将直接退出。

### A.2 ONNX 转换原理

#### 为什么需要 ONNX

Jetson 侧的 C++ 运行链路不会直接加载 PyTorch、训练仓库及完整 Python 依赖。ONNX 的作用是将训练侧计算图序列化为中间格式，使部署侧仅通过 `ONNX Runtime` 调用模型，训练框架与推理框架由此解耦。

#### 为什么需要 `wrapper`

训练阶段的 `nn.Module` 并不是一个简单的纯函数，其中包含：

- 教师与学生两条前向路径
- 探索噪声、dropout 和采样逻辑
- `LSTM` 隐式状态
- 训练期由 `command_manager` 写入的 `proprio[6:9]`
- 训练阶段使用的观测 scale

因此不能直接执行 `torch.onnx.export(model)`。部署时需要通过 `export_loco_onnx.py::LocoExportWrapper` 显式构造部署推理路径，并将跨帧状态作为显式输入输出：

```
class LocoExportWrapper(nn.Module):
    forward(depth, proprio, goal,
            loco_h, loco_c, nav_h, nav_c, cmd_override) ->
            (cmd, cmd_raw, clearance, joint,
             loco_h_out, loco_c_out, nav_h_out, nav_c_out)
```

该路径逐行复刻 `agent_ppo/algorithm/algorithm_lbc.py` 中的 `act_student` 推理逻辑，仅保留真机部署所需的 `loco` 推理分支。

#### 训练模型变更后需同步调整导出脚本的部分

`export_loco_onnx.py` 中的 `SimpleCNN`、`build_teacher_mlp` 和 `LocoExportWrapper` 均为训练模型结构的手写副本。若训练结构变更，导出脚本必须同步更新。常见对应关系如下：

| 训练侧改动 | 导出脚本中需同步修改的位置 |
| --- | --- |
| proprio 维度变化 | PROPRIO_DIM = 45 及其联动维度 |
| CNN 或 latent 维度变化 | CNN_OUT = 32、LATENT_DIM = 32 |
| LSTM 层数或隐藏维度变化 | LSTM_HIDDEN = 64、LSTM_LAYERS = 2 |
| 关节数变化 | NUM_ACTIONS = 12 及相关关节数组长度 |
| teacher MLP 隐层变化 | TEACHER_HIDDEN = (512, 256, 128) |
| CNN 卷积结构变化 | SimpleCNN.__init__ 与 _compute_conv_output_size |
| vision_encoder_state_dict 前缀变化 | load_weights 中的前缀提取逻辑 |

每次修改后，应遵循以下原则：

1. 先重新完成 `[VERIFY] 通过`。
2. 逐项对照 `wrapper.forward` 与训练侧 `act_student` 的实现，确保 latent 归一化与拼接顺序完全一致。
3. 真机部署前，必须完成 `wrapper` 与训练侧 PyTorch 模型之间的数值对拍，而不仅仅是 `wrapper` 与 ONNX 图的对拍。

### A.3 ONNX 八入八出契约

ONNX 图固定使用 `batch = 1`，`dynamic_axes = None`，以简化部署链路和运行时状态管理。

#### 输入

| 名称 | Shape | 说明 |
| --- | --- | --- |
| depth | [1,180,320,1] | NHWC 格式，值域 [0,1]，无效像素记为 0 |
| proprio | [1,45] | C++ 端每帧推理前需覆写 [6:9] 为速度命令 |
| goal | [1,4] | [orientation, pitch, distance, yaw]，loco 图内忽略，仅记录诊断信息 |
| loco_h / loco_c | [2,1,64] | loco LSTM 真实状态 |
| nav_h / nav_c | [2,1,64] | 原样透传，loco 模式下不参与计算 |
| cmd_override | [1,4] | [vx, vy, wz, gate]，loco 阶段仅回显其前三维 |

#### `proprio[1,45]` 内部布局

| 区间 | 维度 | 含义 | scale |
| --- | --- | --- | --- |
| [0:3] | 3 | body angular velocity | 0.25 |
| [3:6] | 3 | projected gravity | 1.0 |
| [6:9] | 3 | velocity commands | 1.0 |
| [9:21] | 12 | joint position relative to default | 1.0 |
| [21:33] | 12 | joint velocity | 0.05 |
| [33:45] | 12 | previous raw joint action | 1.0 |

整段观测在输入前会执行 `clip(-100, 100)`。这些 scale 与训练阶段保持严格一致，不可在运行时随意调整。

#### 输出

| 名称 | Shape | 说明 |
| --- | --- | --- |
| cmd | [1,3] | cmd_override[:, :3] 的回显 |
| cmd_raw | [1,3] | 与 cmd 相同 |
| clearance | [1,3] | 恒为 0 |
| joint | [1,12] | teacher_actor 输出的原始动作，尚未施加 scale/offset |
| loco_h_out / loco_c_out | [2,1,64] | 下一帧 loco LSTM 状态 |
| nav_h_out / nav_c_out | [2,1,64] | 直接透传输入状态 |

### A.4 数值对拍：为什么必须多帧

对于包含 `LSTM` 的 `loco` 模型，单帧 trace 无法覆盖跨帧状态累积差异，因此 ONNX 导出后的校验必须采用多帧 rollout。校验时，PyTorch `wrapper` 和 ONNX 图各自维护状态张量，并逐帧回喂上一帧输出。

统一容差如下：

| 输出 | abs tol | 说明 |
| --- | --- | --- |
| cmd | 1e-4 | 回显输入命令 |
| cmd_raw | 1e-4 | 与 cmd 相同 |
| clearance | 1e-4 | 恒为 0 |
| joint | 1e-4 | 原始动作输出 |

若未出现 `[VERIFY] 通过`，则不得继续部署。常见失败原因包括：

1. `wrapper` 中子模块的 key 前缀映射错误。
2. `do_constant_folding=True` 误将动态量折叠为常量。
3. `opset` 与实际算子实现不兼容。
4. `dummy input` 触发了与部署阶段不同的执行分支。

### A.5 `deploy.yaml` 必须与 `ckpt` 同源

`deploy.yaml` 中的 `joint_ids_map`、`default_joint_pos`、`KP`、`KD`、`proprio_scales`、`action.scale` 等配置均对应训练阶段的固定状态。若与当前 `ckpt` 不一致，四足机器人将处于错误的观测分布或执行映射下。

典型风险包括：

- `joint_ids_map` 错误：关节控制映射错误，可能导致异常姿态
- `default_joint_pos` 或 `offset` 错误：站姿异常、关节逼近限位
- `KP/KD` 错误：控制带宽偏离训练分布
- `proprio_scales` 错误：模型接收到的观测数值分布失真

静态检查要求如下：

- `joint_ids_map` 为 `0..11` 的完整排列
- 所有关节相关数组长度均为 `12`
- `step_dt = 0.02`
- 关节顺序与 Go2 实际定义一致

### A.6 深度输入：内参重投影而非直接缩放

ONNX 输入中的 `depth[1,180,320,1]` 在进入模型前，由 C++ 侧完成预处理。部署链路不能简单对真机 `RealSense` 深度图执行 `resize`，而应依据仿真与真机内参差异，逐像素执行内参重投影，以对齐训练阶段的几何视角。

仿真阶段的针孔相机参数为：

```
width = 320  height = 180
fx = fy = 168.61  cx = 160  cy = 90
FOV ≈ 87.0° × 56.2°
```

真机 `RealSense (D435i)` 的历史参数为：

```
width = 480  height = 270
fx ≈ fy ≈ 241.9  cx ≈ 242.0  cy ≈ 135.2
FOV ≈ 89.5° × 58.3°
```

由于两者的焦距、主点和视场角均不一致，直接缩放会破坏深度图几何关系。标准做法是：先按仿真内参反算归一化方向，再按真机内参回投影到原始深度图坐标。无效深度、非有限值、`<= 0` 或 `>= 5m` 的像素统一记为 `0`，最终输入 ONNX 的深度张量值域应为 `[0,1]`。

当 `config.yaml` 中 `FSM.VisionLoco.depth.source = realsense` 时，运行时会启用该路径；`source: constant` 仅适用于悬空链路排障。

### A.7 FSM 三态与手柄

`go2_loco_ctrl` 内部通过有限状态机管理运行过程，本文档涉及以下三种状态：

| 状态 | 含义 |
| --- | --- |
| Passive | 开机默认状态或急停后的状态，电机不发力 |
| FixStand | 站立状态，控制器将关节拉回 default_joint_pos |
| VisionLoco | 以 50 Hz 执行 loco ONNX 推理并输出关节目标 |

合法状态切换路径为：`Passive → FixStand → VisionLoco`，返回时通过 `L2 + B` 退回 `Passive`。

手柄按键含义如下：

- `L2 + A`：进入 `FixStand`
- `L2 + X`：进入 `VisionLoco`
- `L2 + B`：进入 `Passive`
- `Start`：部分手柄固件版本下，用于在 `FixStand` 后完成使能

急停优先级为：`L2 + B` → `Ctrl + C` → 物理断电。

### A.8 UWB 使用说明

`UWB` 标签与四足机器人硬件绑定，开启后会自动配对；当指示灯为绿色常亮时，表示配对成功。
