### 0.1 唯一入口选择规则

评估任务配置应显式写入：

```toml
[env_conf]
task_name = "Unitree-Go2-Velocity-Camera"
policy_entry = "visual_policy_optimization"
```

`server/agent_ppo/conf/conf.py` 的入口解析固定按以下优先级读取：

```text
env_conf.policy_entry
env_conf.eval_policy
eval.policy_entry
eval.eval_policy
顶层 policy_entry / eval_policy（兼容旧平台）
```

支持的 Standard 视觉入口别名为
`visual_policy_optimization`、`standard_visual_ppo`、`visual_ppo`；
`lbc_loco` 只在操作者明确选择部署形态 loader 时使用。未知值、字段类型错误或未提供
显式入口时只打印 warning，然后按 `task_name` 推导；不伪造“已使用视觉 PPO”的结论，
必须把实际回退入口写入日志。

### 0.2 两条进程链都必须验证

主进程 `Config.load_conf()` 和平台拥有的环境子进程都必须调用
`agent_ppo.conf.conf._infer_stage_for_eval()`。不得修改或依赖平台会覆盖的
`server/isaac_env/base_env.py`；子进程只通过该兼容符号获得相同选择结果。

启动日志必须出现：

```text
[eval] Explicit policy entry selected: visual_policy_optimization -> visual_policy_optimization
Stage: visual_policy_optimization, task_type: standard, model: VisualActorCritic
[eval] Explicit policy entry selected: visual_policy_optimization -> visual_policy_optimization  # 环境子进程
```

平台 `base_env.py` 只有在自身的默认阶段不同于显式阶段时才会额外打印
`[eval/subprocess] Override Config.CURRENT`；因此不能把“缺少这条额外 override 行”误判为
子进程未生效，必须以子进程中的显式入口日志和最终 `Stage:` 共同核对。

若仍出现 `inferred from TOML task_name`、`Stage: lbc_loco` 或
`[LBC-Loco]`，本次只记录 warning 并停止把该轮结果当作目标入口评估结果；这是结果
有效性标记，不是算法启动硬门禁。

### 0.2.1 P0 实现修改清单

入口修复必须同时覆盖以下运行路径，不能只修改活动 TOML：

1. `agent_ppo/conf/conf.py`：把显式入口解析收敛为唯一函数，并让主进程
   `Config.load_conf()` 与子进程 `_infer_stage_for_eval()` 调用同一实现；明确
   `visual_policy_optimization -> StandardVisualPPOConfig`，只在没有显式入口时才根据
   Camera `task_name` 回退。
2. `agent_ppo/agent.py`：`is_eval` 且 Stage 为 `visual_policy_optimization` 时必须进入
   VisualPPO 学生加载路径；禁止随后无条件调用 `_load_lbc_loco_for_eval()` 把已经选对的
   Stage 再次降级成 LBC loader。加载后打印真实网络类型和实际读取的模块。
3. `agent_ppo/checkpoint_io.py`：评估候选按
   `commandfull -> commandblend -> commandbase -> anchorfinal -> anchoranneal ->`
   旧视觉标签排序；若平台显式给出模型 ID，先在同一 ID 内按标签选择，不能跨 ID
   静默回退。未找到同 ID 时只打印完整 warning 和候选清单，由操作者判断。

   `policy_entry = "visual_policy_optimization"`。平台任务页生成的最终 TOML 也必须包含
   该字段，仓库模板不能替代最终配置回读。
5. VisualPPO 评估 loader：只加载训练包中的视觉学生
   `modules.vision_encoder`、`modules.low_level.actor_state_dict` 和动作分布；不加载 Critic、
   optimizer、S0 anchor 或特权 `height_scan` 推理链。网络维度/必需 key 不兼容才报错；

6. 评估启动诊断必须打印：Stage、loader 名称、checkpoint 绝对路径、文件名 ID、包内 ID、

   `uses_height_scan_at_inference=false`、depth shape/有限率/均值、command 范围和前若干步
   action mean/std/min/max。这样能区分“入口正确但模型没加载”与“模型加载正确但策略异常”。
7. `conf.py` 中旧的 Camera 评估说明必须同步删除或改写：它不得再声称 Camera task

   值选择；只有缺少或无效显式值时才按 `task_name` 回退**。这项文字与实现同步更新，
   避免后续维护者为遵循旧注释再次恢复错误分支。

以上七项全部需要静态测试。第 2、5、6 项还必须通过一次短评估的真实日志验证；本地


这不是 timeout、课程、地形比例或模型退化造成的训练结果；该轮在模型加载阶段就已
失败，后续 `time_out`/`completed=0` 只能说明评估生命周期收尾，不能拿来诊断策略能力。
也不能通过上传一个新的 `base_env.py` 解决，因为入口兼容函数已经位于
`agent_ppo.conf.conf`，且平台会覆盖 `base_env.py`。

复核时必须同时区分三种来源：

1. 本地仓库文件（用于计算预期 SHA256）；
2. 容器启动前回读的文件和最终生效 TOML（用于确认同步/平台覆盖）；
3. aisrv 与 learner 的实际启动日志（用于确认真正执行的入口）。

只有第 2、3 项均匹配，才能认为评估入口修复生效。

只有这些静态/行为测试通过后，才继续本计划的 command scheduler 实现；这一步不要求
平台先运行长训，也不把平台模型 ID、路径或 SHA 不一致升级为启动阻断。

### 0.7 P0 放行表

在开始四小时任务前，用一轮不超过三分钟的评估 smoke 逐项登记：

| 层级 | 必须取得的证据 | 失败后的处理 |
|---|---|---|
| 最终配置 | 回读 TOML 含显式 `policy_entry` | 标记配置未生效，不解释模型表现 |
| 容器源码 | `conf.py`、`agent.py`、`checkpoint_io.py` SHA256 与本地一致 | 重新同步并回读；不只看上传响应 |
| aisrv | `Stage: visual_policy_optimization`、VisualPPO eval loader、正确 checkpoint | 标记入口/loader 回归 |
| learner 子进程 | 显式入口选择与 aisrv 一致 | 标记子进程配置漂移 |
| 模型身份 | 路径、文件名 ID、包内 ID、SHA256、模型维度均有日志 | ID/lineage 只 warning；结构错误修复后重测 |

这里的“放行”是人工流程判断，不是在训练代码里增加新的阻断门禁。只有非有限权重、

## 1. 目标与边界

本任务是 Anchor R2 之后的第二个、也是下半个四小时任务。唯一目标是让视觉学生在
新的 command 域上保持可控运动，同时不牺牲已经恢复的上楼、下楼和坡面能力。

本任务不再重新训练特权教师，不修改网络结构，不修改相机外参，不加入深度增强、
摩擦/质量/延迟随机化、外力推动或新的步态奖励。Anchor R2 结束时的学生网络、
CNN 冻结状态、奖励面和地形配置都是本任务的起点。

本任务结束后，只有同时通过 command 泛化和固定 seed 视频验收的 checkpoint 才能作为
后续学生 RL 或 Sim2Real 稳健性实验的父模型。若没有通过点，回滚到 Anchor R2 最佳点，
不把最后一个 checkpoint 自动当成发布模型。

## 2. 父模型选择与恢复

任务一结束先用与 `visionfull-28401` 完全相同的评估配置补齐四个固定 seed。按以下
顺序选择父模型：

1. 满足 Anchor R2 验收条件的候选；
2. 楼梯 hard termination 最低；
3. 上楼前进距离最高；
4. action anchor MSE 较低；
5. 仍有并列时选择较早的稳定 checkpoint。

记录父模型的实际路径、平台 ID、文件大小和 SHA256。ID、路径或血缘不一致只打印
醒目 warning，不以人工 ID 规则阻断平台启动；但训练报告必须保留这些 warning。

任务二使用 `transition_resume`，恢复：

- VisionEncoder 的 LSTM 和 output head；
- Actor、Critic、动作标准差；
- optimizer、累计 iteration、RNG；
- Anchor R2 的训练包 schema 和模型维度契约。

任务二不恢复：

- live LSTM hidden（启动时清零）；
- Anchor R2 的 session clock；
- command bucket 的保持计时、安全窗口和历史计数。

新会话固定从 `command_session_elapsed_hours=0` 开始。Action/latent anchor 在整个任务
保持 Anchor R2 终点值 `0.35/0.10`，不在 command 泛化任务中继续退火，以便把 command
变化与教师退火解耦。

恢复后的 live LSTM hidden、zero grace timer、上一时刻 applied action、上一时刻
action delta 和所有 per-environment command hold counter 都清零；不能把上一个任务的
episode 尾部状态带入新任务。计数器在环境 reset/auto-reset 后只对对应 env 重置，其他
并行环境的 command 计时不得被连带清零。

## 3. 环境与奖励冻结项

以下内容必须与 Anchor R2 完全一致：

```text
num_envs = 256
episode_length_s = 25
terrain curriculum = true
max_init_terrain_level = 9
standard_wall = true
terrain proportions = pyramid_slope 0.20 / pyramid_slope_inv 0.20 /
                     pyramid_stairs 0.20 / pyramid_stairs_inv 0.40 / maze 0.00
depth augmentation = false
domain randomization = false
friction randomization = false
observation noise = false
external pushes = false
```

这里固定的是已经核验过的**原始 terrain 名称与比例**，不以 `inv` 后缀推断上下楼方向。
每次运行必须在日志里同时打印 raw terrain 名称、运行时映射出的方向和固定 seed 视频；
验收表中的“上楼/下楼”以这一运行时映射为准。关闭课程或重新配地形会把 command 变化和
难度变化耦合，本任务不做这种改动。平台 `base_env.py` 可能在启动时被恢复，因此本任务
不修改、不上传、不依赖其 reset 生命周期、难度晋升或 episode 日志。

奖励只保留当前已验证的 command 兼容基线：

```text
track_lin_vel_xy = 3.0
track_ang_vel_z = 1.0
forward_velocity = 0
trot_gait 仅在 command 模长 > 0.1 时生效
joint_position_penalty.stand_still_scale = 2.0
```

本任务允许加入一项范围严格受限的 zero-command 稳定奖励，但不全局缩小
`track_lin_vel_xy.std=0.25` 或 `track_ang_vel_z.std=0.25`。tracking `std` 继续保持
`0.25`，避免正常楼梯速度误差被放大成过强惩罚。新增稳定项只在完整 command 范数
低于 `0.05` 且 zero command 已持续 `0.3--0.5s` 后生效：

```text
zero_stability_penalty =
    normalized(root_v_xy, 0.05)
  + 0.5 * normalized(root_v_z, 0.03)
  + 0.5 * normalized(root_omega_xy, 0.10)
  + 0.25 * normalized(root_omega_z, 0.10)
  + 0.10 * normalized(action_delta)
  + 0.05 * normalized(action_second_delta)
```

`normalized(x, scale)` 定义为先取每个标量分量的 `z=abs(x)/scale`，再使用
`phi(z)=z*z (z<=1)`、`phi(z)=2*z-1 (z>1)` 的有界增长 Huber 形式，向量项按分量
取均值。不能直接把不同量纲的原始平方和相加。

这里必须区分**奖励可计算**和**agent 端可观测**：`RewardProcess` 在环境进程内可以直接
读取 robot asset、action manager 和 command manager，所以可按上式计算该 reward；但在不
修改平台 `base_env.py` 且平台未公开逐步 trajectory telemetry 的条件下，训练 workflow
不能真实取得 `root_v_*`、`root_omega_*`、足端滑移或该 reward 项的逐步样本。它们不得由
未命名的 proprio 向量、episode reward 均值或猜测的字段伪造。当前轮只将该项以保守权重
`-0.05` 加入 reward；其物理量 P95 的可视化留待平台公开 telemetry 契约后再实现。
该项只抑制机身抖动、脚底滑动和高频 action chatter，不把关节拉回默认姿态；zero
command 刚切换后的 grace period 允许机器人先完成减速和重新支撑。当前可真实输出的只
有 clipped action 的 delta/second-delta；其余 stable 项 raw/P95 和 reward contribution
必须写为 `unavailable:no_agent_environment_telemetry`。本轮固定 `-0.05`，不根据不可见的
raw reward 分布调大权重，更不能借由 episode 总 reward 推断它没有压过速度跟踪或楼梯推进。

奖励状态的坐标和采样语义固定为：`root_v_xy/root_v_z/root_omega_*` 使用机身坐标系
的当前值；`action_delta` 使用实际送入环境前的 clipped action（`[-6,6]`），而不是
未裁剪的 PPO 正态采样值；episode reset 时上一时刻 action 置零。zero 稳定项的总
权重必须单独配置并记录，默认从 `-0.05` 的保守量级开始，以实际 raw reward 分布复核，
不能让执行端自行把权重提高到压过速度跟踪。

纯角速度 command 不属于 zero command，因为 zero mask 必须使用完整三维 command：

```python
zero_mask = torch.linalg.vector_norm(command[:, :3], dim=1) < 0.05
```

超时/截断仍按 PPO value bootstrap 处理，不把 timeout 当成摔倒；安全诊断只使用
`hard_termination`、非有限值和实际动作/命令统计。

## 4. Command 混合日程

任务二只允许一个 `visual_command_generalization_v1` scheduler。每个环境在当前
command 保持时间到期时独立抽取下一条 command，保持期间不改写，避免动作突变。

| 墙钟 | target profile | source profile | 目的 |
|---|---:|---:|---|
| 0--30 min | 0% | 100% | 续接父模型并确认恢复无漂移 |
| 30--120 min | 线性 0% → 50% | 100% → 50% | 慢速引入新域 |
| 120--180 min | 线性 50% → 100% | 50% → 0% | 完成切换 |
| 180--240 min | 100% | 0% | 在纯目标域稳定至少一小时 |

线性段的诊断点为 30/60/90/120/150/180 分钟，实际比例按**已到期并重新采样的
command 数量**统计，而不是按环境数量或 PPO iteration 猜测。

时间区间采用左闭右开语义：`[0,30)`、`[30,120)`、`[120,180)`、`[180,240]` 分钟。
在恰好 30、120、180 分钟时使用后一个区间的概率；平台时钟抖动时以 scheduler
记录的单调墙钟为准，不以 iteration 反推时间。

### 4.1 Source profile

Source 完全复制 `visionfull-28401` 原始域：

```text
vx = U(0.3, 1.3)
vy = U(-0.2, 0.2)
wz = U(-0.3, 0.3)
hold = U(6, 10) seconds
```

### 4.2 Target profile

目标类别权重调整为 `15/20/30/15/10/10`，加入独立的纯角速度类别。类别内采样如下：

| 类别 | 权重 | command | hold |
|---|---:|---|---:|
| zero | 15% | `vx=0, vy=0, wz=0` | `U(1.5,3.0)s` |
| low forward | 20% | `vx=U(0.10,0.30), vy=0, wz=0` | `U(3.0,6.0)s` |
| normal forward | 30% | `vx=U(0.30,0.80), vy=0, wz=0` | `U(3.0,6.0)s` |
| forward + yaw | 15% | `vx=U(0.15,0.55), vy=0, wz=±U(0.15,0.30)` | `U(3.0,6.0)s` |
| pure yaw | 10% | `vx=0, vy=0, wz=±U(0.15,0.30)` | `U(3.0,6.0)s` |
| lateral | 10% | `vx=0, vy=±U(0.10,0.20), wz=0` | `U(3.0,6.0)s` |

全局合法范围为两套 profile 的并集：

```text
vx = [0.0, 1.3]
vy = [-0.2, 0.2]
wz = [-0.3, 0.3]
```

PPO 对 source 和 target 的所有样本都训练。只有 S0 anchor loss 使用样本权重：

```text
source 或 target 且 vx >= 0.30：1.0
target low forward：0.25
target forward + yaw：`vx < 0.30` 时 0.25，`vx >= 0.30` 时 1.0
target zero / pure yaw / pure lateral：0.0
```

source 样本无论其 `vx` 取值都使用 1.0；target 的权重按 bucket 和实际采样值决定，
不能只用一个 `vx >= 0.30` 条件漏掉 forward+yaw 的低速边界。这样不会让没有停车/纯
横移/纯转向经验的 S0 监督压制新能力，也不会从 PPO rollout 中删除这些样本。纯 yaw
仍由 PPO 正常训练，但不使用没有对应教师经验的 S0 anchor。

## 5. 不依赖平台 base_env 的实现方式

`visual_command_generalization_v1` 的 agent-side 实现已经在当前分支中形成 release
candidate，但仍必须完成第 0 节的最终配置、同步回读和平台 smoke，不能把本地存在代码
误写成“平台已生效”。其实现只允许由以下 agent-side 模块承担，而不是修改
`server/isaac_env/base_env.py`：

1. `agent_ppo/feature/command_schedule.py`：纯 torch 的 source/target profile
   采样、每环境 hold 计时、线性 target probability 和 bucket 统计；
2. `agent_ppo/feature/command_adapter.py`：唯一的环境 command 注入适配层；
3. `agent_ppo/algorithm/algorithm_visual_ppo.py`：读取 scheduler 的 source/target
   mask，计算加权 anchor loss，并保存/恢复 session 状态；zero-stability reward
   的 mask、grace period 和 raw/P95 统计也在此处或 reward process 中保持一致；
4. `agent_ppo/workflow/visual_ppo_workflow.py`：在每个 rollout step 之前调用适配层，
   在 rollout 结束后打印实际统计并把它们写入 monitor/checkpoint；
5. 活动 TOML：只声明 scheduler 参数和合法范围，不能把 `[300,300]` 之类的非法
   fallback 当成“关闭原生采样”。

纯 yaw 接入时，`feet_air_time` 的 moving gate 必须使用完整 `command[:, :3]` 范数，
不能继续只检查 `command[:, :2]`，否则纯角速度样本会被误判为静止。当前
`trot_gait` 的前后足接触配对不在本任务内重写；它需要在下一独立步态纠正阶段先核对
运行时足端 `body_ids` 后再修正为对角支撑逻辑。

适配层只允许调用平台明确提供的 command setter（例如 wrapper 的
`set_train_commands(commands, env_ids)`）。调用顺序固定为：先让原生环境完成 reset 或
原生 command 到期标记，再由 adapter 对本次到期的 env_ids 写入 source/target command，
最后才执行 policy observation 和 `env.step`。不得把 `base_env.py` 的私有
`command_manager._command` 作为唯一实现前提。启动时打印：

```text
command_hook = <method/path or unavailable>
command_hook_status = active|warning_unavailable
```

如果平台没有公开 setter，适配层只能保留原生 source command，并打印
`warning: target command profile is not applied`；不得伪造 target 比例，也不得静默把
观测里的 command 改掉而让环境奖励仍使用另一条 command。该 warning 不自动退出任务，
由操作者根据日志决定是否停止或先取得平台 hook。此时
`effective_target_probability` 必须记录为 `0.0`，target bucket 计数为零；不得把
requested probability 当成实际比例，也不得把这次运行标记为 command 泛化通过。

### 5.1 Command 接入可行性 smoke（P1，长训前完成）

正式四小时任务前先用 2--3 分钟短运行证明公开 hook 确实存在并作用于环境真实 command：

1. 输出实际绑定对象、方法名和签名；setter 返回 `False`、抛异常或 getter 回读不一致时，
   本次写入记为失败，不能只把“函数调用没有异常”视为成功。
2. 若平台提供公开 command getter，写入后按 `env_ids` 回读并与 requested command 比较；
   输出写入/回读最大绝对误差。没有 getter 时明确打印 `verification=unavailable`，并通过
   环境公开 telemetry 或奖励 command 统计做旁证，不能声称强验证通过。
3. 在同一批 256 环境中同时制造 source、target、未到期和 reset 四类子集，确认只改目标
   `env_ids`，其他环境 command 与 hold timer 不变。
4. setter 不可用或失败时，不 patch actor/critic observation 的 command 字段；否则会产生
   policy command 与 reward command 不一致。该路径必须保持原生 source command，
   `effective_target_probability=0` 并持续打印 warning。
5. 原生 command sampler 的合法 fallback 固定为 source 语义的 `U(6,10)s`，不能用超出
   平台校验范围的超长 resampling 时间。adapter 必须在原生 reset/resample 之后、policy
   observation 生成/修补之前执行，并在 `env.step` 前完成。

公开 hook 尚未验证时可以启动诊断 smoke，但不应消耗正式四小时预算。这个决定属于运行
流程控制，不在算法里新增硬门禁。

### 5.1.1 P1 诊断状态恢复与 zero telemetry 来源

两项诊断语义必须在正式训练前落实，否则日志会制造错误结论：

1. `CommandAdapter` 的公开 setter 一次返回 `False`、抛异常或 getter 回读不一致后，状态可
   暂时为 `warning_unavailable`；后续一次 setter 成功且（如存在）getter 回读验证通过时，
   必须恢复为 `active/verified`。checkpoint 和 monitor 应记录**本次写入**的状态以及累计
   失败计数，不能把一次瞬时故障永久伪装成“target 未生效”。测试必须覆盖
   `failure -> verified success -> active`，并确认 effective target 只从真正成功的 commit
   计数。
2. 第 7 节要求的 zero-command `root_v_xy`、角速度、action delta、二阶差分、足端滑移和
   `zero_stability_penalty` 的 raw/P95，必须先确定可用的数据通路。不得依赖会被平台覆盖的
   `base_env.py`，也不得把 episode reward 平均值误报为 P95。实现应优先在 agent/workflow
   使用已存在的 rollout observation、实际送入环境的 clipped action 与公开 reward/trajectory
   telemetry 做有界分位数累积；每个字段都要在实现注释和启动日志标明来源、坐标系、采样
   时点和不可用时的 `unavailable` 原因。若平台没有可读取的某项原始量，该项只能明确打印
   `unavailable`，不能伪造 P95 或以此作为验收通过证据。

这两项都是诊断真实性修复，不改变 command 采样、奖励数值或训练是否继续的 warning-only
原则。

### 5.2 Scheduler 边界与确定性测试

实现和测试必须覆盖：

- source、target、target 写入失败均按对应 `env_ids.numel()` 生成 hold，不能把
  `num_envs` 长度张量赋给子集；测试同时覆盖 0、1、部分和全部环境到期；
- 时间段采用第 4 节的左闭右开语义，并直接测试 30/120/180 分钟边界；
- bucket 权重、正负号、min/max、zero grace 和 anchor sample weight 与第 4.2 节逐项一致；
- reset 只重置对应环境的 command/hold/zero-grace/action history，不清空其他环境；
- `plan -> setter -> commit` 是一个完整状态转换。checkpoint 只允许在 commit 后的 outer
  iteration 边界落盘；若实现允许中间保存，则必须连同 pending env IDs、command、bucket、
  requested mask 和 RNG 一并序列化，不能恢复后丢失 pending target；
- 同一 `visual_command_generalization_v1` 续训恢复 session clock、每环境 hold、bucket、
  RNG 和累计统计；从 Anchor R2 迁移则将这些 command 状态清零，并保留模型/optimizer
  的 transition resume；
- setter unavailable、setter 返回 `False`、setter 抛异常、getter 回读不一致四条失败路径
  都只 warning、都不伪造 observation、都不增加 effective target 计数；
- setter 失败之后的下一次 verified success 必须恢复 `command_hook_status=active`，同时保留
  累计失败次数和最后失败原因，避免 checkpoint/monitor 永久报告过时的
  `warning_unavailable`；
- actor observation 与 critic observation 中的 command 字段必须一致，shape/dtype/device
  与原观测保持一致。

## 6. 学习、保存与恢复

可训练模块固定为 CNN 冻结、Actor/LSTM/Critic 训练；学习率沿用 Anchor R2 终点配置：

```text
Actor = 1e-5
LSTM = 5e-6
Critic = 1e-4
max_grad_norm = 1.0
action_anchor = 0.35
latent_anchor = 0.10
```

平台任务页控制四小时墙钟；`task_end_hours = 4.0` 只是写入训练包的任务元数据和日志中的
预期时长，**不得**被 workflow 改造成第二个进程内截止条件。`max_iterations` 只保留高安全
上限，不作为正常训练时长控制器。任务创建页必须明确配置四小时，workflow 每分钟打印
`session_elapsed_hours`；若先触及 `max_iterations`，仅最终保存并打印“iteration cap reached,
not a four-hour completion”，不得把它记为完成四小时。平台终止进程时仍应沿用现有退出路径
进行最后一次保存。每约十分钟按墙钟保存，额外在 30/120/180/230 分钟保存。标签仅使用
小写英文字母：

```text
model.ckpt-commandbase-<平台ID>.pkl
model.ckpt-commandblend-<平台ID>.pkl
model.ckpt-commandfull-<平台ID>.pkl
```

平台 lifecycle 和 iteration 语义沿用已验证的视觉长训修复：

```text
continuous_training = true
iteration_semantics = "completed_outer_iterations_v1"
每个完整 outer iteration 只调用一次平台 lifecycle callback
current_iteration = 已经完整完成的 outer iteration 数
total_steps = 累计环境样本数，不是平台模型 ID
```

不得在 recurrent rollout 的每个 inner step 推进平台 iteration，否则会重现“数分钟跳过
上千 ID”和定时保存列表不一致的问题。`frame_no >= 1250` 的单 episode timeout 由逐环境
auto-reset 和 PPO bootstrap 处理；`continuous_training=true` 防止全局 frame counter 被误当成
整项训练完成。若日志仍出现 `reached max length`，必须同时核对 outer iteration、逐环境
reset、optimizer update 和 checkpoint 进度，不能只凭这一行判定失败。

平台 ID 只使用框架传入值。训练包仍为 `kaiwu_train_v1`，新增并恢复：

```text
schedule_mode = "visual_command_generalization_v1"
transition_parent_platform_model_id
transition_parent_sha256
command_session_elapsed_hours
command_target_probability
requested_source_probability
effective_source_probability
effective_target_probability
source_target_counts
target_bucket_counts
command_out_of_range_count
command_hook_status
command_hook_verification
command_profile_mix_history
action_anchor_weight = 0.35
latent_anchor_weight = 0.10
```

恢复时优先显式的 `commandfull`/`commandblend` 候选，不能使用 `latest` 猜测父模型。
恢复后的首次保存延迟约 2 分钟，之后回到十分钟 cadence；保存失败、权重出现
NaN/Inf 或 bundle 校验失败才允许必要停止，其余质量异常只 warning 并继续记录。
首次与任一阶段 checkpoint 必须做真实 PyTorch save-load round-trip：加载刚写入的文件，
核对学生动作一致、scheduler hold/bucket/session clock 恢复、RNG/optimizer 可读、文件名 ID
等于框架传入 ID。写盘日志或平台模型列表任一方单独存在，都不足以证明保存有效。

训练包还必须保存 `command_hook_status`、`command_hook_verification`、requested/effective
统计的计数口径（按 command 重采样事件，不冒充 env-step 占比）和有界的
`command_profile_mix_history`。history 的每条记录至少包含单调 session time、requested/
effective source/target count、bucket count、hook status 和 verification；保留最近固定数量
的快照，避免 checkpoint 随墙钟无限增长。adapter 的 Python 绑定对象本身不序列化；恢复后
重新探测公开 hook，并把新状态与 checkpoint 中的历史状态同时打印。

## 7. 必须打印的运行证据

启动后三分钟内应看到：

```text
schedule=visual_command_generalization_v1
transition parent path/id/sha256
command_session_elapsed_hours=0
anchor action=0.350 latent=0.100
command_hook_status=active|warning_unavailable
source_probability=1.000 target_probability=0.000
```

每 500 个 outer iteration 或每分钟至少打印一次聚合信息：

- source/target 请求比例与实际比例；
- 六个 target bucket 的 count、比例、min/max/mean 和越界率；
- 每个 terrain × difficulty 的样本数；
- 运行时确认的上楼 terrain（同时打印 raw terrain 名称）的完成进度、低进度 timeout、
  hard termination；
- zero command grace period 后的 clipped `action_delta`、二阶差分的均值/P95；其来源必须
  标为 `workflow_clipped_action_after_command_adapter`。当前平台未公开逐步 trajectory
  telemetry 时，`root_v_xy`、`root_omega_xy`、足端滑移和 `zero_stability_penalty` 一律打印
  `unavailable:no_agent_environment_telemetry`，不以 episode 平均 reward、未命名 observation
  或推测值替代；
- action anchor MSE、policy KL、动作 P95/P99、`|action|>6` 比例；
- timeout/truncation 与 hard termination 分开计数；
- 当前 checkpoint 路径、平台 ID 和 SHA256。

每次平台启动还必须打印并保留：`continuous_training`、iteration 语义、outer/inner step
定义、实际 `num_envs=256`、相机外参、depth augmentation 状态、课程开关、地形比例、
command hook 来源以及最终生效配置文件路径。评估日志与训练日志使用同一套 checkpoint/
depth/command/action 身份字段，避免再次把不同入口的结果放在同一张表中比较。

`reached max length` 只作为平台 lifecycle 诊断；只要 outer iteration 继续增长且
timeout 被 bootstrap，它不能单独判定训练失败。

## 8. 四小时验收与回滚

评估候选为 60、120、180、210 和 230 分钟附近的 checkpoint，并保留父模型同配置的
四个固定 seed 基线。通过条件：

```text
总体得分 >= 28401 基线的 95%
运行时确认的上楼总分相对 Anchor R2 父模型下降 <= 3 分
运行时确认的上楼前进距离相对父模型下降 <= 3 分且 >= 90
运行时确认的下楼与坡面总分相对父模型下降 <= 3 分
hard termination 增加 <= 1 个百分点
source profile 下的性能相对父模型下降 <= 2 分
16 环境、20 秒 zero command：平均平面速度 < 0.08 m/s，且无摔倒
zero command 的机身抖动只用固定 seed 视频和平台可公开的评估运动统计复核；当前
agent-side P95 不可用时不得用伪造数值判定通过。zero stability reward 的权重保持 -0.05，
且不得从 episode reward 平均值推断它是否主导总 reward
```

另要求在 target probability=1.0 的最后一小时内，实际 target 比例与请求比例相差
不超过 5 个百分点；若 `command_hook_status=warning_unavailable`，该项标记为未验证，
不得宣称完成 command 泛化。

若多个候选通过，按上楼前进距离、hard termination、zero-command 静止质量、再按
anchor MSE 选择最佳点。若没有候选同时通过，正式回滚点为 Anchor R2 最佳 checkpoint，
不进入步态奖励、深度噪声、动力学随机化或 Jetson 部署。

## 9. 稳定可实操的最终状态

本计划完成并通过验收后，仓库中应固定以下三类证据：

1. Anchor R2 父模型评估报告、SHA256 和四个固定 seed 视频；
2. `standard-command-r1` 的 source/target 实际统计、checkpoint 清单和评估结果；
3. 一个明确的发布候选或明确的回滚到 Anchor R2 的决定。

在这三类证据齐全前，不进行下一轮奖励重写或 Sim2Real 随机化。这样“稳定可实操”
指的是：能从一个已评估 checkpoint 可重复启动、能读出实际 command 是否生效、能保存并
恢复同一 session、能用固定 seed 选择模型，而不是仅凭任务运行到四小时就宣布收敛。

## 10. 八小时扩展边界

若平台允许八小时，本任务的前四小时日程不变；第 240 分钟以后继续使用 100% target
profile、相同奖励、相同 `action_anchor=0.35`/`latent_anchor=0.10`，只延长稳定观察和
checkpoint 选择。额外四小时不得加入新的地形比例、tracking `std`、步态奖励或随机化。
八小时版本新增评估点为 300、360、420 和 470 分钟，仍按上楼/下楼/source/zero 四类
指标选择最佳点；保存 cadence 仍为约 10 分钟，并在这些评估点额外保存；若 command hook
无效，延长时间不弥补“target 未实际进入环境”的缺陷。
