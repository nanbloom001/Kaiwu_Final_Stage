## 0. 架构结论（一句话）

**采用"两个网络、一个组合 checkpoint、一个平台模型 ID、两个 ONNX"的分层架构：低层（VisionEncoder + Actor77）在导航阶段逐位冻结；新增一个 5Hz 轻量高层导航网络（分接冻结 CNN 特征 + UWB goal4 输入，输出限定在低层已训练指令流形内的离散词表 cmd3）；训练包以 `kaiwu_train_v1` 已预留的 `modules.high_level` 扩展承载（`server/agent_ppo/checkpoint_io.py:8-10`）；部署为逐位不变的 loco.onnx 加独立线程运行的新 nav.onnx。**

即"单一组合 checkpoint、两个运行时模型"，附两处独立修正：部署侧用双 ONNX 而非单图混频；高层输出用离散词表而非连续 cmd 头。

## 1. 解耦训练与平台单包约束的调和（针对用户补充）

平台约束：一次训练任务 = 一个模型 ID = 一个 checkpoint 文件，eval 严格同 ID、身份不符硬停止（`checkpoint_io.py:450-501`）。跨文件双 ID 加载不可行。

**调和方式：解耦发生在训练语义层，不在文件层。**

- 每个训练任务只把**一层**的参数放进 optimizer；bundle 始终携带该阶段 eval 所需的完整模块。
- 低层训练阶段：正常低层 bundle，**不含** `modules.high_level` 也完全合法——`validate_low_level_spec`（`checkpoint_io.py:504-519`）只查 format/schema 与 model_spec 整数键，从不检查 modules。
- 高层训练阶段：新任务以 `preload_model_id=<选中的低层 ID>` 首载（跨 ID 父加载有两次平台先例：preload_model_id 10288→28401 逐阶段翻转，`server/conf/configure_app.toml:5-7`），首载分支在内存中复制低层 + 随机初始化高层，首次 save 落盘第一个 nav bundle。此后低层模块逐位不变地随包携带，save 前用 state_dict 级摘要校验（见 §5）。
- **解耦的本质是接口稳定**：只要低层继续满足"接口契约 v1"（§2），低层换代后高层最多短训即可迁移；高层回滚 = 同 ID 内换文件，低层回滚 = 换用旧低层候选重新引导 nav 任务。

**主路线图（按用户确定的顺序）：**

| 阶段 | 内容 | 产物 |
|---|---|---|
| **Phase A 结构与契约冻结**（现在） | 冻结两层网络结构 + 接口契约 v1；cnn_feat 线性探针**随平台任务在线做**（经核查 server/ 无任何观测导出通路——全部 torch.save 均为 checkpoint，模型池只流转参数文件，探针不能离线跑；应在任务内算好统计，经监控指标或 ckpt 内嵌导出，后者有 `sparse_episode_metrics_with_trajectory` 历史先例，`server/agent_ppo/tests/analyze_trajectory.py`），在结构冻结前关闭"共享分接 vs 独立编码器"这个唯一的结构分叉 | 本文档 + 契约条目草案 |
| **Phase B 低层强化训练**（用户下一步） | 独立任务链（新 ID 递增），继续 RL 训练低层：楼梯硬化 + **指令域按词表需求扩展（重点 wz 扩到 ±0.5~0.8，仍在 deploy cmd_ranges [-1.5,1.5] 内）**；每个候选跑 N0 阶梯指令门 | 低层候选 bundle（无 high_level） |
| **Phase C 高层导航训练** | 冻结通过验收的低层候选，nav 任务首载构造 high_level，只训高层（§6 N0-N3） | nav bundle（完整两层） |
| **Phase D 部署** | 影子模式实测 → 接管原子 PR（§7） | loco.onnx（不变）+ nav.onnx |

Phase B 先行的直接好处：当前 command-34728 的 wz 训练域上限只有 **0.3 rad/s**（`server/agent_ppo/feature/command_schedule.py:86-90,218-244`），90° 原地转需 ~5.2s，0.6m 迷宫通道内无法自旋（Go2 扫掠对角 ~0.77m）。低层先扩 wz 域，高层词表就能从一开始就含更快转向档，迷宫时间分（决赛计分 0.4 权重）不再受此天花板压制。

## 2. 接口契约 v1（Phase A 要冻结的内容）

结构冻结 = 冻结以下各项；低层此后无论怎么练都必须保持：

1. **低层结构**：depth[180,320,1]→CNN→32 ⊕ proprio45 → LSTM 2×64 → Linear→32 → L2Norm → latent32；Actor77 MLP(512,256,128) → action12；obs 布局 proprio45（[6:9]=vx,vy,wz 指令位）；`model_spec.goal_dim` **恒为 0**（写 3 会让现有全部加载器硬拒绝，`agent.py:904,1353`）。
2. **高层结构**：输入 ≈48 维 = cnn_feat32（冻结 CNN 分接，训练侧 detach）⊕ goal4 ⊕ exec_cmd3（slew 后真正执行、写入 proprio[6:9] 的当帧值——训练/部署逐位同源）⊕ held_cmd3（当前词表目标，slew 过渡期与 exec 消歧）⊕ ang_vel3 ⊕ proj_grav3；nav LSTM 2 层 hidden 64（与 ONNX 预留端口 nav_h/nav_c[2,1,64] 逐位同形，`deploy/sim2real_test_loco/ARTIFACTS.md:36-37`）；Linear → categorical → 词表查表 → cmd3。**输入白名单原则：Actor 每一维输入必须真机实时可测且训练侧同链路计算；特权量（height_scan、真值位置/线速度、地形标签、接触力）只准进 critic/奖励；训练侧恒为常数、部署侧会变化的输入维（如深度帧年龄）不准进 v1。**
3. **goal4 编码**：`[clamp(local_x/10), clamp(local_y/10), clamp(dist,0,20)/20, freshness]` 体坐标。前三维训练/部署逐位一致（`server/agent_ppo/feature/goal_features.py` encode_track_goal 与 `deploy/.../UwbGoal.h` actor_goal_from_uwb，真机验证过）；第 4 维 freshness 消除"到达目标"与"UWB 失效"的全零歧义（无效 UWB 现返回 {0,0,0,0}，与到达不可分）——deploy 侧 goal 张量本就是 4 宽、第 4 维现为 0.0f 占位，且 `uwb_freshness_scale`（age→1..0）现成，填入即可；训练侧 N0-N2 恒 1，N3 随 UWB 丢帧模拟随机化。
4. **频率**：低层 50Hz；高层 5Hz（K=10 低层步；对齐 UWB 实测 ~5Hz——10Hz 下约半数 tick 看到重复 goal）。训练与部署同值。
5. **cmd 交接语义**：词表目标值 → 训练域白名单 clamp + 有限性检查 → 逐 50Hz 帧 slew（nav 专用常数，非对称建议：加速 0.3-0.5/s、减速 ≥1.0/s；episode 起始清零对齐 `State_VisionLoco.cpp:614`）→ `set_cmd_override(true, exec)` → proprio[6:9] **当帧写入**（`loco_runner.h:112-115`）。训练侧在 aisrv 覆写 obs[6:9] 前施加同一套 clamp+slew。此通路无一帧延迟；真实延迟 = nav 推理耗时 + ≤1 个 50Hz 帧对齐 + slew 整形。
6. **词表**（锚点必须落在当时低层的训练指令支撑内）：
   - 对 command-34728（对照 `command_schedule.py:218-244` 逐点核实）：zero；前进 vx∈{0.20, 0.45, 0.70}；前进+转向 (0.35,0,±0.25)、(0.20,0,±0.25)；纯转向 (0,0,±0.25)。**v1 共 10 项；横移 (0,±0.15,0) 两项暂缓**——训练采样权重低（lateral 桶仅 0.10）、步态质量未验证，N0 单独验收通过后再放行。vx 上锚取 0.70 而非 0.8（0.8 是 normal_forward 桶开区间 [0.30,0.80) 从未采到的边界值）。
   - Phase B 扩域后可加：纯转向/前进+转向 ±0.5 档等（以扩域后的实际采样域为准）。
7. **ONNX 端口**：loco.onnx 8入8出契约原样（`ARTIFACTS.md:33-40`）；nav.onnx：输入 depth[1,180,320,1] / goal[1,4]（第 4 维 freshness，全 4 维入网）/ proprio[1,45]（图内取 ang_vel3+proj_grav3+exec_cmd3=proprio[0:9] 子集）/ held_cmd[1,3] / nav_h、nav_c[2,1,64]，输出 cmd[1,3] / nav_h_out / nav_c_out。opset17、batch=1。

**防 OOD 与防抖四层防线**：① 词表锚点逐点在训练支撑内（诚实声明：slew 过渡轨迹会短暂穿越 vx∈(0,0.10)、vx=0 时 wz∈(0,0.15) 等窄的未训练间隙，两侧被训练区包夹，N0 实测把关，不宣称绝对构造性保证）；② 最小驻留 2-5 tick + 切换惩罚（低层训练 hold 统计最短 1.5s，`command_schedule.py:83-84,138-139`，5Hz 裸切换本身出分布——抑制抖动的承重结构是驻留长度而非 slew）；③ 接口 slew 训练部署逐帧镜像（注意：低层训练只见过阶跃指令，server/ 全目录 grep slew 零命中、`worker_command_bridge.py:144-145` 是瞬时 copy_，所以 slew 匹配服务的是高层自身的训练-部署自洽，常数可为 nav 重调）；④ C++ 现有 max_* clamp 兜底。急停保留 uwb 式硬置旁路（阶跃到 zero 是低层最常见训练形态，安全）。

## 3. 为什么否决另外两个选项

**(1) 端到端单网（Actor80/goal3 直出关节）**：导航梯度直接压在脆弱的楼梯步态上（后腿外展、支撑不对称、偶发失稳），历史唯一保命手段 lr=1e-7+std 夹紧属被禁参数；Actor77→80 合同翻转单向不可逆（`shared/interfaces/server-deploy-contract.md:7-16`）；导航错误的表现形式就是摔倒，无法分层归因——旧 Track 四宗罪（耦合、过拟合、高层错误直接变关节动作、无法单独验证）记录在案。

**(2) 双独立 checkpoint/双模型 ID**：与平台"一任务一 ID 一文件 + eval 同 ID 硬停止"正面冲突（`checkpoint_io.py:450-501`），定义级不可行。其合理内核（训练隔离、双图部署、责任切分）全部被采纳方案吸收。

采纳方案是仓库自己预留的方向：checkpoint docstring 预留 `modules.high_level`（`checkpoint_io.py:8-10`）、ONNX 预留 nav 状态端口、LocoRunner 已回喂 nav 缓冲（`loco_runner.h:163-167`）、`command_source=nav` 空壳分支已存在（`State_VisionLoco.cpp:486-490`）、官方部署指南目录树本就含 `export_vision_nav_onnx.py` 与独立 nav 权重。

- **不生成任何同 ID "locomotion" 别名文件**（该做法已在 command 阶段退役，避免身份混淆）。
- 标签联动约 14 处，最易漏三处：`visual_latest_model_id`（`checkpoint_io.py:294-312`，漏加则 latest 静默评旧 ID）、workflow `_PHASE_CODES`（`visual_ppo_workflow.py:29-41`）、`Config.CURRENT` 翻转与 TOML 命名（`conf.py:280,317`）。

## 7. 部署阶段设计（Phase D）

**第一步：影子模式（先行，~350 行，最便宜且直接回答最大部署未知数）。** `command_source=uwb` 正常跑，NavRunner 同时推理只写 CSV 不接管。需修两个数据竞争：robot 数据快照发布（`robot_->update()` 无锁写）、`last_exec_cmd_` 原子化。用现有 analyzer 阈值（p95 20ms STOP / 15ms WARN、45/48Hz，`analyze_sim2real_logs.py:305-321`）实测双 session 竞争——**仓库零 Jetson 实测数据；nav.onnx 内嵌 CNN 副本使 CNN 总算力翻倍；5-10Hz nav 造成 10-20% 帧重叠会直接进 p95**。影子实测通过是接管的前置门槛。缓解预案：nav IntraOp=1、CPU 亲和隔离、策略线程 SCHED_FIFO；仍超标则 nav CNN 降半分辨率或 tick 降 2.5Hz。

**第二步：接管原子 PR（按 CONTRIBUTING §6 同改三处）：**

- `deploy/`：NavRunner（~200 行，仿 `loco_runner.h`；独立 Ort::Env/Session 无结构障碍，DepthSource::get() 线程安全可并发，`DepthSource.h:91,162-166`）；`command_for_frame()` nav 分支从恒零换为读 nav 原子输出 + **新增训练域 clamp + 有限性检查**（现 nav 分支无任何钳制）；改走 override=true、隔离校验 `:689-692` 逐字保留、**删除 `:693-698` 回显拷回特例**（直接沿用会静默掩盖端口失配）；nav 看门狗 + 运行时降级到 uwb 巡航（`command_source_` 现为构造定死，运行时切换是新代码；nav 模式强制创建 uwb 订阅/utrack）；CSV 加 nav 列；config/脚本三处模式白名单放行。
- `server/`：nav.onnx 导出脚本（从单一 bundle 读 high_level + 冻结 CNN 副本；loco 导出路径零改动）+ 混频 parity 测试（Python 参考实现 vs C++ 行为逐帧比对——现有 8 帧 tol=1e-4 verify 检不出频率纪律错误）。

## 8. 主要风险与替代方案

1. **冻结 CNN 表征不足（最大赌注）**：32 维瓶颈为落足蒸馏训练，远场走廊结构可能已丢弃——低层 CNN 的蒸馏教师视野即机身周围 ~1.5m 近场网格（16×16 @ 0.1m；deploy 副本 `velocity_env_cfg.py:96-101` GridPatternCfg resolution=0.1/size=[1.6,1.0]）。对冲：迷宫通道 0.6-1.0m 机器人几乎始终贴墙，墙面恰在教师蒸馏视野内，近场感知+goal 方向+LSTM 记忆可能已够；Phase A 在线探针提前判定；预注册回退 = nav-LBC 蒸馏独立编码器（远场教师 + 复用 LBC 管线，见 §6 N0），部署结构不变。回退路径需在 S0 冒烟中多验一项：`[sensors]` 段能否过平台 TOML 校验器。
2. **Jetson p95 尾部（条件可行）**：影子模式实测作硬门（§7）。双 session 最终不可行时，备选才是单图混频（nav 分支进 loco 图 + C++ latch）——省一次 CNN 但把频率纪律埋进 latch，错误形态是 nav LSTM 静默以 50Hz 演化且现有 verify 检不出，故列备选。
3. **半 MDP PPO 实现债**：见 §6 尾段。
4. **wz≤0.3 战术上限**（对 command-34728）：Phase B 扩域是正解；扩域落地前接受路口停转的时间代价。**绝不允许高层越界**——冻结策略在 wz>0.3 的步态未经验证，越界即放弃全部安全论证。
5. **平台侧不可查证项**（`server/tools/` 不在仓库）：nav TOML 能否过平台校验、goal_reached 阈值可否 TOML 覆盖、weight=0 项是否仍执行。全部排进 S0 smoke，是排期先决条件。
6. **eval 静默错评**：见 §5 末条；Camera 任务评 nav ID 会静默 loco-only 评估，处置策略是用户决策点。

## 9. 对仓库现有方案的架构级纠错

1. **hier_nav TOML 的 wz±1.5 限幅假设与实际训练域冲突**：command-34728 全部数据 wz≤0.3（`command_schedule.py:86-90,218-244`）。按该 TOML 设计的高层会发出 5 倍越界转向指令。
2. **hier_nav 的 nav_decimation 训练 1（50Hz）/部署 10（5Hz）不一致**是设计级错误：高层决策频率训练与部署必须同值。
3. **ONNX 预留端口暗示的单图混频路线不宜采纳**：混频纪律只能活在 C++ latch，静默失效不可检；双 ONNX 让 loco 图逐位不动、频率纪律天然正确。占位端口继续闲置，无害。
4. **"两个视觉编码器会增加算力"不应作为决定性选型约束**（2026-07-21 分析 :322-323）：绝对算力可承受（CNN ~37M MACs），真正约束是 p95 尾部竞争——可实测、可缓解。
5. **phase_command_adapter 不能作为部署高层**：判定依赖 16×16 height_scan 特权观测，真机只有深度+本体+UWB；且 vy=wz=0 走不出迷宫。只配当训练基线。
6. 文档-代码不一致两处：`ARTIFACTS.md:38` "上一帧 cmd" 在 override=true 通路下实为当帧 exec_cmd（`loco_runner.h:111-116`）；loco 树 config `fixed_cmd=[0.7,0,0]` 被代码 clamp 到 0.30（`State_VisionLoco.cpp:409`），文档宣称的 0.7 楼梯测试实际跑不出。

## 10. 需要用户决策的参数（未确认事项，非既定结论）

1. 词表内容：vx 上锚 0.70/0.75；横移档去留；转向档密度；Phase B 扩域后的加档方案。
2. nav tick 与驻留：5Hz 确认；驻留策略——低层训练 hold 分布为 target 3-6s / zero 1.5-3s（`command_schedule.py:184-198`），0.4-1.0s 的最小驻留在其左尾之外，故 N0 跑驻留阶梯（如 0.6/1.2/2s）选能过步态门的最短值，N1 起步用保守 2s；切换惩罚权重；急停 zero 例外立即覆盖。
3. nav slew 常数（非对称建议值需确认，并写进契约作为接口常数）。
4. N0 两条门的阈值：步态回退容忍度；探针标签集与达标精度（共享 CNN 赌注的判定标准，属风险偏好）。
5. 奖励权重配比；姿态/能耗整形引入时机。
6. nav critic 是否用特权 height_scan（训练合法，推荐用）。
7. Phase B 低层补训的具体范围（wz 扩到多少、是否同时做楼梯硬化、任务条数）。
8. 阶段标签与 schedule_mode 命名（示例 navwarm/navmaze/navfull、hier_nav_vocab_v1），一次定死。
9. Camera 任务评 nav ID 的策略：允许静默 loco-only 还是显式拒绝。
10. 看门狗参数：nav 超时阈值、降级形态；影子模式接管验收标准（时长、p95 余量）。
11. N3 连续残差头：建议不加（保住构造性安全卖点），列为默认否决项供复议。

## 11. 总评

**实现复杂度：高，但分布可控。** 最大一块是半 MDP recurrent PPO（predict/update/storage 三处重写 + 变长终止步），为血缘中从未存在过的训练代码；部署侧约 500-700 行新 C++（loco 链路零改动）；checkpoint/eval 约 14 处标签联动机械但易漏；S0 平台 smoke 是排期先决条件。

**训练风险：中。** 低层步态风险被冻结结构性归零（相对单网方案的本质改善）；剩余集中在 CNN 表征赌注（探针提前判定 + 预注册回退）与半 MDP PPO 收敛调试（无历史超参可抄，但 5Hz × 12 词表的搜索空间比任何历史方案小几个数量级）。

**部署风险：中偏高，但全部可在影子模式中以零接管风险实测。** 双 session p95 竞争是唯一无法从仓库证据预判的硬指标；降级链（nav→巡航→停车保转向）给了真机故障一条不摔倒的退路——这是端到端单网结构上不可能提供的。
