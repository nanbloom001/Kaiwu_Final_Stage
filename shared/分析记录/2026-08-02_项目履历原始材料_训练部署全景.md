## 1. 已验证成果与项目定位

**项目目标：为 Unitree Go2 建立一条视觉 Sim2Real 控制路线，将稳定的 50 Hz 低层步态控制、5 Hz 连续速度导航和显式 command-response 辨识分开演化，同时保持训练平台单 checkpoint、真机传感器与部署时序的可追溯合同。**

**已获证据的闭环。** 已完成特权教师到视觉学生的低层运动控制蒸馏平台闭环；在 Jetson + D435i + ONNX + Unitree DDS 上完成历史 Actor80 视觉控制 bring-up；并在真实训练容器中验证模块加载、PPO 更新、checkpoint 保存/恢复和平台发布链。

**已实现、仍待后续平台/真机验收的目标架构。** 低层 Actor77、独立视觉高层 PPO、ResponseAdapter、schema2 模块化 bundle、`loco.onnx + nav.onnx` 发布合同和高层反馈链已经形成设计与不同程度的代码/容器 smoke 证据；高层迷宫成功率、双 ONNX Jetson 接管时延、SportMode/IMU 反馈质量仍不能写成既成真机成果。

项目并非只训练单个策略网络，而是同时处理四个互相牵制的问题：

1. 低层必须在深度视觉与本体感觉输入下稳定地产生 12 维关节动作，覆盖坡、逆坡、楼梯、转向、横移和停车。
2. 高层必须以较低频率产生连续速度命令，在低层尚不完美、会升级、且仿真与真机响应不同的前提下完成导航。
3. 腾讯开悟训练平台每个任务只允许一个预训练模型 ID/一个 checkpoint，而训练、评估、低层续训和未来部署又要求高低层可以独立演化。
4. 真机部署必须把深度相机、IMU、SportMode/UWB 状态、ONNX recurrent state、关节映射、限速与翻倒保护组织成可观测、可降级的实时系统。

适合的岗位关键词：**机器人强化学习、Sim2Real、四足运动控制、视觉策略蒸馏、层级强化学习、PPO/RNN、ONNX/Jetson 部署、机器人安全状态机、训练平台工程化**。

## 2. 系统全景

### 2.1 当前目标架构

```text
深度相机 depth[180,320,1] ──┬─> 低层视觉编码器 ─> latent32
                             │                         │
本体 proprio45 ──────────────┼─────────────────────────┼─> Actor77 ─> joint_action12
exec_cmd3 ───────────────────┘                         │                (50 Hz)
                                                        │
深度相机 depth[180,320,1] ───> 独立 NavigationEncoder ─┐
goal4 + command/velocity/IMU/capability ────────────────┼─> 高层 LSTM PPO ─> target_cmd3
ResponseAdapter(GRU64) 的物理预测 profile16 ──────────┘                    (5 Hz)
                                                                             │
target_cmd3 -> capability envelope -> slew -> exec_cmd3 -------------------┘
```

关键设计原则是：**低层负责“怎么走”，高层负责“往哪儿、以什么速度走”；ResponseAdapter 负责显式估计“当前低层会怎样响应这条速度指令”。** 高层与低层各有独立视觉编码器，不将会随低层训练漂移的中间 latent 直接暴露给高层。

### 2.2 低层运动控制网络

低层维持可部署的 Standard 外部合同：

```text
depth[180,320,1]
  -> CNN -> cnn_feat32

proprio45 = ang_vel3 + projected_gravity3 + exec_cmd3
          + joint_pos12 + joint_vel12 + last_action12

[cnn_feat32 | proprio45]
  -> 2-layer LSTM(hidden=64)
  -> Linear -> L2-normalized latent32

[proprio45 | latent32]
  -> MLP(77 -> 512 -> 256 -> 128 -> 12)
  -> raw joint_action12
```

该设计将深度感知压缩为 32 维 latent，再与 45 维可测运动状态拼接，最终输出 12 个关节原始动作。低层控制频率为 50 Hz，速度命令被注入 `proprio45[6:9]`。其中 Actor77/goal0 与历史 Track Actor80/goal3 是两份不可混用的网络合同。

### 2.3 高层连续导航网络

高层按 5 Hz 运行，使用独立的深度 CNN，避免高层语义受低层视觉编码器更新影响。当前 P2/P3 版本的输入是：

```text
nav_feat32
+ nav_nonvisual36
  = goal4 + previous_target_cmd3 + exec_cmd3 + measured_velocity3
    + velocity_valid + velocity_age + IMU(ang_vel3 + projected_gravity3)
    + capability_profile15
+ response_profile16
+ confidence1
= 85 dimensions
```

高层使用两层 LSTM（hidden=64）和 tanh-squashed Gaussian 策略，直接输出连续 `cmd3=[vx, vy, wz]`。策略采样、log-prob 和 Jacobian 修正保持一致，避免“硬裁剪动作但仍按原高斯算 PPO 概率”的常见训练错误。高层 Critic 可使用仿真真值、接触力、地形等特权信息；Actor 只使用真机可获得的输入。

### 2.4 ResponseAdapter：跨低层版本与 Sim2Real 的系统辨识层

ResponseAdapter 位于高层内部、低层外部，输入全部可在实机得到：

| 输入 | 维度 | 来源 |
|---|---:|---|
| 前一次高层目标 `previous_target_cmd3` | 3 | 控制软件状态 |
| 实际写入低层的 `exec_cmd3` | 3 | command bridge 回读 |
| `measured_velocity3` | 3 | SportMode 平动速度 + IMU yaw rate |
| `velocity_valid/age` | 2 | 反馈链 freshness |
| IMU `ang_vel3/projected_gravity3` | 6 | 机载 IMU |
| `capability_profile15` | 15 | checkpoint/deploy manifest |
| 合计 | 32 | 固定接口 |

网络是 `MLP(35,64) + GRU64 + multi-head`：图内额外计算 `exec_cmd - measured_velocity`。输出不是任意 latent，而是 16 维固定物理语义：0.2/0.6/1.0 秒后的三维速度、1 秒机体位姿增量、卡滞概率和速度预测不确定度。固定输出语义使 Adapter 可以慢速更新而不让高层面对“latent 坐标系旋转”的灾难性输入漂移。

训练时未来真值速度/位姿只用作 Adapter 标签和 privileged Critic；高层 Actor 从不直接读取仿真真值。短时速度反馈明确排除秒级延迟且噪声大的 UWB：优先 SportMode 的 `vx/vy` 与 IMU `wz`，UWB 仅保留为低频全局运动/卡滞证据。

### 2.5 训练与部署共享的命令闭环

```text
HighLevel Actor 或 Standard sampler
  -> target_cmd3
  -> finite check
  -> capability envelope
  -> 50 Hz slew
  -> exec_cmd3
  -> low-level policy
  -> robot / simulator
  -> FeedbackEmulator 或真实 SportMode+IMU
  -> ResponseAdapter + high-level observation
```

`target_cmd3` 与 `exec_cmd3` 分离是关键：前者表达高层意图，后者是经能力包络和斜率限制后真正写入低层 `proprio[6:9]` 的指令。训练、评估与部署使用同一语义，可以定位“规划错误”“低层未跟上”“命令被整形”分别发生在哪一层。

### 2.6 解耦不是“拆成两个文件”：五层边界

高低层能异步训练的前提不是将模型文件物理分开，而是明确规定每一层可变的内容、不可变的合同以及跨层信息的方向。这里的解耦包含五层：

| 边界 | 固定合同 | 可独立变化的内容 | 为什么能降低联调成本 |
|---|---|---|---|
| 控制频率 | 高层 5 Hz 产生 `target_cmd3`；低层 50 Hz 接收 `exec_cmd3` 并输出 `joint_action12` | 高层导航策略、低层步态参数、slew 参数 | 高层不会直接扰动关节动作；低层可在 Standard 中先扩展动作能力 |
| 表示 | 高层拥有独立 `NavigationEncoder`；低层视觉 latent 不作为高层输入 | 两侧 CNN/LSTM 各自更新 | 避免低层视觉特征重训后，高层面对不可解释的 latent 坐标漂移 |
| 梯度 | 只通过命令与观测闭环耦合，不在一次更新中跨模块反传 | 低层 PPO、高层 PPO、Adapter 辅助监督 | 可以将“步态退化”“导航探索失败”“响应模型不准”分别定位 |
| 训练状态 | 每个模块保存独立 optimizer、scheduler、AMP、RNG、iteration/env/gradient step | `resume_low`、高层 warm start、Adapter 校准 | 不会把面向旧低层动力学的 Adam 动量伪装为高层的精确恢复状态 |
| 发布与部署 | 同一 `target -> envelope -> slew -> exec` 命令语义、模块 digest 和 contract digest | 训练 bundle、评估组装包、部署 ONNX artifact | 文件可单包上传，同时防止不同版本模块被静默混配 |

最容易被忽略的是梯度边界。P1.5 中低层 PPO 与 Adapter 是同一段 rollout 的联合训练，却不是端到端混合优化：Adapter 输入、低层 action 和仿真真值标签均 `detach`；低层与 Adapter 分别 `backward`，优化器参数集合必须互斥，并将跨模块梯度非零视作硬错误。这样 Adapter 学的是“观测到的命令响应”，不会通过辅助损失反向塑形关节策略；低层则只由自己的 PPO/步态保护目标更新。

### 2.7 训练流程：先辨识执行器，再训练导航，而非同时探索所有变量

项目的训练顺序把“视觉表示、步态、低层能力域、高层导航、低层版本变化”拆成可验证阶段。阶段之间沿用同一条 command bridge，减少训练目标与接口同时变化造成的归因困难。

| 阶段 | 指令来源与环境 | 更新模块 | 冻结/透明模块 | 核心目标与当前证据边界 |
|---|---|---|---|---|
| R2 特权到视觉蒸馏 | 教师动作、height scan 到 depth 迁移 | 视觉学生编码器与蒸馏链 | 稳定的 Actor77 控制合同 | 已有平台训练与视频证据；证明基础视觉低层，而非高层导航 |
| Standard 指令扩域/P1.5 | Standard sampler 生成连续 `target_cmd3`，经公共 envelope/slew 写入低层 | 低层 PPO 与 ResponseAdapter，各自 optimizer | 高层不存在或作为透明载荷 | 先扩展低层可执行命令，且以 0.2/0.6/1.0 s 标签预热 Adapter；有单测与容器 smoke，长训效果需按任务归档确认 |
| P2 Track 高层 PPO | 高层 5 Hz 输出 `cmd3`，Track/Camera 课程 | NavigationEncoder、导航 Actor/Critic；Adapter 小学习率随动 | 低层视觉 Encoder/Actor 作为冻结执行器 | 高层学习“在实际低层响应下如何导航”；代码和容器 smoke 已有，迷宫完成率仍待平台证据 |
| 后续低层恢复/P3-P3.5 | Standard 或可回放的高层命令分布 | 低层的局部 RNN/action 参数与 Adapter | 完整高层透明保存、不参与低层优化 | 在不改变 `exec_cmd3 -> joint12` 合同的前提下改善低速楼梯/鲁棒性；当前为在研训练工程 |
| 高层再适配/评估 | 更新后低层 + 同一 command bridge | Adapter-only 校准或高层 warm start | 低层冻结 | 先测 command-response 误差，再决定最小的必要更新范围，避免不必要地整体重训 |

这种顺序的关键不是“先后训练”本身，而是每一阶段只新增一种主要不确定性：R2 先固定低层结构与视觉表征，P1.5 先测清低层在连续命令下的响应，P2 才让高层为导航回报探索；之后低层迭代时先恢复响应模型，再判断是否需要修改高层。相比端到端 Track PPO，同一失败可以被归因到具体层而不是被混成“策略没学会”。

### 2.8 单 checkpoint 下的独立恢复与低层升级策略

平台仅允许一个预训练包，因此采用 `kaiwu_train_v1/schema_version=2` 组合 bundle，而不是要求两个模型 ID 同时加载。包内至少分为 `modules.low_level`、`modules.high_level` 与 `response_adapter`，并分别存储 optimizer、scheduler、RNG、训练计数、父模型血缘、capability/command/feedback digest。其目标是“单文件传输，模块化生命周期”，而不是“任何模块随意热插拔”。

| 使用场景 | 加载/更新策略 | 不可省略的检查 |
|---|---|---|
| `resume_low` | 只实例化低层训练模块；高层权重保留为 CPU 透明载荷 | Actor 输入 shape、`exec_cmd3` 位置、低层 capability digest、低层 optimizer/RNG |
| 高层训练 | 加载并冻结低层执行器；实例化独立高层与 Adapter optimizer | 低层版本、命令 bridge、观测归一化、Adapter 物理输出语义 |
| 低层小幅升级 | 先冻结低层，用新 rollout 校准 Adapter prediction head；再做高层零样本评估 | 0.2/0.6/1.0 s tracking、steady-state/overshoot、capability envelope |
| 低层响应明显变化 | Adapter 校准后，以旧高层参数 warm start 重训高层 | reward/observation contract 不变、旧 optimizer 是否应重建 |
| 指令语义或接口破坏性变更 | 显式 schema migration，必要时重训高层 | shape、单位、slew/envelope 语义、模块 digest；禁止 silent load |

部署同样遵循这条边界：训练 bundle 不等于可部署 release，`adapter_only` 包也不得假装具备完整导航能力。`loco.onnx + nav.onnx` 的双图发布与 Jetson 影子接管是已定义的目标合同，必须经 Python-ONNX 多帧一致性、时延和反馈质量验收后才可宣称完成。

## 3. 训练路线的演进

### 3.1 历史基线：端到端 Track PPO 与 Actor80

早期复赛 Track 路线使用一个完整策略直接把视觉、本体、goal 输入映射到关节动作。这条路线完成了视觉策略和真机部署的早期验证，但暴露出高层导航错误会直接破坏步态、Actor77/Actor80 合同难以兼容、低层升级难以复用等问题。

历史 Track/378413 的部署合同是 `proprio45 + latent32 + goal3 = Actor80`；Standard 低层合同则是 `proprio45 + latent32 = Actor77`。项目后续明确禁止仅按模型 ID 混载这两类 checkpoint，而要求同时检查 task、format、goal 维度和 Actor 首层 shape。

### 3.2 特权教师到视觉学生：R2 DAgger 与视觉蒸馏

第一条稳定主线先解决“可控步态”和“视觉感知”：

```text
特权教师：proprio45 + height_scan256 -> Actor301
          ↓ DAgger / 行为蒸馏
视觉学生：depth -> latent32；proprio45 + latent32 -> Actor77
```

R2 阶段的 `standard-dag_16288` 已有平台执行证据：6000 iterations、147,456,000 environment steps、约 2 小时 59 分，最终学生驱动比例约 0.998，动作 MSE 约 0.000939、cosine similarity 约 0.9998。4 段视频均完成，无 timeout/abnormal，平均分 64.19，楼梯 66.76、逆向段 61.63。它证明了特权教师到学生的动作对齐和基础楼梯步态，但该阶段仍使用 height scan，不能直接当作真机部署模型；当时四阶段晋升被 forced，也留下了“不要让训练状态机的形式门槛冒充质量结论”的工程教训。

随后 Stage 4 将深度视觉蒸馏整合到主线，形成 `visionfull-28401` 等视觉低层血缘；之后的视觉 PPO、连续指令扩展和高层架构均以 Actor77 视觉合同为基础。

### 3.3 Standard 连续指令扩域：34728 到 P1.5

`commandfull-34728` 是低层扩域父模型。P1.5 的目标不是立刻让高层接管，而是先由 Standard command sampler 产生 `target_cmd3`，经过未来高层共用的 envelope/slew 后形成 `exec_cmd3`。同一批 rollout 中：

1. 低层 PPO 继续学习更稠密的前进、转向、刹停和有限横移指令域；
2. ResponseAdapter 以独立辅助损失学习 command-response 动力学；
3. 两个 optimizer 参数集合严格互斥，双方 backward 后都检查对端梯度为零；
4. checkpoint 升级为 schema 2，保存低层、Adapter、各自 optimizer/scheduler/RNG、训练计数、数据合同和 digest。

P1.5 专门处理了 0.2/0.6/1.0 秒未来标签、command hold、reset/termination mask、GRU burn-in、同一低层版本内记录队列和反馈噪声仿真。为了保证未来标签、burn-in 与 PPO rollout 同时可用，平台 256 环境时的 `256x80=20480` 帧预算引发 CUDA illegal-memory；工程上将正式环境数收敛至 128，使预算降为 `128x80=10240`，低于父阶段已验证预算，并保留完整标签链。

### 3.4 P2：连续高层 PPO 取代 Oracle/离散词表最终方案

早期 hier-nav MVP 使用 Oracle/DAgger 和离散命令词表验证训练生命周期、混频时序、checkpoint 发布与评估入口。它保留为 smoke/对照基础，但不是最终高层策略。

P2 将高层改为连续、闭环、recurrent PPO：冻结低层视觉 Encoder/Actor，训练独立 NavigationEncoder、LSTM Actor/Critic，并以小学习率更新 ResponseAdapter。高层从二维 `[vx,wz]` 起步，后续升级到三维 `[vx,vy,wz]`；训练动作使用可信核心与更宽探索硬边界，能力包络用于表达低层可支持的非矩形指令域，不把超域动作简单伪装为可信跟踪。

高层 reward 被多次审查和重构：删除可在原地长期领取的绝对距离/heading 正奖励，改为 5 Hz transition 边界上的进度 potential、一次性完成/失败/超时、时间成本、平滑 crawl dead-zone、command rate、真值 tracking、碰撞和卡滞项。这样可避免机器人因为“靠近目标但不完成”而变得保守，也减少复杂地形门控的不可解释性。步态保护保持低权重、对称、基线超额才触发，避免高层训练反向损坏已经可用的低层步态。

### 3.5 P3/P3.5：低层 Sim2Real 恢复、径向导航与步态非劣化

P3 的重点转向“持续改低层而不推翻高层接口”：

- Standard 路线采用相对真实出生点的 M1/M2/M3 径向里程碑。默认 8 m 地形中，平台完成边界是 3.90 m、timeout 边界是 4.00 m，因此使用 3.93 m 虚拟目标和终点软刹车，防止 5 Hz 指令跨过边界。
- 使用 friction、base mass、noise 等经过平台可用性确认的域随机化；对 push、action delay/gain、PD、COM 等平台覆盖行为，明确规定“只有 runtime readback 证明确实生效才可对外声称”。
- 步态奖励从强制固定步态转为父策略统计基线上的异常超额惩罚，关注四腿 duty、对角频率、持续腾空、滑移和姿态，但不针对单腿塑形、不误罚坡/楼梯中的正常 pitch。
- P3.5 当前进一步收敛为 2 小时低速楼梯、相机时序与后期 push 专项：只训练低层 LSTM、RNN output、最终 action head、Critic 和 Adapter；CNN、Actor body/std、完整高层均冻结。训练专用 transport 扩展接触、关节加速度和 push telemetry，但这些不进入 policy、评估、ONNX 或部署接口。

P3/P3.5 当前应描述为**持续开发中的训练工程与容器 smoke**，不是已经完成的最终赛道性能。

## 4. 核心技术难点与解决方案

### 难点一：平台只允许一个 checkpoint，如何实现高低层异步训练？

**问题。** 腾讯开悟任务按一个模型 ID/一个 checkpoint 运行与评估，不能让高层和低层分别从两个平台模型 ID 自动加载；但两层如果强绑定，又无法独立迭代。

**解决。** 设计 `kaiwu_train_v1/schema_version=2` 的模块化组合包：

```text
modules.low_level: encoder / actor / critic / action distribution
modules.high_level: navigation encoder / actor / critic / ResponseAdapter
optimizers.low_level / optimizers.high_level / optimizers.response_adapter
training_states.low_level / high_level / response_adapter
contracts + lineage + per-module digests + capability profile
```

Standard `resume_low` 可以只实例化低层，把高层的权重、optimizer 和状态作为 CPU 透明载荷逐位保存；高层训练时低层作为冻结执行器；P1.5 则显式允许 `low_level_and_response_adapter` 复合 scope。每个优化器的参数集合必须与 scope 精确匹配，冻结模块 digest 在保存时核验。这样做到“文件是一份、模块和训练状态独立”，并支持高/低层并行训练后由 composer 进行结构化组合、兼容性检查和平台重导入。

### 难点二：低层更新后，高层如何不从头训练并降低 Sim2Real gap？

**问题。** 单纯将高层输出的目标速度喂给低层，无法知道当前低层、地面、执行器和反馈延迟下是否能实际做到；低层升级后，旧高层更可能失配。

**解决。** 将 `target_cmd -> envelope -> slew -> exec_cmd` 固化为稳定接口，配合 capability profile 声明有效方向、范围和 slew 能力；再由 ResponseAdapter 对实测命令响应做短时预测。高层不输入模型 ID，而输入速度、延迟、有效性、IMU、命令历史和能力描述。低层换代后先零样本评估，轻度退化只更新 Adapter/head，中度退化再 warm-start 完整高层，接口破坏才升级 contract major version。

### 难点三：仿真真值与真机传感器语义不同，如何避免训练泄漏？

**问题。** 仿真可直接读到完美 `root_lin_vel_b`、姿态、接触力和地形；真机拿到的是存在频率、噪声、丢帧和延迟的 SportMode、IMU、UWB、D435i。直接将仿真真值喂给 Actor 会造成不可部署的性能幻觉。

**解决。** 实现按环境独立、有 delay queue/filter/dropout/source state 的 `FeedbackEmulator`：仿真真值一条支路只给 Adapter future label、asymmetric Critic 和 metric；另一条经模拟频率、延迟、噪声、偏置、丢帧、freshness 后，才给 Actor/Adapter 形成 `measured_velocity3 + valid + age + IMU`。Standard 指令预热与高层 PPO 复用同一反馈实现和归一化；feedback profile 与实现 SHA 写入 checkpoint，避免复现时悄然改变语义。

### 难点四：UWB 噪声和延迟很大，怎样既保留全局导航又不损坏即时控制？

**问题。** 实测 UWB 存在秒级延迟、噪声大且信号不稳定，将它作为即时速度 tracking 会误导高层和 Adapter。

**解决。** 将 UWB 从即时 `measured_velocity3` 中移除：短时平动优先 SportMode `vx/vy`，yaw 使用 IMU gyro；SportMode 不可用时预留 IMU+关节+足端接触的机身线速度估计器。UWB 只保留为低频全局目标/位移与 3-5 秒卡滞证据，并将 `valid/age` 显式输入模型，防止无效零值被误解为真正静止。

### 难点五：连续高层 PPO 的时间尺度、RNN 和终止样本如何正确处理？

**问题。** 低层 50 Hz、高层 5 Hz，导航动作要跨 10 个低层步累计奖励；auto-reset 和 wrapper 还可能丢失 terminal/truncated 信号。若直接沿用低层 PPO storage，会把旧/新 episode 拼接，产生看似可训练但无效的价值估计。

**解决。** 建立高层专用 recurrent rollout storage、32 tick/TBPTT16、variable-duration GAE；worker transport 显式传递 reset、success/failure/timeout 和 terminal 前地形/目标快照。P2/P3 评估采用模块-only assembly，不创建 critic/optimizer/buffer；并对 terminal 数据冻结 command、速度和奖励 aux，避免 auto-reset 后状态污染前一 transition。

### 难点六：导航奖励容易诱导保守停滞，如何构造稠密但不可刷的奖励？

**问题。** 旧设计的绝对目标距离正奖励在靠近终点时可持续领取，而时间成本太弱；完成 bonus 还可能被 dt 缩放，导致“站在终点附近”优于实际完成。

**解决。** 保留 goal distance 作为 observation/metric，不以其绝对值持续奖励；改用距离差分/进度 potential、new-best frontier、一次性完成奖励、恒定时间成本和温和的 crawl dead-zone，负向绕路惩罚小于正向推进。取消静止也可领取的 heading 奖励、直接奖励大 cmd 值以及重门控规则；在全局奖励中用对称且有上限的步态/碰撞防线保底。这使奖励的优先关系更接近“稳定前进 > 缓慢前进 > 停止 > 失败”。

### 难点七：赛道课程与前端统计可能错误，如何区分真实能力与观测假象？

**问题。** 平台 Track 生成器中 row 表示赛段、column/`terrain_types` 表示难度；课程提升的是 types 而不是 levels。开口迷宫的整数网格使 L0-L3、L4-L7、L8-L9 实际只对应三种通道宽度，且 L0 依然是完整 Kruskal maze，不是“几乎无墙”的简单导航环境。评分器还曾只快照 `terrain_levels`，在 curriculum 更新和 auto-reset 后按 post-reset `terrain_types` 归因，造成 L1/L2 失败计数错位。

**解决。** 通过本地容器源码镜像与 RPC 在线检查地形生成、reset 和 scorer 调用顺序；在训练侧增加 terminal 前快照、目标前快照和分赛段/分方向 metric，并将“配置合同”“worker proxy”“平台 scorer 权威完成数”分开显示。平台 scorer 的最终修复仍须由对应分支和平台回归确认，因此不能把训练侧诊断修复表述成已完成的平台改造。简历中可表述为：**定位训练平台课程/指标归因中的时序与语义错配，建立终止前状态快照与分桶监控。**

### 难点八：改善步态但不能把已有步态奖励塑坏，如何做非劣化训练？

**问题。** 楼梯和低速区易出现快慢脚、跛脚、单脚长时间悬空和 slip；但用强 trot/单腿奖励会误罚必要的坡面/楼梯姿态，反而破坏原有策略。

**解决。** 使用父模型按 straight/turn/lateral、地形类型建立统计 envelope，正常区间内奖励严格为零，只有 duty、对角频率、持续腾空、滑移、关节加速度/姿态等超出基线时施加 capped 轻惩罚。镜像一致性、memory 和 anchor 辅助梯度均限定为 PPO policy gradient 的很小比例，并只流入低层 LSTM、RNN output 和最终 action head；CNN 与 Actor body 保持冻结。接触映射无法证明时，训练项自动归零并记录告警，而不伪造数值。

### 难点九：有限 GPU 显存下同时训练视觉、RNN、PPO 与响应预测

**问题。** ResponseAdapter 需要 future horizon、burn-in 与长 rollout，视觉高层还要保存 depth/RNN 状态。P1.5 的 256 环境长 rollout 已经引发 CUDA 错误。

**解决。** 将 P1.5 训练收敛到 128 环境；P2 高层 rollout 采用 pinned FP16 depth、独立所有权和 CNN microbatch；低层 PPO storage/S0 anchor/第二套 Camera 不在高层训练中创建。P3/P3.5 则以冻结 CNN、只更新局部 RNN/action 参数的方式控制反向图和显存，同时保留完整训练/保存/resume smoke。

### 难点十：从训练 checkpoint 到 Jetson 的实时安全部署

**问题。** 训练包包含 critic、optimizer、Adapter/高层状态等，不能直接当作部署制品；部署侧还要处理 D435i 深度流、ONNX recurrent state、Unitree DDS、UWB、关节排列、异常动作、翻倒和控制权冲突。

**解决。** 已建立训练包与 release artifact 的明确隔离：训练包 `deployable=false`；manifest 记录模块 digest、contract、ONNX SHA、tested pair 和兼容性报告。历史单低层部署已在 C++ 状态机中实现启动时 12 维关节映射/参数/channel 校验、每帧 proprio45 组装与 LSTM state 回灌、ONNX finite/bounded 检查、动作 scale/offset/clip、Passive 降级、slew 和诊断 CSV。基于同源组合包的 `loco.onnx + nav.onnx` 双图导出、影子模式和接管路径则是已定义且待验收的后续合同，不能与历史低层 bring-up 混称为完成。

### 4.11 内部面试备忘：用户推动的关键技术判断

这一节只保留那些改变了系统边界、训练路线或验证标准的判断。它用于项目复盘和面试准备；对外简历应从第 9 节选择经证据分级后的表达，并按实际个人职责决定使用“设计”“实现”“参与”或“负责”。后续的台账案例是这些判断落地时遇到的工程证据，不应反过来成为简历主线。

#### 判断 1：将“导航”和“步态”拆开，但不把平台单 checkpoint 当成解耦障碍

**原始矛盾。** 端到端 Actor80 直接从视觉、goal 到关节动作，导航错误会直接表现为步态失稳；但腾讯开悟又限制每个训练任务只加载一个模型 ID/一个 checkpoint，看似无法让高层和低层独立训练。

**关键判断。** 解耦应发生在模块、optimizer、训练状态和接口层，而不是一定要发生在文件层。低层的稳定外部合同是 `depth + proprio45(exec_cmd3) -> joint12`；高层只通过连续 `cmd3` 调动低层，不碰关节动作。一个 schema2 bundle 可以同时携带两个网络，但 Standard `resume_low` 只实例化低层，高层作为透明载荷不进入 GPU/optimizer；高层训练又把低层视为冻结执行器。并行训练结果再通过带 contract/digest 校验的 composer 组合。

**为什么有价值。** 这同时解开了平台限制、低层可持续优化、后续高层适配和部署模块化四个问题。它不是把网络堆在一起，而是定义了“什么可以变、什么必须不变”的系统边界。

**安全表述。** “主导设计面向单 checkpoint 训练平台的模块化分层控制架构，支持低层续训、高层冻结执行与独立训练状态恢复。”

#### 判断 2：把视觉 Sim2Real 做成两阶段的“表示迁移 + 感知迁移”，而不是强行让教师先可部署

**原始矛盾。** 特权 height-scan 教师能在仿真中提供高质量步态监督，却不能上真机；若要求教师先解决所有真机传感器问题，会把“教师是否可部署”误当成“教师是否有监督价值”。一次从 flat teacher 直接蒸馏到深度视觉学生，又会同时改变网络结构和传感器分布，难以归因。

**关键判断。** 先把 flat301 运动教师转换为共享 Actor77 的 `height_scan -> latent32` 特权学生，先稳定网络内部表示；再把 `height_scan` 替换为 D435i depth，由 `VisionEncoder(CNN+LSTM)` 预测同一 latent32，保持 Actor77 冻结。训练期允许教师使用 scan，评估/部署只允许 `proprio + depth`；单次 forward 缓存、序列语义、hidden reset、三路 latent/cos/action loss 与 DAgger 接管共同保证 recurrent 蒸馏没有“重复推进 LSTM”或单帧 replay 伪样本。

**为什么有价值。** 这是按变化维度拆实验：先解决结构变化，再解决传感器变化；用冻结 Actor 把步态稳定性固定为控制变量。它也是后来“低层可升级、高层不共享可变 latent”的思想起点。

**安全表述。** “设计两阶段特权到深度视觉蒸馏链路，以冻结 Actor77 和 recurrent 表示对齐隔离网络结构与传感器迁移风险。”

#### 判断 3：用连续命令和 ResponseAdapter 表示低层响应，而不是用离散词表、模型 ID 或共享 latent 绑定高低层

**原始矛盾。** 低层初版只“基本能走”，未来仍要拓展指令域、更新步态和改善 Sim2Real；若高层依赖低层 CNN latent、离散词表或固定模型 ID，低层一升级，高层输入语义和输出能力就一起漂移。

**关键判断。** 高层长期输出固定为连续 `cmd3=[vx,vy,wz]`，低层能力以 capability envelope 描述；在高层内部增加 ResponseAdapter，以命令历史、实测速度、IMU、valid/age 和 capability 预测 0.2/0.6/1.0 秒响应、位姿变化、卡滞概率和不确定度。Adapter 输出必须是固定物理语义，而非可任意旋转的 latent；这样先用 Standard sampler 预热 Adapter，再让 RL 高层接管时，低层更新后可先做零样本评估，再决定只适配 Adapter 还是 warm-start 完整高层。

**为什么有价值。** 将“低层版本变化”和“仿真-真机执行偏差”统一成在线系统辨识问题，并将连续控制的可扩展性、可解释性和异步训练结合起来。

**安全表述。** “提出并实现基于连续速度命令与 GRU ResponseAdapter 的分层控制接口，将低层版本变化与 Sim2Real 偏差建模为可预测的 command-response 动力学。”

#### 判断 4：把传感器质量本身纳入合同，拒绝让 UWB 的低频噪声污染即时运动控制

**原始矛盾。** UWB 既能提供全局目标，又存在秒级延迟、噪声和不稳定性；把它直接当作即时线速度反馈，会令 Adapter 和高层学到不可能在真机稳定复现的响应关系。仿真真值速度又过于理想，同样不能直接喂给 Actor。

**关键判断。** 即时 `measured_velocity3` 采用 SportMode `vx/vy` 加 IMU gyro `wz`，将 UWB 限制为低频全局运动与卡滞证据；速度反馈以 `valid/age` 显式传入，失效零值不能被解释成真实静止。训练中将真值严格拆为标签/privileged Critic 支路和经 FeedbackEmulator 产生的部署语义测量支路；随机化频率、延迟、噪声、丢帧和 freshness，而不是把“完美仿真速度”伪装成传感器数据。

**为什么有价值。** 这是把 Sim2Real 视为观测语义问题而不只是物理随机化问题，并直接决定了高层真正可部署的输入白名单。

**安全表述。** “定义 SportMode/IMU/UWB 分层反馈合同并实现 FeedbackEmulator，使高层策略只依赖真机可获得且带有效期语义的状态估计。”

#### 判断 5：奖励设计采用全局势函数与时间成本，而不堆叠难以解释的门控启发式

**原始矛盾。** 低速和复杂地形下，给绝对距离、heading、cmd 幅值或大量 obstacle gate 奖励，容易让策略通过靠近终点、转圈或迎合局部规则刷收益；同时太多条件使训练失败后无法判断责任在高层、低层还是奖励本身。

**关键判断。** 保留目标距离作为输入和诊断，但不持续奖励绝对距离；使用 progress/potential difference、new-best frontier、一次性完成回报、恒定时间成本、平滑 crawl dead-zone、有限 command-rate 和安全底线。面板发现“局部进度升高、success 下降、timeout/spin/stuck 上升”后，不改为增加更多规则，而是把 reward 改成 terminal-consistent frontier potential，在完成、失败和超时时统一清空未兑现势能。

**为什么有价值。** 体现的是从策略可被利用的激励结构出发，选择少而全局的奖励，而不是把机器人问题改写成规则系统。该方向与“低层步态仅非劣化保护、不强制某种 gait”的取舍一致。

**安全表述。** “设计终止一致的导航势函数奖励，使用全局进度与时间成本替代可刷取的绝对距离/多门控启发式，并以训练曲线验证策略套利模式。”

#### 判断 6：将部署时序和比赛规则提前写入训练合同，而不是等模型训练完再补 C++ 适配

**原始矛盾。** 高层 5 Hz、低层 50 Hz，若部署时另起导航线程，就会引入锁、快照、状态竞争和不确定延迟；若把导航频率写死在融合 ONNX，又难以监控和降级。另一个典型边界是 Standard 8 m 地形的完成半径 3.90 m 与 timeout 边界 4.00 m：一个“多走一点”的目标会直接穿越有效区域。

**关键判断。** 采用一个控制线程、两个 ONNX session：每帧先按时发布低层关节动作，随后每 10 帧仅在剩余时隙运行 nav；nav 超时就保持 held/exec 并跳帧，影子模式先测 nav 帧 p95，再允许接管。训练侧镜像同一帧级 `target -> slew -> exec` 语义。对于任务边界，从运行时 terrain size 推导完成/timeout 阈值，使用 3.93 m 虚拟目标、3.90 m proxy 与终点软刹车，而不是硬编码 4.2 m 目标。

**为什么有价值。** 这将实时系统、模型结构、训练数据分布和比赛评分约束统一为一个可测时序合同，显著降低“仿真可以、真机线程调度失效”的风险。

**安全表述。** “以部署时序和赛道终止边界反向约束训练接口，设计单线程双 ONNX 的影子接管路径与 terminal-safe 径向导航合同。”

#### 判断 7：将实验结论分级，把“平台配置”与“实际发生”分离

**原始矛盾。** Isaac 平台的 `BaseEnv` create-once 语义意味着阶段 `env.reset()` 不会重建 friction/mass/EventManager；Push 又可能在短 episode 内根本不触发。若只看 TOML 或监控配置，就会错误地宣称域随机化、外力恢复或课程已生效。

**关键判断。** 读取平台镜像后主动撤回“阶段 reset 动态重建 DR”的方案，改为首次 reset 装配可证明的配置；没有 EventManager/PhysX readback 就将指标标记为 unavailable/telemetry=0。随后将近场深度故障建模为跨完整 RNN sequence 的持续时序事件，并按有效像素预算控制 dropout，避免在已有孔洞上叠加出不真实的几乎全黑图像。

**为什么有价值。** 它把“代码写了什么”与“训练环境实际执行了什么”彻底分开，是复杂仿真平台上形成可信实验结论的前提。

**安全表述。** “建立面向 Isaac 平台语义的实验有效性原则：仅将 runtime readback 可证实的随机化和扰动纳入训练结论，并用时序故障模型替代静态噪声假设。”

**简历取舍建议。** 若只保留四条，优先使用判断 1、2、3、5；强调真机/边缘部署时，用判断 4 或 6 替换判断 5。判断 7 适合研究型岗位、机器人平台或强调实验严谨性的面试追问。

### 4.11.1 历史对话交叉验证：用户推动的问题定义与验收标准

以下六项来自项目相关的 Codex 归档计划/对话，而非事后从代码倒推。为避免将自动摘要误当原始事实，每项均区分“用户直接提出”和“仓库/归档可核验的落地”；原始会话不纳入仓库、不复制敏感运行信息，只在本机按 session ID 留作追溯。

#### 判断 8：先定义“学生在哪些时刻接管”，再把 DAgger 当作训练算法

**用户直接提出。** 不接受只靠训练轮数描述蒸馏过程，要求渐进式 DAgger、明确晋升条件、一次任务覆盖全过程，并把阶段 checkpoint 命名、教师冻结、按环境 safety takeover、reservoir 样本池、阶段最佳点/回退和 resume 语义写成一个可检查的计划。还要求先验证第 100 iteration 能生成 `daggerzero`，任务结束必须有 `daggerfull`，并在下载视频、固定 seed 上下楼评估后才决定是否进入视觉蒸馏。

**简历表达。** “定义渐进式 DAgger 的控制权转移与阶段验收机制，将教师接管率、可恢复 checkpoint 和固定场景视频纳入视觉学生准入标准。”

#### 判断 9：蒸馏稳定性首先来自命令分布一致，而不是事后用网络容量弥补

**用户直接提出。** 在 Standard 过桥/蒸馏讨论中，明确质疑学生训练命令域是否必须和已验证的 `archive/代码存档/复赛_standard` 一致，并坚持教师应指向可核验的原始训练代码，拒绝未经检查的 command sampler 解释。

**形成的能力。** 这迫使训练设计将教师来源、命令采样、归一化和 Actor 输入合同作为同一份血缘信息检查，而不是只校验 checkpoint 能被加载。之后的 34728/P1.5 连续扩域也采用“先以 Standard sampler 预热实际 `exec_cmd3` 响应、再由高层接管”的路径，避免同时改变教师、控制域和策略责任。

**简历表达。** “将 command distribution 与 checkpoint 血缘作为蒸馏稳定性的显式合同，先验证教师/学生控制域一致性，再扩大连续命令能力。”

#### 判断 10：澄清目标坐标系，区分“给速度”与“要求到达并停止”

**用户直接提出。** 真机讨论中主动纠正“前方 1 m”的含义：它不是世界坐标终点，而是随机体变化的相对虚拟目标；随后继续追问固定速度与 goal 是否会自动停车，要求沿 C++ 控制链而不是凭模型名称回答。

**形成的能力。** 运行时 goal 从不参与语义的占位向量修正为训练归一化后的 body-frame 值；同时定位到 fixed-speed 分支只是速度 clamp、并没有 arrival detector。因此将定位反馈、导航 policy、显式停车/超时状态机拆开：UWB/goal 可以提供距离或方向证据，但不能天然替代到达判定。这也是后续 radial terminal contract、3.90 m 完成边界、软刹车和 stale-feedback 降级的起点。

**简历表达。** “在真机控制中厘清 world-frame 终点、body-frame 虚拟目标、速度命令与到达状态机的边界，消除‘固定速度会自动停车’的接口假设。”

#### 判断 11：把 Adapter 视为长期接口，新增诊断只能追加，不能重排已训练语义

**可核验落地。** P1.5 训练完成后，高层 P2 需要更宽的命令域和额外诊断字段；相关归档代码明确保持 ResponseAdapter 前 30 个 worker-owned slots 的稳定语义，将 P2-only diagnostics 追加到尾部，而非重排字段。Adapter 则仍位于组合 checkpoint 的 `modules.high_level`，部署导出会明确忽略 adapter-only 载荷。

**形成的能力。** 这把“低层未来可升级”的设想落实为具体兼容规则：旧 P1.5 record、标签队列和 checkpoint 仍可加载，新导航输入在版本化尾部扩展。它与 schema2 的模块化组合共同防止训练数据格式悄然改变导致高层把旧字段误解释为新语义。

**简历表达。** “为 ResponseAdapter 建立追加式、版本化观测合同，保持已训练 command-response 记录可加载，同时支持导航诊断与命令域演进。”

#### 判断 12：短 smoke 不以“进程没报错”为成功，而以训练生命周期证据为成功

**用户直接提出。** 在发现步数不增长、失败数上升后，要求以 D1--D5 的真实训练链路重定义 smoke success，追问硬编码最大轮数为何覆盖平台配置，并要求保存、模型发布、恢复、视频/固定 seed 评估成为不同层级的验收项。

**形成的能力。** 因而项目的验证口径被拆分为：本地单测、容器 GPU update、checkpoint schema round-trip、平台模型列表发布、平台长训与真机/视频评估。任何一层通过均不会自动升级为下一层结论；这与台账中的 lifecycle、监控口径和 runtime readback 原则一致。

**简历表达。** “建立训练实验的分层验收体系，将优化器更新、checkpoint 发布、可恢复性、固定场景评估和真机证据显式分离，避免以无报错 smoke 代替性能结论。”

#### 判断 13：对扰动和步态恢复坚持少门控、可证实、不可刷的约束

**用户直接提出。** P3.5 计划明确限定：不训练负向前进；横摆正负对称；push 只作用线速度平面、不作用 z/角速度；恢复不设置可刷的专门奖励；外力与相机扰动只有在 telemetry 有效、事件计数递增且实际 delta 非零时才进入正式训练。对于现有良好步态，要求保留对称性与跛行/单脚悬空防线，但拒绝强塑形。

**形成的能力。** 这直接塑造 P3/P3.5 的 fail-closed telemetry、shadow-only gait 项、有效像素预算和非劣化基线设计。它说明项目并非盲目增加随机化和奖励，而是先约束“什么扰动真的发生”“什么恢复行为不应被奖励套利”。

**简历表达。** “制定可审计的相机时序与外力扰动准入原则，并以对称、非劣化的步态约束替代强行指定 gait 的奖励塑形。”

**形成的能力。** 这迫使系统从修改平台 internals 转为利用正式 observation process、worker command bridge、`usr_conf`、EventManager 公开配置和 terminal 前 transport 等扩展点。它不是保守的编码习惯，而是对封闭训练平台的运行时所有权进行建模：本地 diff 即使能跑，也不构成正式训练能力。

**简历表达。** “识别托管仿真平台的源码覆盖边界，重构训练扩展到公开 worker/observation/config 接口，避免正式实验依赖不可持久的本地补丁。”

#### 判断 15：将学生独立化、命令扩域和步态纠正拆成不同实验，拒绝让失败阶段成为错误基线

**简历表达。** “构建按能力风险分解的训练路线：学生独立化、命令泛化和步态修正分阶段验证，以冻结边界和父策略基线防止已验证运动能力被联合训练掩盖。”

### 4.12 工程证据附录：从台账提炼的真实问题解决案例

这一节是本项目最适合在简历和面试中展开的部分。每个案例都来自实际训练记录、容器复现或平台运行现象，而不是预先写好的“功能清单”。

#### 案例 A：把“模型为什么不出现在平台模型列表”还原为平台生命周期错配

**表象。** Nav 训练能够在运行目录写出 checkpoint，却不能稳定按预期频率在开悟前端生成可选模型；最初按业务 outer iteration 和自定义 `save_model()` 推算模型 ID/保存节拍，得到的 ID 甚至与历史成功 LBC 模型不一致。

**调查与关键判断。** 用历史 LBC 的 `10000 x 24 = 240000` 低层帧，对照 `282409 - 42399 = 240010` 平台步，证明模型 ID 与 `dump_model_freq` 实际由 `BaseAgent.learn()` 回调推进，而不是由 Nav 的 5 Hz outer iteration 或写文件次数推进。失败 Nav 从父 ID 34728 只到 34788 的现象也与约 60 个 outer iteration 对齐，排除了“平台随机漏存”猜测。

**解决。** 将 lifecycle callback 移到每个成功低层批量帧，保持 TBPTT 梯度频率不变；标准保存交回平台，设置 3600 callback 的 dump 频率，并把运行中 `/data/ckpt` 与最终 `/data/user_ckpt_dir` 归档候选、callback 成败、步数、文件大小和 SHA256 分开记录。正常结束、平台停止和 SIGTERM 统一进入幂等 final save。

**价值。** 这不是简单加保存逻辑，而是从平台计数语义反推训练生命周期；它解决了“本地文件存在但平台不可复用”的关键断裂。平台发布链已有任务 234786/234805 的归档证据，训练周期细节仍应随任务配置复核。

#### 案例 B：用训练面板数据证明高层 reward 在奖励“失败前的局部移动”

**表象。** P2 训练约 100 分钟后，局部 `progress + new_best` 约为 `0.574/tick`，而 success 只有约 `0.076/tick`；timeout 从 18 上升到 46，spin 从 12.4% 升到 28.4%，stuck 从 17.4% 升到 51.5%。机器人并非“不学”，而是学会了在坡/楼梯取得局部进度后，在迷宫里保守转圈直到超时。

**根因。** 旧奖励在未完成 episode 中持续发放局部 progress/new-best，而 timeout 罚分比 hard failure 更轻。策略可以通过“有一点前进、但不承担探索终点风险”取得比完成更稳定的回报。

**解决。** 不再继续加大 goal/heading/速度等启发式奖励，而是把 reward 改成 episode-relative monotonic frontier potential：终止时 success/failure/timeout 统一令 `phi_after=0`，从而 claw back 尚未兑现的局部潜力；同时提高 timeout 的相对代价。这样把奖励从“过程积分”改成“终止一致的势函数差分”，消除了失败 episode 长期保留正收益的套利通道。

**价值。** 体现的是从量化曲线倒推策略行为，再以 reward algebra 修复，而不是依赖主观观察不断调权重。该修复有定向单测，平台长训效果仍需单独验证。

#### 案例 C：阻止一个 NaN 或 reset 帧污染整段 GAE 与步态统计

**表象。** P2 的 reward settlement 并未统一检查 goal、duration、terminal reason、safety、gait/collision 等每一项是否 finite；任何单行 NaN 都可能在写入 rollout 后污染 `best_goal_distance`、GAE 和 return statistics。另一个隐蔽问题是 reset 帧先写入 gait ring 再清空计数，导致下一帧出现“分子两帧、分母一帧”的 duty factor 大于 1。

**解决。** 建立逐环境的 finite boundary：异常行所有 reward component 归零、duration 收敛到合法范围、保持旧 best、清理 frontier/collision state，并使写入 storage 的 transition 保证有限；只有非-reset 行才增加 gait window 分母。对 checkpoint 则坚持“身份元数据不一致可告警，选中包的反序列化/spec/shape/finite 不兼容必须硬停”，避免为了续训成功静默换成错误父包。

**验证。** P2 定向 79 passed、相邻 P2/Nav/P1.5 回归 152 passed；真实 291713 父包完成 8 Actor + 8 Critic + 1 Adapter update、保存与 exact resume，并在 1-env Track+Camera 走通 `goal_reached -> completed -> score=99.99`。128 环境平台结果未被夸大为已验证。

#### 案例 D：从二维导航策略迁移到三轴命令，而不把硬件 RNG 当成模型兼容性

**表象。** 初版将 `vy` 是否可探索绑定到 20/90 分钟的学习率课程；同时，父 checkpoint 保存的是 16-byte CUDA RNG state，而 CPU smoke 期望 5056-byte state，直接 `set_state()` 造成结构完全兼容的 warm start 被错误阻断。更严重的是 5 Hz cadence 的 `frame_count` 未保存，所谓 exact resume 会在恢复后重新对齐命令时钟。

**解决。** 将动作能力与 optimizer 课程拆开：从第一 rollout 即允许可信 `|vy|<=0.20`、探索 `|vy|<=0.40`，课程只调整新增 head 与共享网络的学习率/熵系数。二维 Actor 按 shape 迁移，新的 vy head 零初始化，Critic/value statistics 重建；RNG 同设备才 exact restore，跨设备明确降级为 `fresh_seed` 并写进 migration report，绝不伪造成 bit-exact；补充并校验 `frame_count`。

**价值。** 解决了“模型结构兼容性”“设备实现细节”“训练时钟一致性”三者被混为一谈的问题。真实 291713 包已完成张量/Adam 迁移、更新与 exact resume smoke；三轴平台长训须另行验收。

#### 案例 E：将视觉避障从中央 ROI 调参，升级为方向相关且 terminal-safe 的风险合同

**表象。** 旧碰撞风险只读中央前向深度 ROI，按 `vx` 处罚：会把坡面误作墙、无法支持横移/纯转向，并在高层 10 帧窗口中途 done 后读取 auto-reset 新 episode 的 telemetry。旧 collision onset 还被错误显示为整段累计。

**解决。** 将深度划分为三方向、三高度带，使用 q20、上下结构一致性、近距与 stopping gap 组合形成 wallness，再按 `[vx,vy,wz]` 所指方向加权。零命令、无效深度和远景严格零罚；真正 terminal 行在首次 done 前冻结 target/exec/反馈/aux，并从 terminal tracking 统计中剔除 reset 后数据。旧 gait 项改为诊断，不让高层 reward 暗中承担低层责任。

**价值。** 这是把感知特征、动作方向、终止时序和可解释监控统一成一个合同，而不是将“加一个障碍惩罚”当作解决方案。已有墙/坡/台阶/横移/纯转向/terminal-safe 的 114 项定向回归，仍待平台 smoke。

#### 案例 F：发现平台 `BaseEnv` create-once 语义后，主动撤回错误的域随机化方案

**表象。** 初始 P3 方案设想在 15/30 分钟通过 `env.reset(config)` 打开更强 friction、mass、noise 和 push。读取平台镜像后发现 `BaseEnv._create_env()` 在环境已存在时直接返回，reset 只会开始新 episode；另一个事实是 Go2 push 是 episode reset 重采样的 event，25 秒 episode 配 25-35 秒间隔几乎不会触发。

**处理。** 没有为了保留原计划去修改平台拥有的 `base_env.py` 或把配置值伪造成实测随机化，而是撤回阶段重建结论：首次 reset 就装配最终但保守的 DR，push 从进程启动使用可在 25 秒 episode 内发生的间隔；面板显式标记 `runtime_telemetry_available=0`，直到拿到真实 EventManager/PhysX 回传。

**价值。** 这体现的是实证式工程：平台源码否定原假设后修改方案和口径，而不是让训练计划看起来“功能完整”。

#### 案例 G：把“楼梯前视觉失效”建模成有记忆的连续过程，而不是随机加噪声

**表象。** 实机靠近楼梯时，距离小于约 0.25 m 的深度回波孔洞率可接近 80%；原 80-frame rollout、16-frame TBPTT 只有约 0.32 秒有效反传历史，无法让 LSTM 学会“远处看到楼梯，近处深度退化仍持续完成抬腿”。同时强平滑、接触/交叉/饥饿惩罚会抑制必要的快速摆腿，Hip/Thigh 又接近 22 Nm 安全线。

**解决。** 建立按环境独立 RNG 的近裁剪/稀疏/块状/severe/blackout 故障课程，且在完整 128-frame recurrent sequence 内固定空间掩码；使用冻结的 clean teacher，只向 LSTM、RNN output 与最终 action head 提供受限 memory auxiliary，CNN/高层不更新。力矩使用 soft-hard 区间的平方软约束，不硬裁剪楼梯短时发力；强步态项保持 shadow-only。之后又发现 severe 会在已有 80% 原始孔洞上叠加到 92%-96%，改为按有效像素预算“补足到目标 dropout”而非重复置零。

**验证边界。** 本地 378 passed/5 skipped 和真实 F2 bundle warm-start/freeze/train/save/exact-resume 通过；Isaac 动态 fault/push/DR 与平台训练仍待。可表述为“实现并本地验证”，不能表述为“已提升真机楼梯成功率”。

#### 案例 H：闭环复现“训练 sampled action 与部署 deterministic mean 不一致”的震荡根因

**表象。** 真机存在高频震荡，但训练只惩罚 sampled action，部署执行的是 deterministic policy mean；与此同时 action tensor 是 axis-major，而早期按 leg-major 解释，导致逐腿 torque、mirror 和 contact onset 统计错位。bucket zero/restart 语义和 anchor 权重也曾被旧路径反转或无条件置 1。

**解决。** 以 deterministic mean 计算 rate/jerk Huber 与软范围约束；加入独立命令 RNG 和 committed bucket transport；通过运行时 preflight 核验真正的 12 维 `JointPositionAction`、scale=0.25、PD/effort/contact mapping；按 `FL[0,4,8] / FR[1,5,9] / RL[2,6,10] / RR[3,7,11]` 修正镜像和触地映射。辅助梯度只进入可调整的 RNN/head，且相对 PPO policy gradient 设上限。

**价值。** 这个案例直接连接训练分布、模型输出语义、关节排列和真机震荡，是典型的 Sim2Real 跨栈问题。真实 884257 父包 warm-start、冻结/更新边界与 exact resume 已验证；真机对比仍待。

#### 案例 I：将 30 Hz 相机、50 Hz 控制和外力扰动变成可审计、fail-closed 的训练条件

**表象。** 低层控制为 50 Hz，而真实深度相机约 30 Hz，旧仿真把每个控制帧都当作新深度，完全没有覆盖重复帧和 40-150 ms 延迟；Push 面板只显示配置，不知道 EventManager 是否真的施加了扰动、幅度是多少、机器人是否恢复。

**解决。** P3.5 新增每环境随机 phase 的 30 Hz capture、50 Hz hold、10-frame FP16 FIFO 与分阶段 delay；使用公开 `get_term_cfg/set_term_cfg/reset` 对既有 EventManager term 安装透明 wrapper，记录实际 event/delta/age/active。任何 preflight、shape 或 finite 失败都将 telemetry 标为无效，并使 Push 条件奖励为零。为支撑该判断，将 training-only transport 从 431 扩到 493，加入 joint acceleration、contact force/onset/duration、mapping validity 和 Push telemetry；这些字段不改变 policy、ONNX 和部署 I/O。

**验证边界。** 417 passed/5 skipped 的本地回归覆盖 FIFO、delay、wrapper、delta、mapping、replay 和监控新鲜度；容器 Isaac、EventManager delta、平台 smoke 和真机验证均待。这一案例可写成“建立了可审计训练扰动与 fail-closed 遥测闭环”，不可写成“已验证外力鲁棒性提升”。

#### 案例 J：防止监控系统把不同生命周期的指标画在同一条“成功率”上

**表象。** 捕获到 866 个指标时，`p3_window_completed_count=0` 而平台 `completed_count>0`。如果直接据此判断训练回归，会误判：前者是 worker rollout reset reason，后者是 scorer lifetime 计数。类似地，部分 Push/DR 面板只是配置合同，部分高层面板在低层专项训练中没有接线却会显示空曲线。

**解决。** 将 worker rollout、平台 scorer、代理 M3、标准完成等口径拆开；为分桶指标补 attempt 分母与样本覆盖率；删除或标注未接线指标，限制每张 line panel 的复杂度；对 Push/DR 无实际回传时输出 unavailable/telemetry=0，而不是“默认 0”或配置范围。

**价值。** 这使监控从演示性 dashboard 变成实验结论的证据系统，直接避免了将平台重置、课程升级或空指标误读为策略能力变化。

## 7. 部署端原始材料

### 7.1 Jetson 运行链路

部署采用 C++17 + Unitree SDK2 DDS + ONNX Runtime + YAML + Eigen；深度输入来自 Intel RealSense D435i，策略步频为 50 Hz，FSM 以更高频率零阶保持下发关节命令。历史 `loco` 部署图有固定 batch 的 8 入 8 出兼容接口：

```text
Inputs:
  depth[1,180,320,1], proprio[1,45], goal[1,4]
  loco_h/loco_c[2,1,64], nav_h/nav_c[2,1,64], cmd_override[1,4]
Outputs:
  cmd[1,3], cmd_raw[1,3], clearance[1,3], joint[1,12]
  loco_h_out/loco_c_out, nav_h_out/nav_c_out
```

运行时每帧覆盖 `proprio[6:9]` 的真实执行命令，回灌 loco LSTM state，episode 开始清零。低层最终 target 接口规划为更清洁的 4 入/3 出图；为兼容现有 runner 的占位端口版本会显式标记，不能混称。

### 7.2 安全与可观测性

- 启动时校验所有 joint array 为 12 维，`joint_ids_map` 是 0..11 的排列；检查 Unitree lowcmd channel 未被占用并等待 lowstate。
- D435i 可用时使用真实深度；无相机时走 ConstantDepth fallback，仅用于诊断/bring-up，不伪装为视觉能力。
- 统一完成命令 finite check、max range、slew、UWB stale 处理和命令回读；D435i 深度经过 resize/clip/invalid encoding，目标为训练使用的 320x180 输入。
- 检查 ONNX 输出 joint/cmd/clearance 是否 finite/bounded；连续异常、策略 fault 或 bad orientation 都进入 Passive。
- UWB goal 具有滤波、跳变拒绝、freshness 与失效降级；UWB 停止平动、保留有限 yaw 的策略用于恢复通信，而不是把陈旧位置持续转换为前进命令。
- 记录诊断 CSV，包含深度有效率、goal/command、输出、反馈等字段，为训练 FeedbackEmulator 的分布拟合和影子模式提供数据来源。

### 7.3 部署制品状态

当前 `deploy/` 存在四套平行子树：`sim2real_test_loco`、`st9`、`st7`、`standard`。378413 checkpoint 已在 loco/st9 中入库；ST7/Standard 的 checkpoint 缺失，多个目录的 ONNX、C++ binary 和 ARM64 ONNX Runtime 也未入库。历史 Jetson 日志证明 Standard 路线曾运行，但当前并非可复现 release。P3 remote fixed-mode 分支另带独立 tar 包和 runtime 加固，也不能与默认路线混为一谈。

## 8. 工程化与可复现性材料

1. **checkpoint 血缘与一致性。** 保存父模型 ID、父 SHA、模块 digest、command/feedback contract digest；按照 schema、stage、module/spec/shape/finite 校验，而不是信任文件名或平台数字 ID。
2. **独立恢复语义。** 区分 `exact_resume`、`warm_start` 与 `weights_only`。对伴随低层发生变化的高层，默认重建 optimizer，不将面向旧动力学的 Adam momentum 当作可精确恢复状态。
3. **训练发布。** 识别到仅写运行目录 checkpoint 不会自动在开悟前端出现，修复为 iteration boundary 调用无参数 `agent.save_model()`，并验证模型 ZIP/id_list 发布链。
4. **真实训练容器诊断。** 用 local sync/RPC 在腾讯 IDE 容器中复核 preload、GPU、模型加载、环境 reset、rollout、optimizer step、保存与 resume；同步工具明确区分 `IDE_SYNC_TOKEN` 与腾讯 proxy Cookie，避免把浏览器登录态错误诊断为训练 token。
5. **平台源码证据纪律。** 对地形、课程、传感器、reset/score 行为使用本地容器源码镜像和必要时 RPC 在线复核；将“镜像历史证据”“当前容器证据”“训练侧 proxy”明确区分。
6. **监控体系。** 按 target/exec/true 命令、正负 `vy/wz`、赛段/难度、四足接触/滑移/腾空、Adapter MAE/NLL/AUROC、reward 分解、DR/push 是否真实生效分桶；将空面板、原始累计量与均值口径、reset 后误归因等问题作为一等工程缺陷处理。

### 9.1 一段式项目概述（约 220 字）

围绕 Unitree Go2 视觉 Sim2Real 控制，构建“50 Hz 低层步态控制 + 5 Hz 连续速度导航 + command-response 系统辨识”的分层强化学习路线。低层通过 depth 与本体感觉输出 12 维关节动作；高层不共享可变的低层 latent，而以独立视觉编码器、连续 `cmd3` 和带物理语义的 ResponseAdapter 适应低层能力边界与测量延迟。针对训练平台只能加载单 checkpoint 的限制，将解耦落实到模块、optimizer、RNG、contract digest 和恢复路径，支持低层扩域、Adapter 预热和高层 PPO 分阶段训练。已取得特权到视觉学生蒸馏平台证据及 Jetson/D435i/ONNX 控制 bring-up；连续高层与双 ONNX 接管仍按平台和真机验收推进。

### 9.2 可直接筛选的成果 bullet

- **两阶段视觉运动控制蒸馏。** 设计 `height_scan -> latent32 -> Actor77` 到 `depth -> latent32 -> Actor77` 的迁移链，在保持 Actor77 控制合同不变的前提下隔离网络结构变化与传感器迁移；R2 平台训练达到 6000 iter、1.47 亿环境步，坡/楼梯视频 4/4 完成、无 timeout/abnormal。`[平台训练与视频证据]`
- **单 checkpoint 下的分层异步训练。** 将高低层解耦从“两个文件”改为模块、梯度、训练状态与 command contract 的边界：同一个 schema2 bundle 分别保存 low/high/Adapter、optimizer、scheduler、RNG 和 digest；`resume_low` 可只实例化低层，导航训练则冻结低层执行器。`[代码、单测、容器 smoke；高层最终效果待平台验收]`
- **ResponseAdapter 与可演化低层接口。** 设计 `MLP + GRU` 响应辨识器，以 previous target、exec command、短时速度、IMU、freshness 与 capability 预测多时域速度/位姿、卡滞和不确定度；用固定物理语义替代共享 latent，使低层升级后可先 Adapter 校准、再决定是否高层 warm start。`[训练侧实现与容器 smoke；实机反馈分布待验收]`
- **从奖励曲线反推策略套利。** 发现绝对距离正奖励、静止 heading 奖励和过弱完成脉冲会让策略在终点附近保守徘徊；改为 transition 进度势函数、一次性 terminal 奖励、时间成本与低权重对称步态保护，避免把已有可用步态用强塑形破坏。`[P2 训练诊断与实现，最终性能待评估]`
- **面向真实传感器的反馈合同。** 将 UWB 的秒级延迟/噪声与即时速度 tracking 隔离：训练侧定义 SportMode 平动 + IMU yaw + `valid/age` 的短时反馈语义，UWB 仅作为低频全局/卡滞证据，并以 FeedbackEmulator 随机化延迟、噪声、丢帧与 hold。`[设计与训练侧实现；SportMode 真机质量待专门验证]`
- **视觉控制边缘端 bring-up。** 完成历史 Actor80 在 Jetson + D435i + ONNX Runtime + Unitree DDS 上的深度预处理、LSTM state 回灌、关节映射、输出检查与安全降级联调；固定 0.15 m/s 命令下确认正常行走，连续 200 帧 recurrent state 无非有限。`[真机现场证据；不等同于分层导航上线]`

### 9.3 面试重点：网络设计与训练解耦如何讲清楚

可以按下面的因果顺序展开，而不要只说“用了分层 RL”：

1. **为什么拆层。** 端到端 Track Actor 将导航误差直接投射成关节级动作，低层步态一旦已经可用，继续为导航探索而整体重训的风险很高；同时低层未来必须扩速度、修低速楼梯、改善 Sim2Real。
2. **网络如何拆。** 低层固定为 `depth + proprio45(exec_cmd3) -> LSTM/CNN -> joint12` 的 50 Hz 执行器；高层是独立 depth CNN + LSTM PPO，5 Hz 输出 `target_cmd3=[vx,vy,wz]`。中间经过 capability envelope 与 slew 形成真正输入低层的 `exec_cmd3`，因此高层知道“想要什么”，低层知道“实际收到了什么”。
3. **为什么不共享 latent。** 低层 CNN 会随指令扩域和步态修复更新；若高层读取它的 latent，低层一次升级会改变高层的坐标系。高层改用独立视觉编码器，并从 ResponseAdapter 获得有单位的多时域响应预测，而不是依赖不可解释的共享特征。
4. **如何分阶段训练。** P1.5 先让 Standard sampler 覆盖连续命令，低层 PPO 与 Adapter 用同一 rollout 但独立优化，学习“给定命令时低层实际上怎样走”；P2 冻结低层，令高层 PPO 只为导航回报探索；低层再升级后先校准 Adapter，响应变化较大时才 warm-start 高层。
5. **如何满足单包平台。** 一个 schema2 checkpoint 仅是容器，内部各模块、optimizer、RNG、digest 和恢复模式独立；这使上传/平台加载保持单包，而训练和后续导出保持模块化。训练包并不自动等于部署 release，双 ONNX 接管还必须通过时延和真机反馈验证。
