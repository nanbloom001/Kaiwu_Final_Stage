# P2 监控面板精简与方向速度统计优化方案

> 实施状态（2026-07-31）：**部分应用**。P3 已使用独立精简面板并保持每个 line
> 面板少于 20 个指标，保留了三轴 target/exec/measured/true、tracking、步态和 Adapter
> 核心链。本文规划的正负方向拆分、绝对幅值/p90、20 格精简为 6 项、60 秒
> GPU 张量窗口、单次 GPU→CPU 快照、5 分钟 terminal 桶及 monitor 自身耗时/载荷指标
> 尚未完整落地。P2 workflow 仍保留旧的过度展开桶指标和 Python 逐项 `float()`；
> P3 当前不生成 20 格桶，且低层恢复阶段的高层命令面板无数据属预期语义。

## 1. 背景与结论

本方案基于 `20260730-224125` 训练抓取。当前 P2 面板共采集约 809 条时序，
5×4 的 `target_vx × |target_wz|` 联合分桶成功暴露了全局均值无法显示的问题：

- `v0w3` 占比约 10.7%，进度仅约 `0.012m/s`，tracking MAE 约 `0.371`；
- `v1w3` 占比约 17.7%，进度约 `0.098m/s`；
- `v4w1` 占比约 8.2%，进度约 `0.894m/s`。

因此不删除联合分桶，但不再为每个桶长期上报十几个重复派生指标。
新方案的核心是：

1. 保留能回答训练决策问题的核心分桶。
2. 对 `vy/wz` 同时报告方向偏置、绝对强度和正负方向占比。
3. 将数百次 GPU 标量读取改为张量化窗口累积和一次性 CPU 传输。
4. 降低面板数量与时序数量，但不修改 reward、observation、action 或 checkpoint 合同。

## 2. 现有问题

### 2.1 有符号均值会抵消

左右转或左右横移可能同时很强，但 signed mean 接近零。signed mean 仍需保留，
因为它能检查长期方向偏置；但不得单独用于判断动作强度。

### 2.2 联合分桶指标过度展开

当前 20 个桶分别上报 count/share、progress、tracking、target/exec/true 三轴链、
gait、terminal outcome 和横移指标。其中存在：

- `gait_penalty` 当前为 monitor-only 且 PPO 权重为零；
- target/exec/true 三条线可用两个实现率代替；
- success/failure/timeout 非常稀疏，一分钟窗口容易全零；
- 桶由 `target_vx` 和 `|target_wz|` 定义，不区分左右方向，也不是完整三维分桶。

### 2.3 指标上报存在同步开销

桶内聚合本身使用 GPU `scatter_add_`，计算量不大。主要可优化边界是 rollout 结束时
在 Python 循环中对数百个 GPU 标量逐个 `float(...)`，以及每个 rollout 重复组装大量面板字段。
这些操作不改变梯度或 reward，但可能引入 GPU/CPU 同步和平台上报开销。

### 2.4 部分面板口径会误导

- `reward_mean/std` 等旧指标为空，不应继续作为主面板。
- `gait_symmetry` 为零是当前合同的 monitor-only 语义，不代表学会了步态。
- `curriculum_row_promotion/demotion` 在 `curriculum=false` 时也会因 reset 后出生 row 变化而累计，
  面板应改名为 spawn-row transition，不得解释为难度课程晋级。

## 3. 目标指标设计

### 3.1 方向速度面板

对 target/exec/measured/true 分别统计：

```text
vx:
  signed mean / p10 / p50 / p90
  reverse_share
  reverse_abs_mean

vy:
  signed_mean
  mean_abs / p90_abs
  positive / negative / zero share
  positive_mean / negative_abs_mean

wz:
  signed_mean
  mean_abs / p90_abs
  left / right / straight share
  left_mean / right_abs_mean
```

阈值固定为：

```text
vy zero: |vy| <= 0.05m/s
wz straight: |wz| <= 0.10rad/s
vx reverse: vx < -0.05m/s
```

误差同时保留：

```text
signed_error_mean   # 系统性高估/低估或方向偏置
MAE / RMSE          # 防止正负误差抵消
```

### 3.2 保留 5×4 核心联合分桶

分桶边界保持不变：

| 编号 | `target_vx` |
|---|---:|
| `v0` | `0–0.1` |
| `v1` | `0.1–0.4` |
| `v2` | `0.4–0.8` |
| `v3` | `0.8–1.0` |
| `v4` | `>1.0` |

| 编号 | `|target_wz|` |
|---|---:|
| `w0` | `0–0.1` |
| `w1` | `0.1–0.4` |
| `w2` | `0.4–0.8` |
| `w3` | `>0.8` |

每个桶的常驻指标精简为：

```text
sample_share
progress_mps
normalized_tracking_mae
vx_true_to_target_ratio
wz_true_to_target_ratio
vy_nonzero_share
```

约定：

- 实现率的分母过小时 mask，不用 epsilon 制造虚假大值。
- `wz` 实现率使用绝对幅值；左右均衡由方向速度面板负责。
- 桶样本数低于当前窗口总样本的 1% 时显式标记 low-sample，不用其判断能力。
- `vy` 仍作为桶内条件指标，不立即扩展成 5×4×N 三维桶。

### 3.3 低频结果指标

success/failure/timeout 不再每个 rollout 按 20 个桶上报，改为 5 分钟窗口：

```text
terminal_event_count
success_fraction
failure_fraction
timeout_fraction
```

这些结果只能表示 terminal tick 落入的命令桶，不宣称该桶是整个 episode 成败的单一因果。

### 3.4 安全、赛道和 Adapter

保留下列核心诊断：

- scanner available/well-formed/finite-hit；
- teacher/student left-center-right risk 和 safety BCE；
- safe alternative eligible share、selected-safest conditional rate、risk lead time；
- collision onset rate、body force、progress recovery latency；
- slope/stairs/maze sample share、progress、spin、creep、stuck 和 outcome；
- Adapter 三时域 MAE/NLL/sigma/coverage/confidence 及 Track/P1.5 record 比例。

删除空面板；monitor-only 指标在中文名称中显式加“诊断”，不使用 `reward_` 前缀。

## 4. 上报频率

| 类别 | 频率 |
|---|---:|
| PPO 有限值、loss、KL、显存和吞吐 | 每 rollout |
| reward decomposition 与全局 outcome | 60 秒窗口 |
| 方向速度与 20 格核心分桶 | 60 秒窗口 |
| 桶内 terminal outcome | 5 分钟窗口 |
| collision 原始 trace | 事件触发，每窗口最多 12 条 |
| 赛道出生 row/难度 column 直方图 | 初始化 + 2 分钟 |

## 5. 性能实现

### 5.1 GPU 聚合

将所有桶数据组织为连续张量：

```text
bin_sums   [20, K]
bin_counts [20]
direction_sums [chain, axis, statistic]
```

每个 high-level tick 只使用向量化 `scatter_add_`，不创建 Python 指标字典。
到达上报窗口后执行一次：

```text
snapshot = torch.cat(...).detach().float().cpu()
```

之后只在 CPU 上展开指标名称，禁止在双层桶循环中对 GPU tensor 逐项 `float()`。

### 5.2 窗口累积

- 常驻 GPU 累积器只保留 sum/count/max，不保留原始 rollout 样本。
- quantile 只对全局指令链使用现有预分配 buffer，不对 20 个桶分别保存原始样本。
- flush 后原地清零，不保留跨 checkpoint 的监控窗口。
- 监控不参与 reward、advantage、observation 或 action 计算图。

### 5.3 新增性能指标

```text
monitor_accumulate_time_s
monitor_flush_time_s
monitor_gpu_to_cpu_time_s
monitor_metric_count
monitor_payload_bytes
```

这些指标用于定量回答“面板是否影响训练速度”，不再仅根据总吞吐猜测。

## 6. 面板布局与规模

建议保留以下主组，任何 line 面板不超过 20 个指标：

1. 训练与资源健康。
2. episode outcome 和分段 outcome。
3. reward decomposition。
4. 三轴 target/exec/measured/true 方向平衡。
5. 三轴幅值、误差偏置和 MAE/RMSE。
6. 20 格分桶覆盖。
7. 20 格分桶进度。
8. 20 格分桶 tracking。
9. 20 格 `vx` 实现率。
10. 20 格 `wz` 实现率。
11. 20 格横向使用率。
12. 安全教师与 SafetyHead。
13. 碰撞预测和恢复因果链。
14. 三段赛道行为。
15. ResponseAdapter 质量与数据组成。

目标是将 P2 唯一时序数从当前约 809 降到 `<=600`，其中联合分桶常驻指标
不超过 120 条。该数值是监控工程目标，不是训练表现门禁。

## 7. 验证与验收

### 7.1 指标一致性

- 20 格 `sample_share` 之和在有效窗口内为 `1±1e-4`。
- positive/negative/zero 或 left/right/straight share 之和为 `1±1e-4`。
- 按桶 count 加权的 progress/tracking 与全局指标一致。
- reward decomposition 之和继续与 PPO storage reward 一致。
- terminal outcome 只使用 terminal-safe 快照，不读取 reset 后新 episode 数据。

### 7.2 别名与所有权回归

- fake env 复用同一 observation buffer 时，统计不被下一帧覆盖。
- 方向条件均值仅在对应有效样本上计算，空分母返回 invalid/NaN 并由面板屏蔽，
  不使用零冒充“表现良好”。
- terminal tick 的桶、命令和速度来自首次 done 快照。

### 7.3 性能 A/B

使用同一父 checkpoint、配置、seed 和 128 环境，分别运行旧/新监控至少 5 个完整 rollout：

```text
samples_per_s
rollout_time_s
env_step_time_s
actor/critic/adapter_update_time_s
monitor_accumulate/flush/gpu_to_cpu_time_s
GPU max allocated/reserved
learner CPU/RAM
```

验收目标：

- 新监控 `samples_per_s` 不低于旧版 98%；
- `monitor_flush_time_s` 的 p90 低于一个 rollout 时间的 1%；
- 面板指标不得增加长期 GPU 存储，不得创建第二份 depth 或 camera buffer；
- 任何吞吐改善不得来自降低环境数、相机分辨率、PPO epoch 或控制频率。

## 8. 实施顺序

1. 当前运行中的 `p2nav2hsafedir` 不修改，避免中途改变监控口径。
2. 先实现张量化窗口累积、单次 CPU 快照和新性能指标。
3. 再替换面板配置，删除空指标和重复派生曲线。
4. 运行单测、面板每行 `<=20` 指标校验、Python 编译、TOML 和 diff check。
5. 开发容器运行旧/新监控 A/B，再做 5 分钟平台 smoke。
6. 只在性能与口径验收通过后，将新面板用于下一轮正式训练。

## 9. 回滚

本方案不改变学习行为。实施后若出现指标错位、面板校验失败或吞吐回归，
回滚范围应限于 monitor accumulator、workflow metric expansion 和 `monitor_builder.py`，
不回滚 SafetyHead、reward-v9、PPO storage、三轴动作或 checkpoint 合同。
