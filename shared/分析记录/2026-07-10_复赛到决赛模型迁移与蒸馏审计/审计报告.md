## 2. 核心结论

当前迁移不能被理解成一次简单的“加载旧模型”。准确链路是：

```text
复赛 Standard flat ActorCritic
policy obs = proprio45 + height_scan256 = 301
actor      = 301 -> 512 -> 256 -> 128 -> 12
        |
        | 首层扩展 3 个 goal 输入 + PPO 微调
        | 不需要蒸馏
        v
复赛 Track flat ActorCritic
policy obs = proprio45 + height_scan256 + goal3 = 304
actor      = 304 -> 512 -> 256 -> 128 -> 12
        |
        | 行为/动作蒸馏，或按新架构重新 PPO
        v
决赛 Track ActorCriticEncoder Teacher
height_scan256 -> scan encoder -> latent32
actor input = proprio45 + latent32 + goal3 = 80
        |
        | LBC latent distillation
        v
决赛 Vision Student
depth57600 -> CNN -> 32
[CNN32 + proprio45] -> 2-layer LSTM64 -> latent32
[proprio45 + latent32 + goal3] -> teacher actor -> action12
```

结论边界如下：

1. `Standard -> 复赛 Track` 不需要蒸馏。两者隐藏层完全相同，只在 actor 和 critic 输入尾部增加 3 维目标特征。
2. `复赛 flat Track -> 决赛 Encoder Teacher` 不能直接加载。旧模型的 256 维 scan 与新模型的 32 维 latent 语义不同；若要保留 `42399` 的行为，推荐做行为蒸馏。
3. 第一段行为蒸馏不是规则强制的唯一解。也可以放弃旧权重，用新 `ActorCriticEncoder` 架构重新 PPO 训练。
4. `height_scan Teacher -> depth Student` 对当前官方部署路线基本是必需的，因为真机没有仿真特权 `height_scan`。
5. 当前仓库已有视觉训练产物，但还不能称为可直接上真机的最终模型。

## 3. 赛题与 Sim2Real 边界

赛题目标是让 Go2 在评测和真机阶段依靠自身观测自主从起点到终点，不是预先写死每一步动作。开发阶段需要编写训练、奖励、观测和部署程序，最终产物是实时输出 12 维关节动作的策略。

官方决赛路线的关键约束是：

- Stage 1 `locomotion`：使用 `height_scan` 特权观测训练 Encoder Teacher；
- Stage 2 `lbc_loco`：冻结教师，用深度图训练 CNN+LSTM Vision Student；
- 部署时没有 `height_scan`，只保留 `proprio + depth -> vision latent -> teacher actor`；
- checkpoint、`deploy.yaml`、相机参数和导出网络必须来自同一训练契约。

## 5. 复赛 Track 审计

### 5.1 网络并没有增加 RNN/LSTM

Track 仍使用与 Standard 相同的扁平前馈网络：

```text

critic     = 319 -> 512 -> 256 -> 128 -> 1
```

模型虽然保留了 `rnn_type`、`rnn_hidden_size`、`rnn_num_layers` 参数，但代码明确 `is_recurrent = False`。这些参数只是接口兼容脚手架，不代表复赛 Track 已经增加 LSTM。

### 5.2 Goal 特征

Track 新增的 `goal3` 实际语义是：

```text
[local_goal_x / 10, local_goal_y / 10, distance / 20]
```

前两维是机体坐标系下缩放后的局部位移，不是单位方向向量。特征会做截断；如果目标位置或机器人姿态获取失败，当前实现会静默返回全零。

证据见 [goal_features.py](../../代码存档/复赛_track/agent_ppo/feature/goal_features.py)。

### 5.3 Standard 到 Track 的正确迁移

Track loader 已实现面向输入扩维的部分加载：

1. shape 相同的参数完整复制；
2. `actor.0.weight` 复制原 `45+256=301` 列；
3. `critic.0.weight` 复制原 316 列；
4. 新增的 3 个 goal 列先清零；
5. 再通过 Track PPO 学习 goal 列和其他参数。

这段迁移不需要知识蒸馏。严格 `load_state_dict` 会因为首层 shape 不同而失败，但仓库的专用部分加载逻辑可以处理该差异。

证据见 [Track Agent 的部分加载实现](../../代码存档/复赛_track/agent_ppo/agent.py)，约第 181-207、259-303 行。

## 8. 为什么复赛 Track 不能直接加载到决赛 Teacher

### 8.1 Shape 不兼容

```text
复赛 Track actor.0.weight = [512, 304]
决赛 Track actor.0.weight = [512, 80]
```

### 8.2 更关键的是输入语义不兼容

```text
旧输入 0:45    = proprio
旧输入 45:301  = raw height_scan256
旧输入 301:304 = goal3

新输入 0:45    = proprio
新输入 45:77   = nonlinear encoded + L2-normalized latent32
新输入 77:80   = goal3
```

不能把旧首层的前 80 列直接复制到新首层，因为旧 `45:77` 是原始射线的前 32 个值，新 `45:77` 是编码后的 latent。两者维度碰巧都是 32，但没有相同语义。

当前通用 `_load_model_partial()` 按左上角切片复制，若用于这次迁移，会误把旧 scan 列当作新 latent/goal。这不是可接受的模型转换。

### 8.3 可以安全 warm-start 的部分

可以考虑以下显式映射，但它只能用于初始化，不能替代训练：

```text
old actor first layer proprio columns 0:45 -> new 0:45
old actor first layer goal columns 301:304 -> new 77:80
old actor later layers and biases -> same-shape new layers
old critic later layers -> optional warm start
```

必须重新学习：

- `encoder.*`；
- Actor 第一层 latent 列 `45:77`；
- Critic 第一层和 Critic Encoder；
- Vision CNN/LSTM。

## 9. 蒸馏必要性的准确边界

### 9.1 第一段：flat Track -> Encoder Teacher

如果目标是保留 `42399` 的既有 Track 行为，推荐行为蒸馏：

1. 冻结 flat Track teacher；
2. 让 `ActorCriticEncoder(goal3)` student 接收同一帧 `proprio+scan+goal`；
3. 以 teacher action 为监督，最小化 raw action MSE；
4. 先 teacher-drive 收集稳定轨迹，再切 student-drive 修复分布偏移；
5. 必要时再用 PPO 做小学习率闭环微调。

替代方案是使用新 Encoder 架构重新 PPO。这不需要第一段蒸馏，但意味着不再直接继承 `42399` 的导航能力和训练投入。

### 9.2 第二段：Encoder Teacher -> Vision Student

这一步是当前官方 Sim2Real 路线的核心：

1. Teacher 使用 `height_scan` 产生 latent；
2. Teacher Actor 驱动环境；
3. Student 使用 `depth+proprio` 产生 latent；
4. 以 latent MSE/cosine 为监督训练 VisionEncoder；
5. 评估时让 Student latent 驱动同一个 Teacher Actor；
6. 真机完全移除 `height_scan` 和 TeacherEncoder。

如果完全自研端到端视觉策略与部署 runtime，理论上可以不用 LBC；但那将脱离当前官方 exporter/runtime 主路径，需要承担更大的训练与部署验证成本。

## 10. 当前调用链和断点

当前默认调用链实际上是：

```text
algo_conf
-> Agent
-> Config.CURRENT = P22LBCLocoConfig
-> _init_lbc_loco()
-> 平台 preload
-> _load_lbc_loco()
-> lbc_workflow
-> model.ckpt-vision-*.pkl
```

行为蒸馏虽然有算法、workflow 和 TOML，但当前不能从入口稳定重跑：

- `conf.py` 没有 `StandardRefDistillConfig`、`TrackRefDistillConfig` 或 `P22RefDistillConfig`；
- 没有任何当前 StageConfig 设置 `algorithm = "behavior_distill"`；
- Agent 的 `_init_behavior_distill()` 依赖 `teacher_num_obs`、`teacher_num_critic_obs` 等当前配置中不存在的字段；
- 主 `train_workflow.py` 只检测 `is_lbc`，没有转发 `is_behavior_distill`；
- 仓库没有保存中间 `model.ckpt-p22-teacher-*`；
- 因此当前快照不能从 `42399` 完整重现 flat Track 到 Encoder Teacher 的桥接过程。

## 11. P0 阻断问题

### P0-1：教师加载必须 fail-fast

原始 `42399` 没有 `encoder.*`，LBC loader 会拒绝它。但 Agent 在所有候选都失败后只打印 warning，使随机 Teacher 和随机 Student 仍可能继续训练并生成格式正确的视觉 checkpoint。

必须改为：训练模式下没有兼容教师、shape 不匹配、key 缺失或 goal_dim 不一致时立即抛异常并停止任务。

### P0-2：补齐行为蒸馏入口和中间产物

需要补充 StageConfig、workflow dispatch、teacher 维度、checkpoint 命名、teacher hash、日志和 student-drive 评估。

### P0-3：先评估当前视觉 checkpoint，再决定续训

必须在相同种子和相同 Track 地形上比较：

```text
flat Track teacher 42399
vs. checkpoint 内 embedded Encoder Teacher
vs. Vision Student
```

如果 embedded Teacher 本身不能完成 Track，继续优化 Vision Student 没有意义。

### P0-4：修复 resume

checkpoint 内部为 `current_iteration=4999`，但当前 LBC workflow 每次都执行：

```text
for iteration in range(max_iterations):
    algorithm.current_iteration = iteration
```

学习率 scheduler 也重新创建。直接加载后运行会从 0 再跑 10000 iteration，并重启余弦学习率，而不是只跑剩余 5000。

需要恢复 scheduler state，或从 `current_iteration+1` 开始，并按全局 iteration 正确设置 scheduler 的 `last_epoch`。

### P0-5：确定最终部署契约

当前模型是 goal-conditioned actor80：

```text
proprio45 + latent32 + goal3 = 80
```

官方 stock loco exporter 是 actor77：

```text
proprio45 + latent32 = 77
```

官方 ONNX 输入中的 `goal[1,4]` 在 loco 图内只用于诊断，不参与 Actor。当前 checkpoint 因此不能直接交给 stock exporter。

必须在继续大规模训练前二选一：

| 路线 | 优点 | 代价 |
| --- | --- | --- |
| 保留 actor80 | 最大程度复用当前 Track 模型 | 必须修改 exporter、ONNX wrapper、Jetson runtime，并在真机实时生成与训练完全相同的 goal3 |
| 回到 actor77 + 高层导航 | 更接近官方部署契约，运控与导航职责更清晰 | 需要训练独立导航/UWB 命令层，并重新训练或适配当前模型 |

两种契约不能在训练完成后再临时混用。

### P0-6：修复 Student-drive 单帧双前向

当前 `_lbc_step()` 在 `student_drive=true` 时，先通过 `act_student(obs)` 推进一次 VisionEncoder/LSTM 并生成动作，随后又对同一帧调用 `compute_latent_loss(obs)`，第二次推进同一个 LSTM 状态。环境只前进一步，`h/c` 却前进两次，因此当前路径不等价于真机 50Hz 推理。

必须让动作与指标复用同一次视觉前向，或在第二次指标计算时保存/恢复 hidden state。修复前不能把当前 student-drive 结果作为可信闭环基线。

## 12. P1 工程风险

### P1-1：真机 goal3 尚未实现

训练侧 goal3 依赖仿真 `goal_positions`、机器人世界坐标和朝向。仓库没有将 UWB、定位或导航目标转换为同一 `[local_x/10, local_y/10, distance/20]` 的真机 adapter。

### P1-2：命令分布没有对齐

复赛/bridge 使用 terrain gate 和 phase gate 改写速度命令；当前 LBC 阶段不调用同一 gate，只在 TOML 中采样 `vx=0.55~0.80`；官方真机示例的速度又更低。Teacher、Student 和真机看到的状态访问分布必须统一或覆盖式随机化，并通过闭环指标验证。

### P1-3：部署材料缺失

当前修改目录只有训练侧 `deploy.yaml`，缺少：

- `export_loco_onnx.py` 或等价 exporter；
- `export_vision_nav_onnx.py`；
- `policy.onnx`；
- Jetson C++ runtime；
- 真机 `config.yaml`；
- 相机标定和深度重投影产物；
- PyTorch wrapper/ONNX 多帧数值对拍；
- Jetson 延迟记录；
- 仿真闭环、真机日志和视频。

### P1-4：阶段自动推断存在断点

`Config.load_conf()` 推断出 eval stage 后只修改局部变量，没有回写 `Config.CURRENT`。`base_env.py` 的注释和调用又引用不存在的 `_infer_stage_for_eval`，实际函数名是 `_infer_stage_from_task_name`。当前硬编码 P22 恰好遮住了问题，切换其他阶段时可能失败。

### P1-5：训练侧 deploy.yaml 不是已验证的真机契约

当前 `custom_obs.scale` 对应 57904 维训练观测，更像平台训练侧自动导出；它不等价于官方真机 runtime 需要的精简 `proprio_scales`、`proprio_clip`、`cmd_ranges` 等配置。

### P1-6：评估增强、无效深度和部署状态 reset 尚未闭环

- 视觉增强使用 `getattr(env, "_is_training", True)`，仓库没有明确在评估时设置为 `False`；外部运行时若不覆盖，评估仍会随机 dropout、加噪和抖动；
- 当前仿真预处理没有显式使用 `torch.isfinite` 清理 NaN，与部署目标协议仍有缺口；
- Python workflow 只证明 episode done 后会清零 LSTM，仓库没有 Jetson runtime，无法证明急停、断流、控制器重启和 FSM 状态切换时会清零 `loco_h/c`。

## 17. 最终判断

当前项目不是“什么都没做”，而是已经完成了复赛 Standard、复赛 Track、决赛视觉训练主体和一个约半程的视觉 checkpoint。真正的问题集中在四个闭环缺口：

1. flat Track 到 Encoder Teacher 的迁移链不能从当前快照复现；
2. 现有视觉 checkpoint 的教师来源和闭环性能没有证据；
3. 当前 actor80 与官方 actor77 部署契约不一致；
4. exporter、ONNX、Jetson runtime、相机标定和真机安全验证尚未完成。

因此下一步不应直接把 `42399` 塞进决赛网络，也不应盲目把 `vision-162404` 再跑若干轮。正确顺序是：先建立同场景基线并验证当前 checkpoint，再恢复行为蒸馏和中间教师血缘，随后确定 actor80/actor77 部署契约，修复 LBC resume，最后完成导出、数值对拍和分级真机测试。
