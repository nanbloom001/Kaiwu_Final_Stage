# 迁移路线评估与训练代码质量审查

本文回答三个实际决策问题：

1. 当前“复赛 Track -> Encoder Teacher -> 深度视觉 Student”的路线是不是最合适；
2. 是否有更能保留复赛 `42399` 能力的路线，还是应该从头训练；
3. `代码存档/决赛_track蒸馏_162404` 是否已经足够支撑下一轮正式训练。

审查日期：2026-07-10。本文是代码、配置和 checkpoint 的静态审查，不是仿真成绩报告。本机没有 PyTorch、Isaac Lab、开悟运行时和 Jetson 部署环境，因此没有执行真实前向、仿真回放或 ONNX 数值对拍。

## 1. 先给结论

### 1.1 当前路线在方向上是对的，但只能算“有条件的首选”

如果复赛 `42399` 确实是目前完成率最高、最稳定的 Track 模型，而且团队愿意维护自定义的 Actor80 导出和真机 goal3 输入，那么最值得推进的主线是：

```text
flat Track 42399
-> 行为蒸馏到 ActorCriticEncoder Track Teacher
-> 小学习率 PPO / student-drive 数据修正
-> depth VisionEncoder 的 LBC 蒸馏
-> student-drive 闭环评估
-> 自定义 Actor80 ONNX 与真机 runtime
```

这条路线比“完全从头训练 Encoder Teacher”更能保留复赛已经投入的训练成果，也比直接用高维 depth 从头跑 PPO 更稳定。

但它不是无条件最优，原因是当前最终 Actor 输入为：

```text
proprio45 + latent32 + goal3 = 80
```

官方现成 `deploy_loco` 的 Actor 是 77 维，ONNX 中的 `goal[1,4]` 在 loco 图内只用于诊断，不会自动变成这里的 goal3。Actor80 必须补自定义 exporter、ONNX 输入、C++ runtime 和真实定位/UWB 到 goal3 的适配器。证据见 [部署指南](../../规则说明/开发指南/部署指南.md)。

### 1.2 不建议现在直接放弃 `42399` 从头训练

当前没有证据说明 `42399` 已经失效，也没有一个闭环合格的新 Encoder Teacher 可以替代它。此时直接从头 PPO 会主动放弃已有导航能力，并重新承担复杂 Track 奖励、课程、地形门控和探索的成本。

更合理的做法是保留两条分支：

- 主分支：增强版行为蒸馏，尽量继承 `42399`；
- 对照分支：从头训练或 warm-start 的 Encoder PPO，用同一批固定种子比较。

只有在 `42399` 同场景基线本身不合格，或修复后的行为蒸馏仍无法达到闭环门槛时，才把从头训练提升为主线。

### 1.3 当前训练代码还不够好，不能直接开始下一轮正式长训

当前目录已经具备正确的主体概念：

- `ActorCriticEncoder`；
- flat Teacher 到 Encoder Student 的 action MSE 算法草稿；
- `VisionEncoder = SimpleCNN + 2 层 LSTM + 32 维 latent`；
- 冻结 Teacher、只训练 VisionEncoder 的 LBC；
- 一个结构完整的 `model.ckpt-vision-162404.pkl`。

但代码尚未形成可信的端到端训练和部署闭环。至少存在以下 P0 阻断项：

- 行为蒸馏没有 StageConfig，主 workflow 也没有分发入口；
- LBC Teacher 加载失败只 warning，可能围绕随机 Teacher 继续训练；
- `student_drive=true` 时同一帧让 LSTM 前向两次；
- 平台 eval 没有可验证的 episode 级 LSTM reset；
- actor80 的真实 goal3、exporter、ONNX 和 C++ runtime 均不存在于仓库；
- 当前视觉 checkpoint 没有 Teacher 来源 hash、训练曲线和闭环成绩；
- LBC resume 会重置 iteration 语义和 cosine scheduler；
- eval 可能仍随机做图像增强，深度输入也没有 NaN/Inf 清理。

所以当前状态应定义为“研究原型 + 半程 checkpoint”，不能定义为“可复现训练代码”或“可部署策略”。

## 2. 当前真实的数据流和模型差异

### 2.1 复赛 Track

```text
obs304 = proprio45 + raw height_scan256 + goal3
Actor: 304 -> 512 -> 256 -> 128 -> 12
```

goal3 是：

```text
[local_goal_x / 10, local_goal_y / 10, distance / 20]
```

代码证据：

- [复赛 Track Agent](../../代码存档/复赛_track/agent_ppo/agent.py)
- [复赛 Track ActorCritic](../../代码存档/复赛_track/agent_ppo/model/actor_critic.py)
- [复赛 Track goal3](../../代码存档/复赛_track/agent_ppo/feature/goal_features.py)

### 2.2 当前决赛 Encoder Teacher

```text
height_scan256
-> Encoder: 256 -> 512 -> 256 -> 32 -> L2Norm

proprio45 + latent32 + goal3
-> Actor: 80 -> 512 -> 256 -> 128 -> 12
```

代码证据见 [actor_critic_encoder.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/model/actor_critic_encoder.py)。

### 2.3 当前决赛视觉 Student

```text
depth[180,320,1]
-> SimpleCNN -> image_feature32

image_feature32 + proprio45
-> 2-layer LSTM(hidden=64)
-> Linear 64->32
-> L2Norm student_latent32

proprio45 + student_latent32 + goal3
-> frozen Teacher Actor80
-> action12
```

代码证据见 [vision_encoder.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/model/vision_encoder.py) 和 [algorithm_lbc.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/algorithm/algorithm_lbc.py)。

### 2.4 为什么不能只改输入层或裁剪权重

旧 Actor 首层权重是 `[512,304]`：

```text
0:45    proprio
45:301  raw scan256
301:304 goal3
```

新 Actor 首层权重是 `[512,80]`：

```text
0:45   proprio
45:77  nonlinear latent32
77:80  goal3
```

旧 `45:301` 的含义是 256 个原始扫描值，新 `45:77` 的含义是经过三层 Encoder 和 L2Norm 后的 32 维特征。即使 shape 可以人为裁剪，语义也完全不同。把旧扫描权重前 32 列塞给新 latent，相当于错误地假设“第 1 至 32 条射线就是 latent 第 1 至 32 维”。

## 3. 哪些旧权重可以复用

如果新 Actor 仍使用 `[512,256,128]` 隐层和 12 维动作，可以安全或相对安全地做以下 warm-start：

| 旧权重 | 新位置 | 建议 |
|---|---|---|
| `actor.2.weight/bias` | 新 Actor 第二个 Linear | 可完整复制 |
| `actor.4.weight/bias` | 新 Actor 第三个 Linear | 可完整复制 |
| `actor.6.weight/bias` | 新 Actor 输出层 | 可完整复制 |
| `actor.0.bias` | 新 Actor 首层 bias | 可作为初始化 |
| `actor.0.weight[:,0:45]` | 新首层 proprio 列 `[:,0:45]` | 可复制 |
| `actor.0.weight[:,301:304]` | Actor80 goal 列 `[:,77:80]` | 可按语义重映射 |
| `std/log_std` | 新 PPO 探索尺度 | 仅作 PPO 初始化，不进入部署 |

以下内容不能直接复用：

- 旧 raw scan 列不能变成新 latent 列；
- 旧 checkpoint 没有 `encoder.*`；
- 旧 checkpoint 没有 Vision CNN、LSTM 和视觉 head；
- Critic 首层 shape 和特征分布都变化了；
- 行为蒸馏只训练 Actor 路径，未参与 action loss 的新 Critic 仍是随机状态。

旧 `actor.0.weight[:,45:301]` 恰好也是 `[512,256]`，与新 Encoder 第一层 shape 相同，但不代表它们语义相同。旧网络在同一个线性和 ELU 之前已经混合 proprio、scan 和 goal；新 Encoder 只处理 scan，并且后面还有额外非线性和单位球约束。最多把它当实验性初始化，不能当等价迁移。

## 4. 六条迁移路线比较

下表是基于当前仓库和工程风险的先验评分，不是实测比赛分数。每项 1 至 5 分，越高越有利。

| 路线 | 保留 42399 行为 | 训练稳定性 | 样本/算力效率 | 官方工具兼容 | Sim2Real 可控性 | 建议 |
|---|---:|---:|---:|---:|---:|---|
| A. Encoder Teacher 从头 PPO，再 LBC | 1 | 3 | 2 | 4 | 4 | 可靠兜底，不作当前首选 |
| B. 语义化 warm-start，PPO，再 LBC | 3 | 3 | 3 | 4 | 4 | 快速基线 |
| C. flat->Encoder 行为蒸馏，PPO 修正，再 LBC | 5 | 4 | 4 | 4 | 4 | 当前主线 |
| D. depth->pseudo-scan256，冻结旧 flat Actor | 4 | 3 | 4 | 1 | 2 | 诊断或辅助任务 |
| E. flat Teacher->端到端视觉动作蒸馏 | 4 | 3 | 4 | 2 | 3 | 一段式备选 |
| F. depth->旧 Actor 第一隐藏层 h1(512) | 5 | 3 | 4 | 1 | 3 | 强对照实验 |

“官方工具兼容”这里还要再区分一次：latent32 的模型结构更接近官方 LBC，但当前 goal3 使 Actor 成为 80 维，所以它仍不能原样使用官方 actor77 部署图。

### 4.1 路线 A：从头 PPO

```text
ActorCriticEncoder(goal3) 从随机初始化开始 PPO
-> 得到闭环 Encoder Teacher
-> LBC
```

优点是血缘最清楚，训练产物天然有 `encoder.* + actor.*`。缺点是基本放弃 `42399` 的成熟 Track 行为，而且 Track PPO 奖励和探索比监督蒸馏更难稳定。

适用条件：

- `42399` 在统一环境复测后本身不合格；
- 行为蒸馏在修复后仍无法达到闭环门槛；
- 有足够平台预算并需要一条完全可复现的独立基线。

### 4.2 路线 B：部分 warm-start + PPO

先按第 3 节复制可复用权重，再用 PPO 重新协调随机 Encoder、新 latent 列和 Critic。它通常比完全从头快，但初始函数并不等价于旧模型，所以不能跳过闭环验证。

建议把它作为“快速 Encoder Teacher 基线”，而不是声称它已经迁移了 `42399`。

### 4.3 路线 C：增强版两段蒸馏

这是本文首选：

```text
第一段：行为迁移
flat 42399(obs304) -> teacher_action12
Encoder Student(obs304) -> student_action12
loss_behavior = MSE(student_action, teacher_action)

第二段：视觉迁移
Encoder Teacher(scan256) -> teacher_latent32
Vision Student(depth, proprio) -> student_latent32
loss_lbc = latent_loss + lambda * action_consistency_loss
```

建议不要只做当前的纯 action MSE 和纯 latent MSE，而是增加三个稳定化步骤：

1. 行为 Student 先在 Teacher 轨迹上学习，再切到 Student 访问状态上继续由 Teacher 标注，降低分布偏移；
2. 行为蒸馏后做短程、小学习率 PPO，让新 Encoder 策略修正闭环误差；
3. LBC 在 latent loss 外加入 action consistency：比较同一冻结 Actor 在 Teacher latent 和 Student latent 下的动作。

这一方案的优点是每一阶段都可单独验收，失败时能判断是行为迁移失败，还是深度感知失败。

### 4.4 路线 D：预测 pseudo-scan256

```text
depth + proprio history
-> CNN/LSTM
-> predicted height_scan256
-> 原 flat 42399 Actor304
```

它可以完整冻结旧 Actor，也能把预测结果画回 16x16 检查。但深度相机看不到所有 RayCaster 格点：脚下、遮挡后方和从未进入视野的区域可能不可恢复。只优化 256 维 scan MSE 还会浪费容量拟合对动作无关的格点。

更合适的用途是辅助任务：

```text
主损失：latent/action distillation
辅助损失：可见格点 masked scan reconstruction
```

不建议把 pseudo-scan 作为唯一决赛主线。

### 4.5 路线 E：直接视觉动作蒸馏

```text
flat 42399(scan, proprio, goal) -> teacher_action
depth Student(depth, proprio, goal) -> student_action
```

它省掉中间 Encoder Teacher，减少一段近似误差；但失去官方 latent 接口和现成 checkpoint 契约，问题也更难定位。若使用，必须采用 Student-drive/DAgger 式状态收集，并维护自定义 exporter。

### 4.6 路线 F：蒸馏旧 Actor 第一隐藏层 h1

旧策略的第一层输出为：

```text
h1 = ELU(Linear304->512([proprio, scan, goal]))
```

可以训练视觉网络直接预测 `h1_hat512`，然后原样冻结复用旧 Actor 后三层：

```text
depth + proprio + goal -> CNN/LSTM -> h1_hat512
h1_hat512 -> old actor.2 -> actor.4 -> actor.6 -> action12
```

推荐损失：

```text
loss = normalized_hidden_loss + lambda * action_loss
```

这条路线只做一次感知替换，理论行为上限很高，是最值得和路线 C 做同种子对照的替代方案。但 h1 混合了 scan、proprio、goal，部分通道可能不可由相机稳定恢复；同时它完全不兼容现有 latent32 exporter，需要自定义 checkpoint 和部署图。

## 5. 推荐的最终执行路线

### 阶段 0：先固定部署契约

必须先选择以下之一：

| 方案 | Actor 输入 | 优点 | 代价 |
|---|---:|---|---|
| 自定义端到端 Track | 80 = proprio45 + latent32 + goal3 | 最大程度保留 `42399` 导航行为 | 自定义 exporter/runtime/goal3/安全处理 |
| 官方 loco + 独立高层导航 | 77 = proprio45 + latent32 | 最接近 stock 部署包 | 需要另做 UWB/depth 到速度命令的导航层，不能直接继承旧 Track Actor |

如果目标是“尽量把复赛强 Track 模型迁移过来”，应选 Actor80，并正视其部署工作量。若团队没有修改 ONNX/C++ 的时间和能力，则应尽早转为 actor77 分层方案，不要训练结束后才发现部署契约不匹配。

### 阶段 1：建立三个固定种子基线

在完全相同的 Track 地形、命令、噪声、终止条件和种子下分别评估：

1. flat Track `42399`；
2. `vision-162404` 内嵌的 Encoder Teacher；
3. `vision-162404` 的 Vision Student。

至少记录：

- 完成率；
- 摔倒率和超时率；
- 完成用时；
- roll/pitch；
- 能耗；
- 每种子地形的失败位置；
- Teacher/Student action MSE；
- latent cosine、夹角和距离。

如果内嵌 Encoder Teacher 已经接近 `42399`，不必为了形式整洁盲目重跑全部行为迁移；先补血缘和评估，再决定是否重训。

### 阶段 2：修复行为蒸馏入口和血缘

需要完成：

1. 新增 Track behavior-distill StageConfig；
2. 明确 `teacher_num_obs=304`、`teacher_num_critic_obs=319`、`num_goal_obs=3`；
3. 在主 workflow 中分发 `behavior_distill_workflow`；
4. Teacher load 失败立即退出；
5. 保存 Teacher 文件名、SHA-256、配置快照和代码版本；
6. 保存中间 Encoder Teacher checkpoint，不再只保留视觉最终产物；
7. checkpoint 同时保存 optimizer、iteration 和必要的恢复状态；
8. 增加 held-out seeds 和 Student-drive 的闭环报告。

### 阶段 3：增强版行为迁移

建议顺序：

```text
语义化 warm-start
-> Teacher-drive action distillation
-> 混合 Teacher/Student drive，继续用 Teacher 标注
-> 小学习率 PPO 闭环修正
-> 固定种子对比 42399
```

行为蒸馏阶段可采用以下工程门槛：

| 指标 | 建议门槛 |
|---|---:|
| held-out raw action MSE | `<= 1e-3` |
| action cosine | `>= 0.99` |
| Encoder Teacher 完成率相对 `42399` | 下降不超过 5 个百分点 |
| 摔倒率 | 不高于 `42399` 2 个百分点以上 |

阈值是工程建议，不是比赛官方评分线。闭环成绩优先级高于 action MSE；一个 action MSE 很低但会在关键楼梯口摔倒的模型不能放行。

### 阶段 4：视觉 LBC

冻结已经验收的 Encoder Teacher，只训练 VisionEncoder。建议把“驱动来源”和“是否更新参数”拆成两个开关：

```text
drive_source = teacher | mixed | student
update_student = true | false
```

当前 `student_drive=true` 被实现成纯评估，不能在 Student 访问状态上继续学习。更稳的路线是：先 Teacher-drive 训练，再在 Student-drive 状态上继续使用同步的 height_scan 生成 Teacher latent 监督。

建议损失：

```text
L = latent_distance
  + lambda_action * MSE(
        Actor(proprio, student_latent, goal),
        Actor(proprio, teacher_latent, goal)
    )
```

不要先扩大网络。当前 SimpleCNN、2 层 64 隐状态 LSTM 和 latent32 足够作为第一条基线。只有在数据表明容量不足后再改：

- 训练集和验证集 loss 都高：先检查输入对齐、相机视角，再考虑 CNN 容量；
- 训练 loss 低而验证/闭环差：优先处理增强、域随机化和分布偏移；
- latent 对齐好但动作差：检查 Teacher Actor、goal3、命令分布和 LSTM 状态；
- Encoder Teacher 本身差：不要继续优化 Vision Student。

### 阶段 5：部署闭环

Actor80 至少需要：

1. 真实相机内外参和设备序列号；
2. 真机内参到训练相机视角的逐像素重投影，不能只 resize；
3. NaN/Inf、零深度、超量程和断帧处理；
4. `depth[1,180,320,1] + proprio[1,45] + goal3[1,3] + h/c` 的 ONNX 契约；
5. UWB/定位姿态到 `local_x/10, local_y/10, distance/20` 的同义实现；
6. goal 数据超时、定位丢失、相机断流时进入安全状态；
7. Passive、FixStand、VisionLoco、急停、重启和 episode 边界的 LSTM reset；
8. PyTorch -> wrapper -> ONNX -> Jetson 连续多帧数值对拍；
9. 与 checkpoint 同源的精简 `deploy.yaml`。

## 6. 当前代码质量审查

### 6.1 已经做对的部分

- Teacher Encoder 和 Teacher Actor 会被冻结；
- LBC optimizer 只包含 VisionEncoder；
- Teacher/Student 都输出 32 维 L2-normalized latent；
- policy obs 的 proprio、scan、goal、depth 切分方向正确；
- Vision checkpoint 保存了 Student、Teacher、optimizer、iteration 和 total_steps；
- 训练 workflow 在 `terminated|truncated` 后会按环境 reset LSTM；
- 128 个 Camera 环境低于规则建议的 256 上限，显存配置合理；
- 51 个 Python 文件和 10 个 TOML 文件均通过静态语法解析。

这些说明代码不是空壳，但“核心类写出来”与“训练闭环可信”是两件不同的事。

### 6.2 P0：正式训练前必须修复

#### P0-1：LBC Teacher 必须 fail-fast

[agent.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/agent.py) 在没有找到兼容 Teacher 后只打印 warning，Teacher 和 Student 保持初始化状态。由于 LBC loss 只要求两侧 shape 一致，即使 Teacher 是随机的，训练也能下降并保存格式正确的 checkpoint。

当前 [configure_app.toml](../../代码存档/决赛_track蒸馏_162404/conf/configure_app.toml) 使用 `preload_model_id=42399`。这里存在一个不能忽略的歧义：

- 如果平台注入的是原始 flat `model.ckpt-42399.pkl`，它没有 `encoder.*`，LBC loader 必然拒绝；
- 如果平台注入的是之前行为蒸馏后故意沿用 42399 编号的 Encoder Teacher，它可以加载；
- 仓库没有保存该中间 Teacher、来源 hash 或日志，因此无法判断当时是哪一种。

对 `vision-162404` 二进制的进一步检查表明，其内嵌 Teacher 权重明显超出了当前 `nn.Linear` 随机初始化范围，例如 Teacher Actor 首层绝对值最大约为 `1.13`，而 `fan_in=80` 的默认初始化界约为 `0.112`；Teacher Encoder 第一层绝对值最大约为 `0.270`，也高于 `fan_in=256` 的约 `0.0625`。这说明这一个 checkpoint 在当时很可能确实加载了某个训练过的 Encoder Teacher，而不是把当前随机初始化 Teacher 原样冻住。

但这仍不能证明该 Teacher 来自原始 `42399`，也不能证明其 Track 性能合格。正确结论是：“现有 checkpoint 内嵌了已训练形态的 Teacher，但来源和成绩不可追溯；当前代码仍允许未来训练在加载失败后继续。”

必须保存 Teacher SHA-256，并在 LBC 启动前检查：`encoder.*`、`actor.*`、goal_dim、首层 shape、所有参数 finite，任一不符立即退出。

#### P0-2：行为蒸馏没有真正接入主线

虽然存在 [algorithm_behavior_distill.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/algorithm/algorithm_behavior_distill.py)、[behavior_distill_workflow.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/workflow/behavior_distill_workflow.py) 和三份 TOML，但当前 `conf.py` 没有 `algorithm="behavior_distill"` 的 StageConfig，`train_workflow.py` 也只分发 LBC。

按当前存档不能从原始 `42399` 稳定重跑并产出 Encoder Teacher。

#### P0-3：Student-drive 每帧推进两次 LSTM

当前 `_lbc_step()` 先通过 `act_student(obs)` 生成动作，又对同一帧调用 `compute_latent_loss(obs)` 计算指标。两个函数都会前向同一个有状态 VisionEncoder。

结果是：

```text
环境时间前进 1 帧
LSTM hidden state 前进 2 次
```

必须让动作和指标复用同一次 student latent。验收测试应证明 1000 次 env step 恰好发生 1000 次 VisionEncoder forward。

#### P0-4：平台 eval 和真机 FSM 的 LSTM reset 未闭环

eval 载入时只初始化一次 hidden state，逐帧 `_exploit_lbc_loco()` 没有 done mask。需要明确 episode reset API；真机还要在急停、相机断流、控制器重启和模式切换时清零 h/c。

#### P0-5：actor80 和 goal3 没有部署实现

[goal_features.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/feature/goal_features.py) 在 goal 或机器人姿态缺失时静默返回零。训练时这可能掩盖输入故障，真机时则可能让机器人在无有效目标的情况下继续走。

必须改为 fail-fast 或进入安全状态，并实现真实定位链。当前仓库没有 exporter、`.onnx`、`.cpp` 或 `.hpp` 文件。

#### P0-6：没有闭环性能证据

`model.ckpt-vision-162404.pkl` 结构信息为：

| 字段 | 值 |
|---|---|
| format | `lbc_loco` |
| goal_dim | 3 |
| Teacher Actor 首层 | `[512,80]` |
| current_iteration | 4999 |
| total_steps | 120000 |
| optimizer 当前 LR | `0.000255` |
| 当前配置计划 | `10000 x 24 = 240000` updates |

optimizer 当前 LR 恰好接近 `5e-4 -> 1e-5` 的 10000-step cosine 在中点的值，与 `current_iteration=4999` 相互印证。它大约处于当前计划的一半，但仓库没有 loss 曲线、完成率或失败录像。结构完整只能说明“文件可解析”，不能说明 Teacher 合格、Student 收敛或真机可用。

本轮对本地文件计算的 SHA-256 如下，便于以后判断文件是否发生变化：

| 本地 checkpoint | SHA-256 |
|---|---|
| `复赛_standard/model.ckpt-10288.pkl` | `d5999461f00c4634bdea0648e46baac9fba34e621eaa586fe26f64f68953eeed` |
| `复赛_track/model.ckpt-42399.pkl` | `9ff6e67ec0146183d83a421926d76c1d3eb1db85b1bf627761dbd888f3acd818` |
| `决赛_track蒸馏_162404/model.ckpt-vision-162404.pkl` | `9227834c014d7ff1ee5904853a30178b150657f12988401855253b144da0c5b6` |

这些是当前工作区内 `.pkl` 文件的 hash，不是 `kaiwu.json` 中整包 zip 的 `model_file_hash`，两者不能混用。

#### P0-7：当前半程 checkpoint 不能按“剩余 5000 iteration”直接续训

checkpoint 会恢复 optimizer、`current_iteration` 和 `total_steps`，但 workflow 随后仍从 `range(max_iterations)` 的 0 开始，覆盖恢复的 iteration，并重建新的 cosine scheduler。optimizer state 不匹配时还会被静默忽略。

因此，直接预载 `vision-162404` 会重新跑一套新的迭代编号和学习率曲线，而不是从中点连续走完后半程。对于当前最可能的下一步，这属于阻断项。必须保存/恢复 scheduler state 和全局 iteration，或者明确把操作定义为“仅权重 warm-start”，重新设计训练长度与学习率。

### 6.3 P1：影响可信度和可复现性

#### P1-1：eval 可能仍在随机增强

[nav_observation_utils.py](../../代码存档/决赛_track蒸馏_162404/agent_ppo/feature/nav_observation_utils.py) 使用：

```python
training = getattr(env, "_is_training", True)
```

仓库环境明确设置的是 `_is_eval`，没有清楚设置 `_is_training=False`。因此 eval 很可能仍随机 dropout、加噪、roll 和 pitch 抖动。同一原始帧连续处理 100 次必须逐元素一致，才能证明评估确定。

#### P1-2：深度没有 finite 清洗

`torch.clamp` 不会把 NaN 变成有效值。必须把 `NaN/Inf/<=0/>=max_depth` 统一映射为无效值 0，并在进入 CNN 前断言所有值 finite 且在 `[0,1]`。

#### P1-3：命令和状态分布没有对齐证明

behavior-distill TOML 使用 terrain-phase 命令改写；相应 gate 会改写 `proprio[6:9]` 和环境 command，并将 `vy/yaw` 置零。当前 LBC TOML 没有同一段 `rl_navigation` 配置，只设置 `vx=0.55~0.80` 范围并关闭 navigation，而且 `LBCObservationProcess` 只拼 goal 和 depth，不调用 terrain gate。Teacher 行为迁移、LBC 和真机因此可能看到不同的命令/goal 分布。即使 latent loss 很低，分布不一致仍会导致闭环失败。

需要制作统一覆盖表：每一阶段的速度命令、goal3、地形、难度、摩擦、噪声和相机姿态必须可比较。

#### P1-4：相机外参没有可追溯标定

当前 TOML 只有 `offset_pos` 和 `offset_rot` 数值，没有设备序列号、安装照片、标定日期、误差报告和原始标定文件。最终相机和支架固定后，应先完成标定，再启动最终一轮 LBC。

#### P1-5：当前 `deploy.yaml` 不是已验证的真机契约

当前文件的 `custom_obs.scale` 对应训练侧高维观测，总长度为 `57904 = 45 + 256 + 3 + 57600`。真机推理不应再携带 `height_scan256`，而且文件中也没有形成 Actor80 goal3、LSTM h/c 和相机重投影所需的完整 runtime 契约。它更像平台训练环境自动导出的配置，不能仅因文件名是 `deploy.yaml` 就认为已经可以交给 Jetson。

#### P1-6：eval stage 推断接口名称不一致

环境侧还存在对 `_infer_stage_for_eval` 的引用，而当前配置实际定义的是 `_infer_stage_from_task_name`。硬编码 `P22LBCLocoConfig` 暂时遮住了问题；切换其他阶段或依赖自动推断时可能失败。应统一函数名，并让 `Config.load_conf()` 推断出的 stage 成为 Agent、保存命名和加载命名的唯一来源。

### 6.4 P2：建议优化，但不要阻塞第一条正确基线

- 把 hard-coded dropout/noise/roll/pitch 写入 TOML 和 checkpoint；
- 为 `_split_obs` 增加总维度、shape、goal_dim、finite 和范围断言；
- 对比 carried LSTM state 与每帧 reset，证明 LSTM 是否真正有用；
- 如需利用更长时序，考虑 8 至 16 帧 TBPTT，而不是默认每帧 detach；
- 增加 action consistency 辅助损失；
- 可增加 masked pseudo-scan 辅助 head，帮助解释视觉失败；
- 建立最小单元测试和 checkpoint 契约测试。

## 7. 从头训练还是迁移：决策树

```text
42399 在统一 Track 固定种子下是否合格？
|
+-- 否 -> 从头/重训 Encoder PPO，旧模型只作参考
|
+-- 是 -> 修复行为蒸馏并生成可追溯 Encoder Teacher
          |
          +-- Encoder Teacher 闭环 >= 42399 - 5个百分点？
          |   |
          |   +-- 是 -> 进入 LBC
          |   |
          |   +-- 否 -> warm-start + DAgger式数据 + 小学习率 PPO
          |             |
          |             +-- 仍失败 -> 从头 Encoder PPO 或 h1 一段式蒸馏
          |
          +-- LBC Student 闭环 >= Encoder Teacher - 5个百分点？
              |
              +-- 是 -> 导出、数值对拍、真机分级测试
              |
              +-- 否 -> 查相机对齐/增强/分布偏移，再查模型容量
```

这里最重要的原则是：

```text
Teacher 不合格，不训练 Student；
Student 仿真闭环不合格，不导出真机；
部署数值不一致，不上机器人。
```

## 8. 最小实验矩阵

不要同时改很多变量。建议先跑四个同种子实验：

| 实验 | Teacher 来源 | 感知接口 | 目的 |
|---|---|---|---|
| E0 | flat `42399` | raw scan256 | 成熟策略上限基线 |
| E1 | 从头或 warm-start Encoder | latent32 | 独立 Encoder PPO 基线 |
| E2 | `42399` 行为蒸馏 | latent32 | 主迁移路线 |
| E3 | `42399` | h1(512) 一段式视觉蒸馏 | 高保真强对照 |

E2 和 E3 使用完全相同的训练/验证 seeds、相机增强和评估脚本。只有这样才能判断“两段 latent32 路线是否真的优于一段式 h1 路线”，而不是比较两个不同环境中的偶然结果。

## 9. 放行门槛

以下是工程建议，不是官方评分线：

| 阶段 | 放行条件 |
|---|---|
| Teacher 加载 | 文件/hash/shape/goal_dim 全部匹配，失败立即退出 |
| 行为蒸馏 | action MSE `<=1e-3`，cosine `>=0.99`，闭环完成率下降不超过 5 个百分点 |
| 视觉蒸馏 | latent cosine 建议 `>=0.985`，action MSE `<=1e-3` |
| Student 闭环 | 完成率相对 Encoder Teacher 下降不超过 5 个百分点 |
| 稳定性 | 姿态和能耗退化不超过 10%，关键地形无集中失败 |
| eval 确定性 | 同帧预处理 100 次逐元素一致 |
| LSTM | 每 tick 一次前向，所有 episode/FSM 边界正确 reset |
| ONNX 对拍 | 连续 1000 帧含 reset，raw action 最大误差 `<=1e-4` |
| goal3 对拍 | Python 与真机 adapter 最大误差建议 `<=1e-5` |
| 相机重投影 | 建议像素 RMS `<=1 px`，并验证深度/无效值规则 |
| Jetson 时延 | 重投影加推理 p99 `<20ms`，建议目标 `<15ms` |

## 10. 当前最优先的工作顺序

1. 不继续盲跑 `vision-162404`；先复测它的 embedded Teacher 和 Student；
2. 决定 actor80 自定义部署还是 actor77 分层部署；
3. 将所有 Teacher load 改为 fail-fast，并记录 hash；
4. 接通 behavior-distill StageConfig 和主 workflow；
5. 生成并归档一个可追溯的 Encoder Teacher；
6. 修复 Student-drive 双前向、eval 确定性、NaN/Inf 和 LSTM reset；
7. 修复真正的 LBC resume，并加入 action consistency；
8. 固定最终相机/支架，完成标定和内参重投影；
9. 完成 exporter、ONNX、goal3 runtime 和多帧数值对拍；
10. 按安全规范做低速、系绳、分地形的真机测试。

## 11. 最终判断

当前迁移思路不是错误，反而是保留复赛强模型最合理的主方向。但“行为蒸馏 -> LBC”应升级为：

```text
可追溯 Teacher
+ warm-start
+ Teacher/Student 状态分布混合
+ 小学习率 PPO 闭环修正
+ latent 与 action 双重约束
+ 固定种子分阶段验收
```

从头训练不是默认答案，而是必须保留的对照和兜底。当前代码的网络主体可以继续使用，暂时没有证据要求扩大 CNN、LSTM 或 latent；真正优先级更高的是训练入口、checkpoint 血缘、评估可信度、相机数据契约和部署闭环。
