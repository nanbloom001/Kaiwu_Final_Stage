# 《蒸馏深度模型真机部署转换报告》审核意见

> 审核日期：2026-07-11  
> 审核对象：[蒸馏深度模型真机部署转换报告.md](./蒸馏深度模型真机部署转换报告.md)  
> 审核依据：仓库代码、`决赛_track蒸馏_162404` 存档、Tencent Arena 27.0.21 本地规则镜像  
> 审核性质：静态代码与文档审核，不代表已经完成仿真、ONNX 或真机验证

## 一、总体结论

报告的总体部署方向基本合理，但当前版本不建议直接作为 `model.ckpt-vision-162404.pkl` 的真机实施说明。

报告已经正确识别以下事实：

- 真机不能使用仿真 `height_scan`，需要由深度相机驱动 Vision Student。
- `162404` 使用 Actor80，即 `proprio45 + latent32 + goal3`。
- 官方 stock LBC 使用 Actor77，原版 exporter 不能直接等价导出 Actor80。
- 自定义模型需要同步修改 wrapper、ONNX 输入和 Jetson C++ runtime。
- LSTM 模型必须进行连续多帧数值对拍，并按离线、悬空、站立、低速、复杂地形逐级验证。

但是，报告混淆了当前主线与归档代码，并在 goal3、terrain gate、相机重投影、相机标定和模型性能证明上存在关键错误。修订完成前，只能将其视为部署方案草稿。

## 二、必须修正的问题

### 1. 明确审核对象不是当前根目录主线

报告称当前主线默认使用 `P22LBCLocoConfig`，但根目录实际为 `Config.CURRENT = LocomotionConfig`：[根目录 conf.py](../agent_ppo/conf/conf.py#L186)。

`P22LBCLocoConfig`、goal3 和 Actor80 只存在于归档：[归档 conf.py](../代码存档/决赛_track蒸馏_162404/agent_ppo/conf/conf.py#L186)。

报告应统一改为：

> 本报告分析对象为 `代码存档/决赛_track蒸馏_162404`，不是仓库根目录当前主线。

同时修正报告末尾所有不存在的 `主线/...`、`参考代码/...` 和 `开发指南/开发指南/...` 路径。

### 2. 修正真机 goal3 公式

真机必须完整复现训练侧公式：

```text
goal3 = [
    clamp(local_goal_x / 10, -1, 1),
    clamp(local_goal_y / 10, -1, 1),
    clamp(goal_distance, 0, 20) / 20,
]
```

训练实现见 [goal_features.py](../代码存档/决赛_track蒸馏_162404/agent_ppo/feature/goal_features.py#L31)。报告当前正式 ONNX 输入示例遗漏了前两维的 `clamp`，远距离目标会进入训练分布之外。

### 3. 重写 terrain gate 章节

报告称当前 P22 LBC 启用了 worker-side terrain gate，这一结论不成立：

- gate 出现在参考蒸馏配置中：[p22_ref_distill.toml](../代码存档/决赛_track蒸馏_162404/agent_ppo/conf/train_env_conf_track_p22_ref_distill.toml#L54)；
- P22 LBC 配置没有 `[rl_navigation]`：[p22_lbc_loco.toml](../代码存档/决赛_track蒸馏_162404/agent_ppo/conf/train_env_conf_track_p22_lbc_loco.toml#L38)；
- LBC 观测处理没有调用 gate：[lbc_observation_process.py](../代码存档/决赛_track蒸馏_162404/agent_ppo/feature/lbc_observation_process.py#L21)。

原 gate 还依赖仿真 `height_scanner` 和 `nav_scanner`。从真机深度图重建地形再分类属于新感知模块，不能表述为简单移植。

应先确认 Encoder Teacher 的来源配置和命令分布，再决定是否重建 gate、使用固定低速命令，或重新训练完成分布对齐。

### 4. 不得宣称当前 checkpoint 已保留导航能力

当前 checkpoint 的结构保留了 goal3-conditioned Actor80，但仓库没有 Student 闭环完成率、摔倒率、用时、视频和 Teacher/Student 对照结果。

当前配置计划训练 `10000 x 24 = 240000` 步：[P22 LBC 配置](../代码存档/决赛_track蒸馏_162404/agent_ppo/conf/train_env_conf_track_p22_lbc_loco.toml#L54)；checkpoint 静态信息显示约完成一半。

报告应改为：

> 当前 checkpoint 在结构上具备保留 Track 导航策略的可能性，但实际导航能力尚未通过 Student 闭环评估证明。

### 5. 修正深度重投影和相机标定顺序

官方部署路径应采用目标图像的反向采样：对每个目标仿真像素按仿真内参计算射线，再投影到 RealSense 原图坐标取样。不能只描述为从真机像素向目标图前向投影，否则可能产生孔洞和重叠。依据见 [部署指南](../规则说明/开发指南/部署指南.md#L688)。

相机标定也不能放在最终训练和 ONNX 导出之后。正确顺序是：

```text
固定相机和支架
-> 标定真机内参和安装外参
-> 更新训练配置
-> 最终训练或微调
-> 导出 ONNX
-> 多帧数值对拍
-> 分级真机测试
```

官方指南明确要求部署模型基于标定后的相机参数训练：[部署指南](../规则说明/开发指南/部署指南.md#L96)。

### 6. 区分已确认定位链路与待确认方案

规则明确提到的终点相关链路是 UWB：[项目简介](../规则说明/开发指南/项目简介.md#L68)。视觉 SLAM、外部定位系统和预设赛道里程计状态机只能列为工程候选，必须向主办方确认现场接口和合规性。

无论使用何种定位方式，都必须输出与训练完全同义的机器人世界位置、机器人 yaw 和目标世界位置，并在定位超时或异常时进入安全状态，不能静默输出全零 goal3。

### 7. 修正 deploy.yaml 的状态描述

归档中已经存在 [deploy.yaml](../代码存档/决赛_track蒸馏_162404/agent_ppo/conf/deploy.yaml#L1)，因此不能写成“仓库中不存在”。

正确结论是：

> 存在训练侧生成的 deploy.yaml，但其 custom observation 对应 57904 维训练观测，尚未证明与 `162404` checkpoint 同源，也没有形成经过验证的 Actor80 Jetson 精简部署契约。

最终配置仍需核对 `joint_ids_map`、默认关节位置、action scale、KP/KD、proprio scale、clip、命令范围和 `step_dt=0.02`。

### 8. 增加当前代码风险说明

报告还应记录以下风险：

- 评估环境只设置 `_is_eval`，深度增强代码却默认读取 `_is_training=True`，评估可能继续随机加噪：[nav_observation_utils.py](../代码存档/决赛_track蒸馏_162404/agent_ppo/feature/nav_observation_utils.py#L63)。
- `student_drive=true` 时，同一帧可能使 VisionEncoder/LSTM 前进两次：[lbc_workflow.py](../代码存档/决赛_track蒸馏_162404/agent_ppo/workflow/lbc_workflow.py#L195)。
- 平台评估路径没有明确传递 episode done mask，LSTM episode reset 尚未闭环：[agent.py](../代码存档/决赛_track蒸馏_162404/agent_ppo/agent.py#L276)。
- wrapper 必须保证 `proprio[:, 6:9] == cmd_override[:, :3]`，避免模型实际速度命令与日志输出不一致。
- 初次落地速度应限制在 `0.2-0.3 m/s`；`vx=0.70` 只适合无电机输出或可靠吊架下的分布检查。

## 三、关于官方模型结构的审核结论

比赛规则没有要求选手必须使用官方推荐网络结构。

- 官方将提供的智能体称为“简单实现”：[智能体详述](../规则说明/开发指南/智能体详述.md#L5)。
- Track 阶段允许通过 `CustomConfig` 自定义模型、观测和训练阶段：[智能体详述](../规则说明/开发指南/智能体详述.md#L159)。
- 框架层面的明确要求是模型符合 PyTorch `torch.nn.Module`：[模型开发](../规则说明/强化学习框架/模型开发.md#L7)。

因此，Actor80 并不违反比赛规则。实际问题是官方 stock exporter/runtime 直接支持 Actor77，而不直接支持 Actor80。Actor80 在补齐自定义 exporter、goal3 adapter、C++ runtime 和多帧数值对拍后，技术上可以部署，但当前 checkpoint 的比赛性能仍需单独验证。

## 四、建议修订和验证顺序

1. 将报告分析对象统一改为 `代码存档/决赛_track蒸馏_162404`，修正全部路径。
2. 修正 goal3 clamp、深度 inverse mapping 和命令输入契约。
3. 删除“当前 LBC 已启用 terrain gate”的错误结论，补充 Teacher 来源与命令分布审计。
4. 固定并标定最终相机和支架，确认训练外参与真机一致。
5. 单独验证 checkpoint 内嵌 Teacher 的 Track 完成率和稳定性。
6. 修复随机评估增强、Student 双推进和 LSTM reset 问题。
7. 完成 Vision Student 闭环评估，并与 Teacher 比较完成率、摔倒率、用时和动作差异。
8. 只有 Student 达标后，再编写 Actor80 exporter 和 Jetson runtime。
9. 完成训练模型、wrapper、ONNX 三方连续多帧对拍。
10. 整理同源精简 deploy.yaml，并按离线、悬空、站立、低速和完整 Track 顺序上机。

## 五、审核结论

审核意见为：**修改后再实施**。

报告可以保留 Actor77/Actor80 差异、Vision Student 推理路径、自定义导出器、多帧对拍和分级安全验证等主体内容；但必须先修正分析对象、goal3、terrain gate、相机处理和性能证明。当前 `162404` 可作为继续评估和开发 exporter 的候选 checkpoint，不能直接认定为已经具备真机 Track 部署条件。
