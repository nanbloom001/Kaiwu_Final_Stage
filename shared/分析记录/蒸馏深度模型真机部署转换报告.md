# 蒸馏深度模型真机部署转换报告

> 日期：2026-07-10  
> 项目：Tencent Arena / Unitree Go2 四足机器人 Sim2Real  
> 分析范围：`主线/agent_ppo`、本地《部署指南》及当前 Track 深度视觉蒸馏配置

## 1. 报告目的

本报告说明如何将当前项目训练得到的深度视觉蒸馏模型转换为可在 Unitree Go2 机载 Jetson 上运行的部署模型，并明确：

1. 当前 checkpoint 的网络结构和真实推理路径。
2. 当前模型与官方 `deploy_loco` 部署包的兼容性。
3. ONNX 导出脚本需要进行的修改。
4. Jetson/C++ 运行时必须提供的传感器、目标和速度命令输入。
5. 上机前的数值验证、安全验证和验收标准。

## 2. 结论摘要

当前主线默认训练阶段不是普通 standard LBC，而是 Track 深度视觉蒸馏阶段：

```python
Config.CURRENT = P22LBCLocoConfig
```

该阶段的主要配置为：

```text
stage name       = p22_lbc_loco
task type        = track
checkpoint name  = model.ckpt-vision
goal dimension   = 3
action dimension = 12
```

因此，训练产物形如：

```text
model.ckpt-vision-<id>.pkl
```

虽然 checkpoint 顶层仍保存：

```python
format = "lbc_loco"
```

但它与官方标准 `lbc_loco` 模型存在关键结构差异：

| 项目 | 官方标准 LBC | 当前 Track 深度模型 |
| --- | ---: | ---: |
| proprio | 45 | 45 |
| latent | 32 | 32 |
| goal | 0 | 3 |
| teacher actor 输入 | 77 | 80 |
| checkpoint 前缀 | `model.ckpt-lbc-loco` | `model.ckpt-vision` |
| 导航目标参与 actor | 否 | 是 |

**结论：当前 `model.ckpt-vision-*.pkl` 不能直接使用官方原版 `export_loco_onnx.py` 导出并部署。**

官方脚本只能直接处理 `goal_dim=0`、teacher actor 输入为 77 维的 standard LBC 模型。当前 Track 模型需要新增 Track-aware ONNX wrapper，并同步修改 Jetson 侧目标特征和速度命令生成逻辑。

## 3. 当前模型结构

### 3.1 学生视觉编码器

当前学生模型为 `VisionEncoder`：

```text
depth image [B,180,320,1]
        │
        ▼
SimpleCNN
        │
        ▼
cnn feature [B,32]
        │
        ├──────── proprio [B,45]
        │
        ▼
concat [B,77]
        │
        ▼
2-layer LSTM, hidden=64
        │
        ▼
Linear 64→32
        │
        ▼
L2-normalized latent [B,32]
```

关键维度：

```text
depth shape       = 180 × 320 × 1
CNN output        = 32
proprio dimension = 45
LSTM input        = 77
LSTM hidden       = 64
LSTM layers       = 2
latent dimension  = 32
```

代码位置：

- `主线/agent_ppo/model/vision_encoder.py`
- `主线/agent_ppo/model/simple_cnn.py`

### 3.2 Track teacher actor

学生视觉编码器只负责从深度图预测教师 latent。最终关节动作仍由冻结的 teacher actor 产生：

```text
teacher actor input
    = proprio45
    + student latent32
    + Track goal3
    = 80 dimensions

teacher actor
    = 80 → 512 → 256 → 128 → 12
```

最终输出为 12 个 Go2 关节的原始动作：

```text
raw joint action [B,12]
```

代码位置：

- `主线/agent_ppo/agent.py::_init_lbc_loco`
- `主线/agent_ppo/algorithm/algorithm_lbc.py::_teacher_actor_input`
- `主线/agent_ppo/algorithm/algorithm_lbc.py::act_student`

### 3.3 Track goal3

当前 Track 模型使用以下三维目标特征：

```text
goal3 = [
    clamp(local_goal_x / 10, -1, 1),
    clamp(local_goal_y / 10, -1, 1),
    clip(goal_distance, 0, 20) / 20,
]
```

前两维先除以 10 再 `clamp(-1, 1)`，第三维距离先 `clip(0, 20)` 再除以 20。对应 `goal_features.py` 中 `torch.clamp(local_goal / 10.0, -1.0, 1.0)` 与 `torch.clamp(norm(delta_w), 0.0, 20.0) / 20.0`。

其中：

- `local_goal_x`：目标在机器人坐标系下的前后方向分量。
- `local_goal_y`：目标在机器人坐标系下的左右方向分量。
- `goal_distance`：机器人与当前目标点之间的平面距离。

代码位置：

- `主线/agent_ppo/feature/goal_features.py::build_track_goal_features`

真机部署时必须使用与训练完全相同的坐标变换、裁剪和归一化方式；尤其不能漏掉前两维的 `clamp(-1, 1)`，否则目标较远时 goal3 会超出训练分布。

## 4. Checkpoint 部署内容

`AlgorithmLBC.save()` 保存的主要字段为：

```python
{
    "format": "lbc_loco",
    "vision_encoder_state_dict": ...,
    "teacher_encoder_state_dict": ...,
    "teacher_actor_state_dict": ...,
    "goal_dim": 3,
    "optimizer_state_dict": ...,
    "current_iteration": ...,
    "total_steps": ...,
    "learning_rate": ...,
}
```

真机部署实际需要：

| 字段 | 是否需要 | 用途 |
| --- | --- | --- |
| `vision_encoder_state_dict` | 是 | 深度图和 proprio 编码为 latent |
| `teacher_actor_state_dict` | 是 | latent、proprio、goal3 解码为关节动作 |
| `goal_dim` | 是 | 确认 actor 输入契约 |
| `teacher_encoder_state_dict` | 否 | 仅训练时从 height scan 生成教师 latent |
| `optimizer_state_dict` | 否 | 仅续训使用 |

导出前应执行以下静态检查：

```text
ckpt["format"] == "lbc_loco"
ckpt["goal_dim"] == 3
vision encoder 包含 cnn.*、rnn.*、rnn_output_layer.*
teacher actor 第一层 weight.shape == [512,80]   # nn.Sequential 键名 "0.weight"
teacher actor 最后一层输出维度 == 12              # nn.Sequential 键名 "6.weight"，shape == [12,128]
```

## 5. 与官方部署包的兼容性

官方 `deploy_loco/export_loco_onnx.py` 面向 standard LBC，默认构造：

```text
teacher actor input = proprio45 + latent32 = 77
```

官方 ONNX 接口中的 `goal[1,4]` 在 loco 模式下只用于诊断，不参与关节动作计算。

当前 Track 模型则要求：

```text
teacher actor input = proprio45 + latent32 + goal3 = 80
```

直接运行官方脚本可能出现两类问题：

1. teacher actor 第一层加载时发生 `80 → 77` 的尺寸不匹配。
2. 即使通过非严格加载绕过错误，goal3 没有进入 actor，导出的模型也不等价于训练模型。

因此不能仅以：

```text
ckpt["format"] == "lbc_loco"
```

作为可直接部署的判断标准，还必须检查 `goal_dim` 和 teacher actor 第一层输入维度。

## 6. 推荐 ONNX 导出方案

### 6.1 新增 Track 导出脚本

建议以官方脚本为基线，新建：

```text
export_track_loco_onnx.py
```

不要直接覆盖官方 `export_loco_onnx.py`，以便同时保留 standard LBC 和 Track LBC 两条部署链路。

### 6.2 Wrapper 计算图

Track wrapper 的核心前向应严格复刻训练侧 `act_student`：

```python
def forward(depth, proprio, goal, loco_h, loco_c,
            nav_h, nav_c, cmd_override):
    cnn_feature = cnn(depth)
    lstm_input = torch.cat([cnn_feature, proprio], dim=-1)
    lstm_output, (loco_h_out, loco_c_out) = lstm(
        lstm_input.unsqueeze(1),
        (loco_h, loco_c),
    )
    latent = rnn_output_layer(lstm_output.squeeze(1))
    latent = torch.nn.functional.normalize(latent, p=2.0, dim=-1)

    goal3 = goal[:, :3]
    actor_input = torch.cat([proprio, latent, goal3], dim=-1)
    joint = teacher_actor(actor_input)

    return (
        cmd_override[:, :3],
        cmd_override[:, :3],
        torch.zeros_like(cmd_override[:, :3]),
        joint,
        loco_h_out,
        loco_c_out,
        nav_h,
        nav_c,
    )
```

### 6.3 保持八入八出接口

为减少 Jetson C++ 修改范围，建议继续使用官方八入八出 ONNX 契约：

#### 输入

| 输入 | Shape | Track 部署含义 |
| --- | --- | --- |
| `depth` | `[1,180,320,1]` | 重投影并归一化后的 D435i 深度图 |
| `proprio` | `[1,45]` | 与训练一致的缩放后本体观测 |
| `goal` | `[1,4]` | 前三维放 Track goal3，第四维保留为 0 |
| `loco_h` | `[2,1,64]` | LSTM hidden state |
| `loco_c` | `[2,1,64]` | LSTM cell state |
| `nav_h` | `[2,1,64]` | 兼容字段，原样透传 |
| `nav_c` | `[2,1,64]` | 兼容字段，原样透传 |
| `cmd_override` | `[1,4]` | `[vx,vy,wz,gate]` |

建议将 `goal` 重定义为：

```text
goal = [
    local_goal_x / 10,
    local_goal_y / 10,
    clip(goal_distance, 0, 20) / 20,
    0,
]
```

#### 输出

| 输出 | Shape | 含义 |
| --- | --- | --- |
| `cmd` | `[1,3]` | 当前速度命令 |
| `cmd_raw` | `[1,3]` | 当前原始速度命令 |
| `clearance` | `[1,3]` | 兼容字段 |
| `joint` | `[1,12]` | 原始关节动作 |
| `loco_h_out` | `[2,1,64]` | 下一帧 hidden state |
| `loco_c_out` | `[2,1,64]` | 下一帧 cell state |
| `nav_h_out` | `[2,1,64]` | 原样透传 |
| `nav_c_out` | `[2,1,64]` | 原样透传 |

### 6.4 导出参数

推荐参数：

```text
batch size       = 1
dynamic axes     = None
opset            = 17
constant folding = False
depth dtype      = float32
state dtype      = float32
```

参考命令：

```bash
python3 export_track_loco_onnx.py \
  --ckpt models/model.ckpt-vision-XXXX.pkl \
  --out runtime/unitree_rl_lab_test/logs/loco/exported/policy.onnx \
  --opset 17 \
  --frames 32
```

## 7. ONNX 数值验证

不能只验证 wrapper 与 ONNX Runtime 一致，还必须先证明 wrapper 等价于当前训练模型。

### 7.1 第一层：训练模型与 wrapper 对拍

输入相同的：

```text
depth
proprio
goal3
初始 h/c
```

逐帧比较：

```text
student latent
raw joint action
loco_h_out
loco_c_out
```

### 7.2 第二层：wrapper 与 ONNX Runtime 对拍

PyTorch wrapper 和 ONNX Runtime 必须各自维护 LSTM 状态，并将上一帧输出的 `h/c` 回喂到下一帧。

建议：

```text
最少验证帧数：32
推荐验证帧数：100+
joint 最大绝对误差：<= 1e-4
h/c 最大绝对误差：<= 1e-4
输出中不得出现 NaN/Inf
```

除随机输入外，应优先使用仿真评估期间记录的真实连续观测进行对拍。

## 8. 真机输入处理

### 8.1 Proprio

真机需要构造与训练一致的 45 维 proprio：

```text
[0:3]    body angular velocity       scale 0.25
[3:6]    projected gravity           scale 1.0
[6:9]    velocity command            scale 1.0
[9:21]   joint position relative     scale 1.0
[21:33]  joint velocity              scale 0.05
[33:45]  previous raw joint action   scale 1.0
```

整段输入执行：

```text
clip(-100, 100)
```

注意：

- `last_action` 应使用上一帧 ONNX 输出的原始动作，而不是经过 action scale 后的关节目标。
- 关节顺序必须与训练时 `joint_ids_map` 完全一致。
- `projected_gravity` 的坐标系、四元数顺序和符号必须与仿真一致。

### 8.2 深度图

真机 RealSense D435i 深度图不能直接 resize 为 `320×180`。

正确流程：

```text
D435i depth
    → 去除无效值和非有限值
    → 按真机内参反投影
    → 按仿真相机内参重投影
    → 输出 320×180
    → 处理 <=0 或 >=5m 的像素
    → 归一化到 [0,1]
    → NHWC float32
```

仿真模型使用的目标输入参数为：

```text
width  = 320
height = 180
fx     = 168.61
fy     = 168.61
cx     = 160
cy     = 90
```

相机外参也必须与训练 TOML 中的安装位置和姿态保持一致。

### 8.3 Goal3

当前模型不能仅依靠深度相机完成完整 Track 推理，还需要实时目标点信息。

真机侧应提供：

```text
robot_world_x
robot_world_y
robot_world_yaw
goal_world_x
goal_world_y
```

可选来源：

1. UWB 定位。
2. 视觉 SLAM。
3. 外部定位系统。
4. 已知赛道下的里程计与目标点状态机。

必须按照训练侧 `goal_features.py` 的公式转换到机器人局部坐标系。

## 9. 速度 Gate 的部署问题

当前训练配置启用了 worker-side terrain gate：

```text
pre-maze speed = 0.80
slope speed    = 0.80
stairs speed   = 0.70
maze speed     = 0.70
```

训练过程中，gate 会直接修改：

```text
proprio[6:9]
```

因此 gate 虽然不在 ONNX 网络内部，却属于模型真实推理环境的一部分。

官方 Fixed Loco 运行包只会将固定速度或上层速度命令写入 `proprio[6:9]`，不会自动执行当前 Python `terrain_gate.py`。

### 9.1 推荐方案

在 Jetson C++ 中实现部署版 terrain gate：

```text
重投影深度图
    → 构造局部高程或地形特征
    → 判断 flat/slope/stairs/maze
    → 执行 sticky 状态机
    → 选择 vx
    → 写入 proprio[6:9]
```

至少需要迁移：

- 坡道、楼梯和平地判定。
- 楼梯上下方向判定。
- 迷宫阶段判定。
- sticky confirm/hold/release 状态。
- 对应速度值。

### 9.2 临时最小方案

如果暂不移植 gate，可先固定：

```text
vx = 0.70
vy = 0
wz = 0
```

该方案可用于悬空和低速链路测试，但不等价于训练分布，在坡道、楼梯和迷宫中的完成率可能明显下降。

### 9.3 更稳定的长期方案

重新训练或微调一个只依赖真机可获得输入的版本：

- 去除仿真专用 height scan/nav scanner gate。
- 将地形速度控制显式并入深度网络或真机可复现的 C++ 模块。
- 对固定命令、定位误差和深度噪声进行域随机化。

## 10. deploy.yaml

`deploy.yaml` 必须与生成 checkpoint 的训练配置同源，至少包含：

```yaml
joint_ids_map: [...]
step_dt: 0.02
stiffness: [...]
damping: [...]
default_joint_pos: [...]

actions:
  JointPositionAction:
    scale: 0.25
    offset: [...]
    clip: [-100.0, 100.0]

proprio_scales:
  ang_vel: 0.25
  projected_gravity: 1.0
  vel_cmd: 1.0
  joint_pos_rel: 1.0
  joint_vel_rel: 0.05
  last_action: 1.0

proprio_clip: [-100.0, 100.0]
```

以下配置不一致时可能直接造成真机异常：

- `joint_ids_map`
- `default_joint_pos`
- action `scale/offset`
- `stiffness`
- `damping`
- proprio scale
- 控制周期

当前仓库 `主线/` 中没有实际生成的 `deploy.yaml`，应从与目标 checkpoint 同一次训练或测试环境中导出。

## 12. 上机验证顺序

### 阶段 A：离线验证

1. checkpoint 字段和权重 shape 检查。
2. PyTorch 原模型与导出 wrapper 多帧对拍。
3. wrapper 与 ONNX Runtime 多帧对拍。
4. 回放仿真记录，检查动作范围、LSTM 状态和延迟。

### 阶段 B：无电机或悬空验证

1. 检查深度图是否有效。
2. 检查 proprio 维度、范围和 scale。
3. 检查 goal3 的方向和距离变化。
4. 检查 ONNX 单帧推理时间。
5. 检查 raw action 是否存在 NaN、Inf 或异常尖峰。
6. 检查 LSTM reset 是否在控制器启动和状态切换时执行。

### 阶段 C：FixStand

1. 进入 `FixStand`。
2. 检查关节方向和顺序。
3. 检查默认站姿。
4. 检查 KP/KD 是否造成高频抖动。
5. 确认急停能够立即进入 Passive。

### 阶段 D：低速 VisionLoco

1. 初始速度限制在 `0.2～0.3 m/s`。
2. 先测试平地。
3. 再测试低难度坡道。
4. 再测试低台阶。
5. 最后测试完整 Track 和迷宫。

## 13. 性能与安全验收

建议真机部署前满足：

| 项目 | 建议标准 |
| --- | --- |
| ONNX joint 对拍误差 | `<= 1e-4` |
| ONNX LSTM state 对拍误差 | `<= 1e-4` |
| 控制频率 | 稳定 50 Hz |
| 单帧总耗时 | `< 20 ms` |
| NaN/Inf | 0 |
| 深度丢帧 | 有超时和安全降级 |
| 定位超时 | 停止或进入 Passive |
| action 异常 | 有范围和连续错误保护 |
| 急停 | 手柄和进程级急停均有效 |

真机安全状态切换应保持：

```text
Passive → FixStand → VisionLoco
```

异常时优先：

```text
L2+B → Ctrl+C → 必要时物理断电
```

## 14. 两条可选部署路线

### 路线 A：只要求机器狗进行视觉运控

重新训练或使用 standard、`goal_dim=0` 的 LBC checkpoint：

```text
model.ckpt-lbc-loco-*.pkl
```

优点：

- 可直接使用官方 `export_loco_onnx.py`。
- Jetson C++ 无需处理 goal3。
- Fixed Loco 部署链路完整。

缺点：

- 只能按固定/UWB 速度命令运动。
- 不具备当前 Track teacher 的目标点导航能力。

### 路线 B：部署当前 Track 深度模型

使用：

```text
model.ckpt-vision-*.pkl
```

需要完成：

1. `export_track_loco_onnx.py`。
2. 80 维 teacher actor 导出。
3. goal3 真机计算。
4. C++ terrain gate 或部署分布重新对齐。
5. 修改 Jetson 侧 ONNX 输入构造。
6. 完整 Track 真机验证。

该路线工作量更大，但能够保留当前 Track 蒸馏模型的导航能力。

## 16. 推荐实施顺序

建议按以下顺序推进：

1. 获取准备部署的 `model.ckpt-vision-*.pkl`。
2. 编写 checkpoint 静态检查脚本，确认 `goal_dim=3` 和 actor 输入 80 维。
3. 获取官方 `unitree_isaaclab_deploy/deploy_loco`。
4. 新建 `export_track_loco_onnx.py`。
5. 完成训练模型、wrapper、ONNX 三方多帧对拍。
6. 从同源训练环境导出 `deploy.yaml`。
7. 修改 Jetson C++，生成 goal3。
8. 决定移植 terrain gate，或先使用固定 `vx=0.70` 做链路测试。
9. 完成相机标定和深度重投影。
10. 按离线、悬空、FixStand、低速、复杂地形顺序逐级上机。
