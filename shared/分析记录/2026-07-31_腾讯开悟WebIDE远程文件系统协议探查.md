# 腾讯开悟 Web IDE 远程文件系统协议探查

## 1. 目的与范围

日期：2026-07-31

本次探查用于判断腾讯开悟 Web IDE 是否存在比当前 HTTP GET 分片 RPC
更高效的大文件上传通道。2026-07-31 完成只读协议探查；
2026-08-01 在用户明确授权下完成小文件、分块大文件和本地文件传输的
可写 POC，所有远程测试文件均在校验后删除。

文档不记录任何 Cookie、Token、WebSocket Key、完整鉴权帧或临时
`reconnectionToken`。这些值不得被写入源码、日志、测试 fixture 或提交历史。

## 2. 结论摘要

1. Web IDE 使用 `code-server 4.98.2 / VS Code 1.98.2` 的 Remote Agent 协议。
2. 远程文件系统确实通过持久化 WebSocket 二进制 RPC 运行，通道名为
   `remoteFilesystem`。
3. 协议提供 `writeFile` 以及 `open -> write -> close` 两种写入路径；
   64 KiB 单次写入、4 MiB 分块写入和 2 MiB 本地文件传输已实测通过。
4. 它不是可直接调用的 JSON WebSocket 或 REST 上传 API。已验证的路径依赖
   用户已登录的 Chrome IDE 页面，由 CDP 在页面中建立独立 Remote Agent
   连接；它尚不是一个脱离浏览器鉴权上下文的通用 CLI。
5. 当前腾讯定制 workbench 中没有发现可调用的 `uploadFiles` 命令，
   文件夹右键菜单也没有“上传文件”入口。
6. 同一 Remote Agent 连接还提供 `remoteterminal` channel。当前工具只用它
   启动受限的容器端 `sha256sum` 校验，不对调用方暴露任意 shell 命令。

## 3. 实测协议证据

### 3.1 WebSocket 连接

页面会建立两条同类型连接，端点形式为：

```text
wss://tencentarena.com/p5/ide/<ide-id>/stable-<commit>
  ?reconnectionToken=<ephemeral>
  &reconnection=false
  &skipWebSocketFrames=false
```

实测握手返回 HTTP `101 Switching Protocols`，数据帧使用 WebSocket opcode 2，
即二进制帧。连接开始阶段可观察到以下逻辑阶段：

```text
auth
-> sign challenge
-> connectionType
-> VS Code IPC channel registration
```

`reconnectionToken` 是临时值，不能作为固定配置或硬门禁。

### 3.2 Remote Agent 环境

远程环境响应证明容器使用：

```text
code-server: 4.98.2
VS Code protocol version: 1.98.2
remote scheme: vscode-remote
remote authority: tencentarena.com
```

客户端 workbench 资源由平台的 `stable-<commit>` 目录提供。协议实现随
code-server/VS Code 版本变化，不能把当前压缩代码中的符号名当成长期稳定接口。

### 3.3 文件系统 RPC

前端代码注册的 channel 名为：

```text
remoteFilesystem
```

已从实际二进制帧与 workbench 实现中确认的方法包括：

```text
stat
readdir
readFile
readFileStream
writeFile
open
read
write
close
mkdir
delete
rename
copy
cloneFile
watch
unwatch
```

客户端 provider 的关键写入语义为：

```text
writeFile(uri, VSBuffer, options)

open(uri, options)
write(handle, position, buffer, offset, length)
close(handle)
```

`writeFile` 会把完整 buffer 作为一次 RPC 调用参数。当 provider 选择
open/read/write/close 能力时，VS Code FileService 会以流式方式写入；当前源码中
用于文件流复制的默认 buffer 为 `256 KiB`。

### 3.4 Remote Terminal PTY

同一主连接提供 `remoteterminal` channel。VS Code 1.98.2 的请求与事件语义为：

```text
$createProcess -> $start
$input(process_id, data)
$onProcessDataEvent -> $acknowledgeDataEvent
$onProcessExitEvent
$shutdown(process_id, immediate)
```

2026-08-01 已在当前容器完成真实交互测试：启动 `/bin/sh -i`，通过四次独立
`$input` 发送 marker、`pwd`、`python3 --version` 和 `exit`。实测进程退出码为
`0`，工作目录为 `/data/projects/legged_robot_competition_26`，Python 为
`3.13.12`，并收到了命令回显、执行结果和 ANSI 控制序列。测试证明该通道是
真实 PTY 输入输出，不只是一次性后台命令。

仓库当前只公开固定、无副作用的 `runKaiwuInteractiveTerminalSmoke()`；底层协议
虽可发送任意字符串，但尚未将通用 shell 执行作为公共 API 开放。

同步服务自举入口为：

```js
const { startKaiwuSyncService } = await import(
  "./shared/tools/tencent_kaiwu_webide_upload.mjs"
);

const result = await startKaiwuSyncService({ tab });
```

该函数必须在 Codex Chrome browser client 的 Node 会话中调用，并接收已登录目标
IDE 的受控 `tab`。它是可复用库 API，不是普通 shell CLI，也不负责执行本地文件
diff、上传或删除；这些操作仍由 `server/local_sync_client.py` 承担。

该入口固定检查 `127.0.0.1:8765/health`，已有 HTTP 响应时返回
`alreadyRunning=true`，不会重复启动；没有响应时才以 `nohup` 执行固定路径
`/data/projects/legged_robot_competition_26/conf/start_tongbu.sh`，随后轮询健康状态。
`/health` 受 Token 保护，未带 Token 的 HTTP 401 仍证明端口服务存活，因此探针不能使用
`curl -f`。2026-08-01 已在真实容器验证 already-running 分支，并在关闭 PTY 后通过本地
`PY311test container_rpc_client.py` 再次执行 `pwd` 成功。为避免中断当前服务，冷启动分支
尚未通过关闭 8765 后重启的破坏性测试。

推荐的日常调用顺序固定为：

```text
已登录 IDE tab
-> startKaiwuSyncService({ tab })
-> bootstrap.healthy == true
-> server/local_sync_client.py --check-local
-> server/local_sync_client.py --dry-run --skip-unchanged
-> server/local_sync_client.py --skip-unchanged
-> 可选 container_rpc_client.py --cwd . "pwd"
```

自举连接使用的随机 WebSocket token 仅属于 Remote Agent 握手，不能替代同步服务的
`IDE_SYNC_TOKEN`。无 Token 的 `/health` 返回 `401` 只能证明 HTTP 服务存活；后续
`local_sync_client.py` 仍可能因为共享 Token 不一致或腾讯代理 Cookie 失效而拒绝请求。
若自举返回失败，先查看返回信息指向的 `/tmp/codex-tongbu-18005.log`；当前实现不会
为了失败回滚而终止可能已经启动的后台服务，避免误杀同时存在的健康实例。

### 3.5 当前页面没有原生上传入口

对当前 IDE 进行的只读检查结果：

- 文件夹右键菜单中没有“上传”。
- DOM 中没有可用的 `input[type=file]`。
- workbench bundle 中没有以下命令或符号：

```text

因此当前不存在“只找到隐藏按钮就可自动化”的简单路径。

## 4. 与现有 RPC 上传的比较

| 项目 | 当前 `tongbu.py` GET bundle | VS Code Remote Filesystem |
|---|---|---|
| 传输单元 | URL-safe GET 小 chunk | WebSocket 二进制帧 |
| 当前可用性 | 已实现并使用 | 已在登录 Chrome 页面中实测，尚无独立 CLI |
| 原子合并 | 已有暂存和 SHA256 | `.uploading` + SHA256 + `rename` 已实测 |
| 断点续传 | 分片层可续传 | provider 不支持，中断后从头重传 |
| 吞吐 | 受 4 KiB GET 和代理开销限制 | 24 MiB 单次实测约 2.64 MiB/s |
| 协议稳定性 | 仓库内自有协议 | 跟随 VS Code/code-server 版本 |
| 鉴权 | 自有 Token + IDE 代理 Cookie | IDE Cookie + 临时 token + sign challenge |

新通道已完成小文件和 4 MiB 分块 POC。当前实测只能证明协议和
数据完整性可行；2 MiB 本地传输用时约 1.24 秒，但测试规模过小，
不应把该数值直接外推为正式模型的稳定吞吐。

## 5. 独立客户端所需实现

一个可靠的客户端至少需要：

1. 从当前已登录 IDE 会话获取 Web IDE 地址，不持久化 Cookie。
2. 每次连接动态获取 `stable-<commit>` 和 `reconnectionToken`。
3. 实现 `auth/sign/connectionType` 握手。
4. 实现 VS Code Persistent Protocol 帧格式、请求 ID、响应匹配与 ping。
5. 实现 IPC channel 参数编码，特别是 URI、VSBuffer 和二进制数组。
6. 通过 `remoteFilesystem` 调用 `mkdir/open/write/close/stat/rename/delete`。
7. 只允许写入经过白名单校验的目录，例如
   `agent_ppo/test_artifacts/`。
8. 远程先写入 `.uploading`，核对 size 和 SHA256 后原子 rename。
9. 连接断开后删除或覆盖 `.uploading` 文件并从头重传；当前
   `open` 语义不支持可靠断点续传。
10. 禁止在调试输出中打印 Cookie、完整 WebSocket URL、鉴权帧或临时 token。

remote staging: agent_ppo/test_artifacts/ws-upload-poc.bin.uploading

```

可写、分块、校验、原子改名、中断恢复语义和 24 MiB 模型尺度载荷已验证，
版本固定、路径白名单和失败清理也已封装为可复用工具。在完成与现有
GET bundle 的同文件稳定性与吞吐对比前，仍不应直接替换现有默认上传器。

## 7. 风险与决策

### 主要风险

- 平台升级 code-server/VS Code 后二进制协议可能变化。
- 直接复制或固定化临时鉴权参数会形成凭据泄露和失效风险。
- 未处理好请求 ID、并发响应与重连可能写坏远程文件。
- 直接 `writeFile` 大 buffer 可能引入高峰内存和单帧限制。
- 客户端过度依赖压缩后的内部符号会导致维护成本过高。

### 当前建议

1. 保留自有 RPC 分片上传器作为不依赖 Chrome 的保底路径。
2. WebSocket 路径可用于已登录 Chrome 会话中的模型上传，但必须保留
   版本检查、目录白名单、`.uploading` 后缀、远程回读 SHA256 和原子改名。
3. 正式上传默认使用 256 KiB 分块，并必须在接收端按 13 字节
   Persistent Protocol 头部的 length 跨 WebSocket message 重组。
4. 连接中断后从头重传，不实现伪断点续传；只有当平台提供可写的
   非截断打开语义后才可重新评估。

## 8. 2026-08-01 可写 POC 结果

### 8.1 双连接与正确通道

页面同时建立 Remote Agent 主连接和 Extension Host 连接。只有主连接承载
`remoteFilesystem`。将文件系统帧发往 Extension Host 会触发 `sid` 未定义异常；
该异常不是 URI、文件权限或鉴权参数问题。

独立主连接已验证以下顺序：

```text
WebSocket open
-> auth
-> sign
-> connectionType
-> ok
-> renderer initialization
-> remoteFilesystem stat
```

鉴权值和临时连接标识均仅在已登录页面内存中使用，未输出或落盘。

### 8.2 数据完整性测试

| 测试 | 路径 | 结果 |
|---|---|---|
| 64 KiB 确定性载荷 | `writeFile -> readFile -> rename` | 暂存与改名后逐字节一致，已清理 |
| 4 MiB 确定性载荷 | `open -> 16 x 256 KiB write -> close` | size 与全量回读一致，约 1.49 秒，已清理 |
| 2 MiB 本地文件内容 | 本机 -> CDP -> IDE 页面 -> Remote Agent | 暂存与最终 SHA256 均匹配，约 1.24 秒，已清理 |
| 24 MiB 模型尺度载荷 | 96 x 256 KiB，同上完整链路 | 暂存与最终 SHA256 均匹配，约 9.10 秒 / 2.64 MiB/s，已清理 |
| 31.46 MiB 真实 P3 ZIP | 126 x 256 KiB，同上完整链路 | 纯上传 34.59 秒，双重校验后总计 89.18 秒，已清理 |
| 31.46 MiB 优化回归 | 126 x 256 KiB 串行写，后台 SHA256 + 改名后 stat | 纯上传 27.26 秒，总计 53.92 秒，已清理 |
| 31.46 MiB 终端校验回归 | 同上上传，容器端 `sha256sum` + 改名后 stat | 纯上传 26.58 秒，总计 27.31 秒，已清理 |

4 MiB 首次回读只得到约 256 KiB，原因不是写入损坏，而是单个 Persistent
Protocol packet 被拆成多个 WebSocket message。加入跨 message 累积缓冲并按
header length 重组后，4 MiB 全量回读逐字节一致。这是正式客户端的
强制实现要求。

### 8.3 断点续传实测

对 2 MiB 载荷写入前 1 MiB 后断开并重连：

- `open(path, {create: false})` 可打开已有文件，但后续 `write` 返回 `EBADF`；
- `open(path, {create: true})` 会立即将已有文件截断为 0 字节。

因此当前 provider 不支持“从已有 offset 继续写”。可靠恢复策略是保留
`.uploading` 后缀、重连后从头覆盖重传，完整校验后再原子改名。

## 9. 已验证的可复用上传路径

```text
本地文件读取（256 KiB 分块）
-> Chrome CDP 将当前分块传入已登录 IDE 页面
-> 页面内独立 Remote Agent WebSocket
-> remoteFilesystem.open(create=true)
-> remoteFilesystem.write(position, buffer, offset, length)
-> remoteFilesystem.close
-> stat + remoteterminal 中受限执行 sha256sum
-> remoteFilesystem 读取小型摘要 marker
-> rename(<target>.uploading, <target>, overwrite=true)
-> 再次 stat（可选严格模式再次 SHA256）
```

仓库内的可复用实现为：

```text
shared/tools/tencent_kaiwu_webide_upload.mjs
```

该模块必须在 Codex Chrome browser client 的 Node 会话中使用，调用方传入
已登录 IDE 的受控 `tab`；它不读取或持久化 Cookie，也不是可直接从普通
shell 运行的独立 CLI。最小调用形式：

```js
const { uploadKaiwuWebIdeFile } = await import(
  "./shared/tools/tencent_kaiwu_webide_upload.mjs"
);

const result = await uploadKaiwuWebIdeFile({
  tab,
  localPath: "/absolute/local/model.pkl",
  remotePath: "/data/projects/legged_robot_competition_26/agent_ppo/test_artifacts/model.pkl",
});
```

模块默认限制远程路径在 `agent_ppo/test_artifacts/` 下，并始终拒绝凭据与
Git 元数据路径。默认上传安全上限为 4 GiB，可通过 `maxUploadBytes` 向下收紧；
它不是 Remote Agent 的已验证能力声明。确需其他临时目录时必须显式传入
`remoteRoot`，但受保护路径仍不可覆盖。当前已使用 31.46 MiB 真实模型 ZIP
完成实测。模块返回 size、SHA256、分块数、用时和吞吐。
`deleteAfterVerify=true` 仅用于
POC，会在最终路径校验成功后删除测试文件。工具自身已使用仓库
小文件执行过默认终端校验、严格双 SHA、浏览器回读兼容模式和自动清理回归。

默认与兼容校验模式：

```js
verificationBackend: "terminal_sha256" // 默认，不全量回读模型
verificationBackend: "browser_readback" // 兼容回退，会全量读入浏览器内存
verificationMode: "staging_sha256_final_stat" // 默认：暂存 SHA + 改名后 stat
verificationMode: "double_sha256" // 严格模式：改名后再次 SHA
```

正式模型上传的必要前置与失败策略：

1. 用户已在指定 Chrome 中登录目标 IDE，且容器未被回收。
2. 上传前记录本地 size 和 SHA256，并校验远程目标位于白名单目录。
3. 每次使用新的临时连接标识，不记录 Cookie、完整 WebSocket URL 或鉴权帧。
4. 收包必须跨 WebSocket message 重组 Persistent Protocol packet。
5. 任一分块失败、连接断开、size 不符或 SHA256 不符时，不得改名；
   重建连接后从头覆盖 `.uploading` 文件。
6. 只有暂存文件校验成功后才原子改名；改名后再校验一次最终路径。
7. 默认校验不再全量 `readFile` 模型，只读取几十字节的摘要 marker；
   `browser_readback` 回退仍会占用浏览器内存，不能据此宣称超大文件已验证。
8. `remoteterminal` 只接受工具内部构造的 `/bin/sh -c` 参数，命令内容固定为
   `sha256sum -> 临时摘要 -> 原子改名`；公共 API 不接受任意命令文本。

优化实测确认：

- 512 KiB 和 1 MiB 数据块会逼近或超过 Chrome 扩展/CDP 单消息稳定上限；
- 同一文件描述符的 4 路并行 `write` 会导致请求超时；
- 因此脚本固定为 256 KiB 单路顺序写，不暴露未验证的并发开关；
- 默认由容器端 `sha256sum` 计算摘要，IDE 页面只轮询小型结果文件，既绕开
  单次 CDP 约 30 秒等待上限，也避免模型经 Remote Agent 再传回浏览器；
- 浏览器后台 `readFile + crypto.subtle.digest` 保留为兼容回退；
- 默认仅对 `.uploading` 文件做一次完整 SHA256，原子改名后校验 size。
  `verificationMode="double_sha256"` 保留严格双重校验。
