## 1. 一页结论

仓库已经不处于“要不要做高低层”的架构讨论期，而是已经进入了首轮 `nav_dagger` 平台联调和训练生命周期修复期。当前的训练架构已大致落地：冻结 `commandfull-34728` 低层，用特权 Oracle 生成 10 类离散 command token，训练 48 维输入、2×64 LSTM 的高层策略。

现在的首要阻力不是网络还没写，而是以下四个闭环没有同时成立：

1. **Oracle 能力闭环未过门**：已有平台首轮证据为 `0 completed / 256 timeout`。如果教师自己走不通迷宫，DAgger 学生只会更稳定地模仿一个无法完成任务的教师。
2. **平台发布生命周期未复验**：已找到 Nav 每 160 低层帧只推进 1 次 `BaseAgent.learn()` 的计数错误，当前修改为每个成功低层帧推进一次，但最新修复仍只有本地测试记录，没有新的平台模型池发布证据。
3. **组合 checkpoint 评估闭环未过门**：`NavEvalConfig` 和 Camera 强制 `lbc_loco` 时的升级防线已写，但尚无同 ID 组合包在平台完成一次身份校验、三模块加载和真实评估的证据。
4. **部署发布闭环还没开始实施**：现有默认部署树还是 Track `378413` / Actor80 / `lbc_loco`，而新路线的低层是 Standard `34728` / Actor77 / `kaiwu_train_v1`。`nav.onnx`、组合包导出器、release manifest、单线程双 session 影子模式和 Jetson p95 数据均不存在。

因此，下一步不应该直接开长时 DAgger，也不应该立即进入 PPO。应先用最小证据链依次证明：Oracle 能完成短链、平台能发布组合包、评估能读到同一组高低层权重。

## 4. `standard-com_34728` 的可核查事实

### 4.1 制品事实

- checkpoint：`archive/代码存档/standard-com_34728/ckpt/model.ckpt-commandfull-34728.pkl`
- 大小：13,639,635 bytes
- SHA256：`0ce3b485053faa5da37c2b0ad792ad414ec6f5a482208c728cee65487d019d0f`
- 平台任务：`234510`
- 平台记录训练步：`34728`
- 平台记录训练时长：`28813s`
- 生成时间：`2026-07-26T10:14:09+08:00`
- 格式血缘：`kaiwu_train_v1` 的 `commandfull` 训练恢复包，不是现有 exporter 直接接受的 `lbc_loco` 部署包。

### 4.2 结构事实

- 低层合同是 Standard Actor77：`proprio45 + latent32 -> action12`，`goal_dim=0`。
- 视觉编码器：`depth[180,320,1] -> CNN32`，与 `proprio45` 拼接后经 2 层 64 hidden LSTM，再生成 L2Norm `latent32`。
- 当前高层不分接低层 LSTM latent，而是使用同帧 `vision_encoder.cnn(depth)` 的原始 32 维 CNN 特征。这是为了避免低层 50Hz LSTM 和高层 5Hz LSTM 的时序语义漂移。
- 已冻结的 command 训练支撑域限制了当前词表：`vx <= 0.7`、`|vy| <= 0.2`、`|wz| <= 0.3`。

### 4.3 不能由归档文件推导的事

归档中未发现 34728 的固定 seed 分地形评估报告、原始视频索引、楼梯失稳统计或真机报告。因此：

- checkpoint 存在不等于低层已通过 B1 楼梯修复门。
- `commandfull` 表示命令泛化 schedule 到达 full 阶段，不自动表示高难地形、快速切换或真机已验收。
- 该包不能通过改名冒充 `lbc_loco` 进入部署。

## 5. 架构决策演进

### 5.1 2026-07-21 早期计划

早期方案的主要贡献是把低层能力门、高层导航门、严格 checkpoint 迁移和分级 Sim2Real 验收建立了起来。但其最终“单 checkpoint/单 ONNX/高低层有限联调”的实现形态已被后续设计修订。

### 5.2 2026-07-26 v1

决策收敛为：两个网络、一个组合 checkpoint、一个平台 ID、两个 ONNX；低层冻结，高层 5Hz 输出离散 command 词表。v1 原始建议直接实现 semi-MDP categorical recurrent PPO，并在部署侧使用独立 nav 线程。

### 5.3 2026-07-26 v2（当前设计权威版）

v2 改为：

- MVP 先做特权 Oracle BC -> DAgger，PPO 放到 DAgger 后的独立阶段。
- 部署默认为单控制线程、双 ONNX session，nav 在低层动作发布后的剩余时隙运行。
- freshness 随机化从第一个高层任务开始，不允许推迟到后期鲁棒化。
- `vision_encoder` 自高层验证起永久冻结；B1 若进行，只训 Actor77 + critic。
- 高层首轮的验收重点是管线、包、eval、探针和 Oracle-only 门，不是学生导航得分。

### 5.4 当前代码已比 v2 文档走得更远

代码与 Bug 台账表明以下项目已实现：

- `configure_app.toml [app].policy_entry="nav_dagger"` 在拼接 stage TOML 路径前选中训练阶段。
- `NavDaggerConfig` / `NavEvalConfig` 及评估纯推理分支。
- `HighLevelPolicy(48 -> LSTM 2x64 -> 10)`。
- `NavScheduler` 的 hold/slew/dwell/zero 急停和每环境 reset。
- `NavGoalChain` 的 UWB 等效采样、丢帧和 freshness。
- `NavTickBuffer` 与 16 tick TBPTT 序列交叉熵更新。
- 冻结 VisionEncoder/Actor77，optimizer 参数集必须精确等于 HighLevelPolicy。
- `nav_scanner` 特权特征压缩到 `[available,front,left,right]`，支持平台实际 273-ray 非方阵网格。
- 组合 checkpoint 的 high_level codec、低层 digest、契约校验和 nav 候选选择。
- Camera 被平台送入 `lbc_loco` 时，发现 nav 包并升级到完整高低层装配的防线。
- 完整开发容器 smoke 工具、原子 JSONL 事件链和细粒度 lifecycle 探针。

## 7. 当前训练链路

```text
Track + Camera worker
  -> policy obs: proprio45 | height_scan256 | measured goal4 | depth57600
  -> critic obs: critic proprio60 | height_scan256 | true goal3 | nav_priv4

aisrv NavScheduler (50Hz)
  -> exec_cmd 写入 policy[6:9] / critic[9:12]
  -> 冻结 VisionEncoder + Actor77 输出 joint12
  -> 每 10 帧：CNN raw32 + goal4 + exec3 + held3 + ang_vel3 + gravity3
  -> HighLevelPolicy 输出 10 类 token
  -> Oracle 从特权 critic obs 生成标签
  -> NavTickBuffer 收集 16 tick
  -> 序列 CE/TBPTT 更新高层
  -> DAgger ramp 控制 Oracle/学生驱动比例
```

关键契约：

- 低层 50Hz，高层 5Hz，训练与部署必须同值。
- 新 token 在 nav tick 得出，从下一个 50Hz 帧起通过 slew 影响低层，有一帧确定性延迟。
- zero token 绕过 slew，立即急停。
- 高层 Actor 不得看 height scan、terrain type、全局位置、精确接触力或未验证的 base linear velocity。
- checkpoint 内不保存活 LSTM hidden 和 per-env scheduler 状态；resume 后全环境 reset。

## 8. 主要阻力与判断

### P0：Oracle 不能完成短链（能力阻断）

当前 Oracle 是一个反应式规则器：目标角度大时原地转/慢转，直行时检查前墙并选开阔一侧。它没有显式的通道中心线、路口状态、脱困记忆、死胡同回退或子目标。`0/256` 说明“有墙特征”不等于“教师能完成任务”。

目前不应先调学生网络、CE 学习率或 DAgger ramp。必须先把 Oracle-only 的失败按赛道段、超时位置、token 序列、墙分数和 goal 角度分类，确认它是困在坡地进入、迷宫入口、通道中、路口还是终点停车。

### P0：平台模型发布仍待真实任务证明（工程阻断）

现有证据已说明业务侧 `save_model()` 写出文件不等于模型池登记。最新修复改成每个成功低层批量帧调用一次 lifecycle callback，并把平台自动发布作为唯一常规发布路径。下一个 smoke 必须同时核对：

- callback 成功/失败计数；
- 父 ID 与当前平台 ID 差值；
- `dump_model_freq=1000` 边界；
- 模型池列表真实出现新 ID；
- 下载包的 checkpoint 标签、包内 ID、父血缘和 high_level 是否存在。

### P0：评估入口还没有平台闭环（可用性阻断）

评估不应仅依赖“加载器单测通过”。必须看到以下完整自检：requested ID、选中绝对路径、文件 SHA256、包内 ID/血缘、low-level digest、high_level present、实际加载模块列表，且第一次 inference 不能在这些检查之前发生。

### P1：34728 低层能力门证据不完整

v2 把“高层架构验证轮先行”和“B1 楼梯修复后再做正式 DAgger”分开。当前 34728 可以作为架构验证父模型，但若要把它直接定义为“正式低层”，仍需补齐：

- 固定 seed 的坡/楼梯/平地分项；
- 连续 command 与 10 token/2s dwell 阶梯切换的对照；
- 后腿外展、支撑对称、终止类型和恢复步数视频抽查；
- command 包络实测，特别是 pure yaw 和低速。

### P1：活动文档与实际代码不同步

- 根 `README.md` 和 `server/README.md` 仍将 `visual_policy_optimization` / command generalization 描述为活动基线，但当前 `configure_app.toml` 和 `Config.CURRENT` 都是 `nav_dagger`。
- v2 的多个“S0 未知”已有部分答案：Track+Camera 能进真实更新，256 能启动但固定降到 128，273-ray scanner 结构已知。
- `shared/interfaces/server-deploy-contract.md` 仍是 `v0.3`，只在统一包 schema 中泛化预留 `modules.high_level`，还没正式写入 nav.onnx I/O、单线程时序、一帧延迟、vocab/slew/dwell/freshness 成对常数和 release manifest。
- `deploy/sim2real_test_loco/ARTIFACTS.md` 的 `proprio[6:9]` 仍写“上一帧 cmd / 固定注入”；新 Nav 契约是当帧 `exec_cmd[t]` 写入低层观测，新 token 从下一帧生效。

文档落后会直接造成错误的训练/评估操作，不是单纯的文档美化问题。

### P1：部署路线与新模型合同存在结构断层

现有默认部署树的真实状态：

- checkpoint 是 `model.ckpt-vision-378413.pkl`，Track Actor80，`format=lbc_loco`。
- `policy.onnx`、Jetson C++ binary 和 ONNX Runtime 仍待生成/构建/部署。
- 8 入 8 出的 nav state 端口只是透传占位，`command_source=nav` 当前等价零速。
- 当前 exporter 拒绝 `kaiwu_train_v1`，不会从组合包导出 Actor77 loco.onnx 和 nav.onnx。

新路线需要的是一个新的、可验收的发布流水线，而不是在当前 378413 路线上仅切换 `command_source=nav`。

### P2：Jetson 实时性和真机降级链全部是未知

v2 将默认实现收敛为单线程双 session，这降低了并发复杂度，但并没有消除计算预算未知。nav 帧比例约 10%，恰好会落入整体 p95 统计。在真实 `nav.onnx` 出现前，无法预测：

- nav 帧是否挤压下一个 20ms 低层周期；
- 跳 nav tick 是否会造成持续延迟或命令抖动；
- 从 nav 降级到 UWB 巡航、再降级到停车的状态机是否与训练语义一致。

## 9. 建议的下一阶段顺序

### 步骤 0：固化当前实验基线

在继续修复前，先把当前工作区拆成可审查单元：最新 Nav 行为修复、生命周期修复、历史配置清理、同步/RPC 工具和文档。每个单元记录对应平台任务、父模型、测试和回滚点。这不是洁癖，而是防止下一个平台结果无法归因。

### 步骤 1：单独解决 Oracle-only 门

固定 128 env、ramp=0、短 track，不训学生。必须输出每段超时位置、token 序列、front/left/right 分数、goal 角度/距离和实际进度。先让 Oracle 在短链上有稳定非零完成率，再讨论是否进入 DAgger。

Oracle 可能需要的升级优先级：

1. 明确的状态机：进入迷宫、沿通道、路口选择、脱困、终点。
2. 短期记忆/转向承诺，不只依赖 2s dwell 对称打破。
3. 用特权 track 进度或局部子目标作为教师内部信息，但不泄漏到学生 Actor 输入。
4. 拼接坡地和迷宫的专项门，避免“通道 Oracle 修好了但低层在坡段耗尽时间”。

### 步骤 2：一次最小平台发布 smoke

在同一任务中只验证：真实 34728 preload -> 首个有效 TBPTT update -> 1000 个成功 lifecycle callback -> 模型池出现新 ID -> 下载包存在 high_level。不在这个任务里同时调 Oracle、监控和长训超参。

### 步骤 3：组合包 Camera eval smoke

用步骤 2 的确切 ID 启动评估，以加载身份闭环为验收目标，不以分数为验收目标。如果评估分数不好，但三模块身份和输入契约完全正确，才进入策略能力调查。

### 步骤 4：架构验证轮 DAgger

只在 Oracle-only 过门、发布和 eval 都闭环后开始。这一轮的目标是证明学生能够学到 Oracle，不是宣称得到正式导航模型。需要至少关注 CE、top1、分歧率、token 混淆矩阵、学生驱动比例、学生驱动时的完成率和低层终止分布。

### 步骤 5：决定 B1 与正式 DAgger 的父模型

若 34728 只满足架构验证，不满足楼梯/切换门，就按 v2 执行 B1：永冻 encoder，只训 Actor77 + critic，command 域先不变。B1 通过后，以新低层 ID 从头训正式高层，不做跨包高层权重嫁接。

### 步骤 6：在正式 DAgger 前冻结部署契约草案

这一步不需要等导航权重训完。先原子定义：

- Standard Actor77 loco.onnx 的导出来源；
- nav.onnx 的 I/O 和 state reset；
- 单线程每 10 帧调度、一帧生效延迟和跳 tick 规则；
- clamp/slew/dwell/zero/freshness 的成对常数；
- `manifest.json` 中绑定两个 ONNX 与同一源 checkpoint SHA256 的规则；
- `capabilities.deployable` 和 `freshness_randomized` 的导出硬门。

### 步骤 7：影子模式后再接管

真实 nav.onnx 出来后，先在 `command_source=uwb` 下运行 `apply=false`，分开统计 nav 帧和非 nav 帧的 p50/p95/max、实际 Hz、跳帧率和命令切换率。只有影子路径通过才允许 `apply=true`。

## 10. 暂不应该做的事

- 不在 Oracle-only 为 0 时直接延长 DAgger 训练。
